# Правила разработки

Обязательны для всех — людей и AI-агентов. Если правило мешает, его меняют отдельным PR
с обоснованием, а не нарушают молча.

## 1. Задачи и ветки
1. Одна задача — одна ветка — один PR. Ветки: `feat/<кратко>`, `fix/<кратко>`,
   `chore/<кратко>`, `docs/<кратко>`.
2. В `main` напрямую не пушим; `main` всегда собирается и проходит `npm run check`.
3. Мёрж — squash; заголовок PR = заголовок коммита.
4. Коммиты — [Conventional Commits](https://www.conventionalcommits.org/ru/):
   `feat(bookings): запрет пересечения броней`. Тип и scope — английские, описание — по-русски
   или по-английски.
5. Задачу формулируем проверяемо: цель, ограничения (что нельзя трогать), критерии готовности
   (шаблон — `docs/agents/TASK_TEMPLATE.md`).

## 2. Код
1. TypeScript strict, ESM. `any` запрещён (`unknown` + сужение типа).
2. Идентификаторы, имена файлов, API — на английском. Комментарии, документация, тексты UI — на
   русском. Термины — по глоссарию в `AGENTS.md`.
3. Комментарий объясняет «почему», а не «что». Неочевидные инварианты — комментарием рядом
   с кодом и в `MODULE.md`.
4. Без попутных рефакторингов: замеченное вне задачи — в `docs/agents/TECH_DEBT.md`.
5. Форматирование — Prettier (`.prettierrc`), линт — oxlint; предупреждения не копим.
6. Новая зависимость — только если без неё заметно хуже; указать причину в описании PR.

## 3. Архитектура api
1. Домен = модуль `apps/api/src/modules/<domain>/` (`*.module.ts`, `*.controller.ts`,
   `*.service.ts`, `dto/`, `MODULE.md`, `*.spec.ts`).
2. Контроллер тонкий: разбор запроса, вызов сервиса, ответ. Бизнес-логика — в сервисах.
3. Вход валидируется схемой (zod) на границе; внутрь передаются уже типизированные данные.
4. Контракты, которые видит фронтенд, — в `@btx24/shared`, а не копией в web.
5. Конфигурация — только через `apps/api/src/config/env.ts`; `process.env` в остальном коде
   не читаем.
6. Ошибки — исключения Nest (`BadRequestException`, `ConflictException`, …) с понятным
   сообщением; 500 — только для действительно неожиданного.

## 4. Предметная область бронирования
1. **Тенант = портал Битрикс24.** Все доменные таблицы содержат `portalId`; все запросы
   фильтруются по порталу из контекста аутентификации. Тест на изоляцию тенантов — обязателен
   для каждого нового репозитория/сервиса данных.
2. **Время** хранится в UTC (`timestamptz`), интервалы полуоткрытые `[start, end)`. Конвертация
   в часовой пояс — только на границах (расчёт слотов, отображение). «День» — понятие часового
   пояса, а не UTC.
3. **Брони и ресурсы хранит Битрикс24** (`booking.v1.*`, ADR 0003). Пересечения отсекает
   Битрикс24 (`1018` → `409 Conflict`); наша предварительная проверка — для понятной ошибки.
4. **Бронь привязана к сделке**; товары и суммы — в сделке. `crm.deal.productrows.set`
   заменяет все строки — передаём полный список.
5. **Идемпотентность и сбои:** многошаговые операции (сделка → бронь → связь → товары) ведутся
   журналом с ключом идемпотентности; при частичном сбое — компенсация или явный статус
   «требует внимания», а не молчаливая полупровалившаяся бронь. Обработчики событий
   Битрикс24 безопасны к повторной доставке.
6. Портал-специфичное (коды UF-полей, стадии, шаблоны БП, часовой пояс) — только в настройках
   портала, не в коде.
7. Статусы брони меняются только через явные переходы в сервисе (никаких произвольных
   `update status`).

## 5. Интеграция с Битрикс24
1. Все REST-вызовы — через единый клиент модуля `bitrix24`; доменные модули не ходят в портал
   напрямую.
2. OAuth-токены портала хранятся зашифрованными; refresh выполняется централизованно.
3. Учитываем лимиты REST (очередь/батчи `batch`), ошибки `QUERY_LIMIT_EXCEEDED` и
   `expired_token` обрабатываются клиентом, а не каждым вызывающим.
4. Входящие события и запросы установки проверяются (`application_token`, подпись/параметры
   авторизации) до любой обработки.
5. Подробности и ссылки на официальную документацию — `docs/bitrix24/README.md`.

## 6. База данных и миграции
1. Схема меняется только миграциями Prisma (`npm run prisma:migrate -w @btx24/api -- --name <имя>`).
   Применённые миграции не редактируются — исправление новой миграцией.
2. То, что Prisma не выражает (EXCLUDE, частичные индексы, CHECK), — дописывается SQL в ту же
   миграцию с комментарием, зачем это нужно.
3. Деструктивные изменения (удаление колонки/таблицы, смена типа) — в два шага (перестать
   использовать → удалить) и с явным упоминанием в PR.
4. Индексы — под реальные запросы (как минимум `portalId` + поле фильтрации).

## 7. Безопасность
1. Секреты — только в `.env` (не коммитится) и переменных окружения. В коде, логах, тестах,
   описаниях PR и ответах агентов секретов быть не должно.
2. Логи не содержат токенов, `AUTH_ID`, персональных данных сверх необходимого.
3. Авторизация проверяется на сервере для каждого эндпоинта; скрытая в UI кнопка — не защита.
4. Iframe-встраивание не ломаем (`X-Frame-Options` не включаем), но CORS и cookies
   настраиваем строго под домены портала.

## 8. Тесты и проверки
1. Новая логика — с unit-тестами (`*.spec.ts`, vitest) рядом с кодом. Для бронирования
   обязательны граничные случаи: соседние интервалы, пересечение на минуту, смена дня в
   часовом поясе, переход на летнее время (где применимо), повторный запрос.
2. Перед PR: `npm run check` локально. CI повторяет его и прогоняет миграции на чистой БД.
3. В PR — точные команды и их результат, а не «тесты проходят». Не запускали что-то — так и
   пишем, с причиной.

## 9. Документация
1. У каждого модуля есть `MODULE.md`: назначение, инварианты, подводные камни, контракт.
2. Изменили поведение → обновили `MODULE.md`/`docs/features/*.md` в том же PR.
3. Архитектурные решения — ADR в `docs/decisions/NNNN-<тема>.md` (контекст, решение,
   последствия).
4. Новый доменный термин → глоссарий в `AGENTS.md` и `tools/mcp-server/domain-aliases.json`.

## 10. Стенд и общий сервер
1. Стенд поднимается `docker compose up -d --build` (см. `README.md`).
2. Сервер общий: `docker compose down -v`, удаление томов, `prisma migrate reset`, правка `.env`
   на сервере — только по согласованию с владельцем.
3. PostgreSQL слушает только `127.0.0.1`; наружу приложение публикуется через reverse proxy
   с HTTPS.

## 11. Работа AI-агентов
1. Агент следует `AGENTS.md`; MCP-сервер `btx-dev` — основной способ навигации и диагностики.
2. Агент не расширяет scope задачи, не коммитит и не пушит без явной просьбы, не выполняет
   разрушительных команд без подтверждения.
3. Параллельные агенты работают в отдельных ветках/worktree; изменения общих файлов —
   узкие и аддитивные.
4. Итог работы агента: что сделано, какие проверки запущены (с результатом), что не
   проверено и почему.
