# openlines

**Назначение:** чаты открытых линий и дашборд менеджера. Сделки, клиенты, звонки и сотрудники для
дашборда — из копии CRM (`modules/crm-mirror`, ADR 0013), когда она загружена; права — токеном сотрудника. Маршруты (`B24AuthGuard`):

| Маршрут                                                        | Право            | Что                                                                                       |
| -------------------------------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------- |
| `GET /api/dashboard?from=YYYY-MM-DD&to=YYYY-MM-DD`              | любая группа     | свои показатели за дни `[from, to]` (≤92, по умолчанию сегодня): с кем общались, брони из журнала — сделки с бронью и отменённые; ожидания за всё доступное время, состояние на сейчас |
| `GET /api/dashboard/calls?kind=incoming\|new\|repeat\|answered\|missed\|lost&from=&to=&scope=all\|mine&funnel=` | любая группа | клиенты вида за период — окно со сделками (`call-stats.ts`) |
| `GET /api/dashboard/activity?date=YYYY-MM-DD`                 | руководитель или администратор приложения | «Активность сотрудников» за день по всем24часам (`activity.service.ts`, см. ниже) |
| `POST /api/dashboard/hidden-chats/:chatId`                     | `openlines.read` | 👁 скрыть чат с **своего** дашборда (`DashboardHiddenChat`); в списке чатов он остаётся |
| `GET /api/openlines/chats?scope=all\|mine&status=all\|waiting&from=&to=&offset=` | `openlines.read` | список чатов, сверху — с самыми новыми сообщениями                                        |
| `GET/POST /api/openlines/folders`, `PUT/DELETE /api/openlines/folders/:id` | `openlines.read` | **личные папки** чатов (охрана, ресепшн, АХО…) со сводкой: число чатов, непрочитанные, последнее сообщение |
| `PUT /api/openlines/folders/:id/chats/:chatId`, `DELETE /api/openlines/folder-chats/:chatId` | `openlines.read` | положить / перенести чат в папку, вернуть в общий список |
| `GET /api/openlines/chats/search?q=<номер>`                    | `openlines.read` | поиск по телефону клиента по всему порталу: `crm.duplicate.findbycomm` → `imopenlines.crm.chat.get` |
| `GET /api/openlines/chats/:chatId/messages?beforeId=`          | `openlines.read` | история (50 сообщений, старее — по `beforeId`)                                            |
| `POST /api/openlines/chats/:chatId/join`                       | `openlines.send` | войти в диалог (`imopenlines.session.join`)                                               |
| `POST /api/openlines/chats/:chatId/send`                       | `openlines.send` | цепочка сообщений по порядку                                                              |
| `POST /api/openlines/files` (multipart `file`, ≤10 МБ)         | `openlines.send` | вложение для цепочки/шаблона                                                              |
| `GET/POST/PUT/DELETE /api/openlines/templates[/:id]`           | `openlines.send` | **личные** шаблоны: название + цепочка (текст и вложения)                                 |

Право = `openlines.read`/`openlines.send` хотя бы в одной группе или администратор приложения.
Что именно видно и можно — решает Битрикс24 по **токену пользователя**.

**Порядок — как в списке диалогов Битрикс24** (`/contact_center/dialog_list/`, сверено на
портале): по последнему сообщению **клиента или оператора**; системные сообщения и боты не в
счёт (`lastMeaningful`). REST этого списка не отдаёт (из 58 методов `imopenlines.*` нет
списочного), а дата изменения дела CRM за сообщениями не следует (у сессии 19216 дело не менялось
с создания, хотя клиент писал сутки спустя). Поэтому точный порядок даёт только **индекс**
`OpenlineChat`: worker раз в минуту обходит все открытые сессии и закрытые с прошлого прохода
(первый проход — за неделю, ~25 с на 660 чатов) и хранит по чату только сессию, ответственного,
канал, время и автора последнего сообщения. Индекс ведётся, **только пока включён «сбор
метаданных диалогов»** (⚙ → «Приложение»); выключили — строки удаляются. Список по индексу:
порядок из индекса, видимость и данные — запросами токеном пользователя (`exactOrder: true`).

**Без индекса** (сбор выключен или индекс старше 15 минут) — запасной способ ниже,
`exactOrder: false`, интерфейс предупреждает, что порядок приблизительный.

**Как строится список чатов без индекса.** REST не отдаёт «все диалоги линии», а события открытых линий
приходят приложению только для его собственного коннектора (не для WhatsApp/Telegram и т. п.).
Поэтому источник — дела CRM `PROVIDER_ID = IMOPENLINES_SESSION` (`crm.activity.list`, видны по
правам CRM, есть ответственный): «мои» — ответственный я; «отдел» — я и активные сотрудники моих
отделов с вложенными; «все» — без фильтра. Затем пакетно `imopenlines.dialog.get` по сессии (чат,
роль, привязки CRM) и `im.dialog.messages.get` (5 последних). Сортировка по последнему
сообщению — **в пределах страницы** (50 сессий, упорядоченных CRM по `LAST_UPDATED`).

**Звонки на дашборде — по клиентам**, не по звонкам (решение владельца 2026-10-21): дела CRM
`PROVIDER_ID = VOXIMPLANT_CALL` токеном пользователя (его права), `call-stats.ts`. Клиент — контакт
из `COMMUNICATIONS` (без него — последние 10 цифр номера, без номера — элемент CRM): 3 звонка от
клиента и 2 ему — один клиент. Виды: входящие (клиенты с входящим в периоде), уникальные /
повторные, отвеченные (был отвеченный входящий), пропущенные (был `SETTINGS.MISSED_CALL`),
упущенные (после последнего пропущенного не состоялся успешный входящий/исходящий разговор
или общение с сотрудником в чате — в том числе после периода и другим сотрудником). **Повторный** — у контакта есть **состоявшаяся** сделка в
выбранной воронке (`callsFunnel`, из воронок групп пользователя) до его первого звонка в периоде:
не проиграна и её бронь (системное поле «завершение бронирования») уже закончилась; без даты брони
— выигранная, закрытая раньше; **покупка сертификата** (поле «Тип сделки» = «Покупка сертификата»,
брони у неё нет) — не проиграна и оплачена («Сумма внесённых оплат» > 0 или выиграна),
`happened` в `bookings/deal-outcome.ts` (решение владельца 2026-10-23). Уточнение владельца: большинство
прошедших броней не переводят в «успешно». «Мои» — входящие, где ответственный я.
«Не дозвонились» на исходящих по делам не видно — нужна статистика телефонии (право `telephony`).
**Журнал звонков дня** (запрос владельца 2026-10-22): плитка «Все звонки» за период (`callsTotal`,
входящие и исходящие по «Все/Мои») и `GET /api/dashboard/call-log?date&scope` — каждый звонок: время,
длительность (`END_TIME − START_TIME`), направление, статус (`callStatus`: входящий — пропущен по
`MISSED_CALL`; исходящий с нулевой длительностью — «нет ответа»), номер клиента, сотрудник
(ответственный), контакт, элемент CRM. Номер линии компании («куда звонили» у входящих) — только со
статистикой телефонии; пока вместо него сотрудник. Блок **«Звонки»** дашборда —
`GET /api/dashboard/recent-calls?scope&from&to` — последние 50 звонков периода дашборда (дела CRM, правами
сотрудника), новые сверху; дашборд показывает по 5 («Показать ещё 5»). Цвет строки (решение владельца
2026-10-23): входящий — зелёный, исходящий — голубой, исходящий без ответа — жёлтый, пропущенный — красный;
длительность разговора; за один день — только время, за период — с датой (так же в «Сделках за …»).

**Папки** (`ChatFolder`, `ChatFolderItem`) — личные: видит и меняет только владелец; чат — в одной
папке сотрудника. Чаты моих папок **не показываются в общем списке** (`?folder=` — только они).
Удаление папки возвращает чаты в общий список. **Непрочитанные** (`ChatSummary.unread`) — личные
счётчики мессенджера сотрудника (`im.recent.list`, `ONLY_OPENLINES`): есть только у чатов, где он
участник.

**Телефоны клиента** в сводке (`phones`) — из привязанных контакта/лида/компании, одним пакетом
`crm.*.list` токеном пользователя; не сохраняются. В интерфейсе: часть номера ищется среди
загруженных чатов, полный номер (10+ цифр) — по всему порталу. По умолчанию — «Все доступные».

**Инварианты**

- «Ждёт ответа» = последнее сообщение клиента или оператора — от клиента (`users[].connector`) и сессия не
  закрыта. Нет доступа к диалогу (`ACCESS_ERROR`) — чат не показывается.
- Участник чата — `role` диалога не `guest`; писать можно только участнику с `openlines.send`.
- Отправка: шаг без файлов — `im.message.add`; с файлами — `im.v2.File.upload` (право `im`,
  текст уходит с первым файлом). На ошибке — стоп, ответ `{ sent, error }`, интерфейс оставляет
  неотправленные шаги. Запись в Битрикс24 подчиняется режиму «только чтение» и песочнице.
- **Тексты сообщений не сохраняем** — только показываем (переключатели сбора данных в настройках
  — для будущей аналитики). Храним лишь шаблоны и файлы вложений автора.
- Шаблоны и файлы видит и меняет только автор (`portalId` + `ownerUserId`); чужой id — 404.
  Разовые вложения удаляются после успешной отправки, неиспользованные — через сутки.
- Брони в дашборде — из журнала приложения (`bookings`, ADR 0006): свои клиентские брони,
  созданные за период, и свои брони, отменённые за период (с причиной). Названия сделок и
  ресурсов — токеном пользователя; недоступная ему сделка → `deal: null`.

**Пока нет:** живых обновлений (опрос: список — 30 с, открытый чат — 15 с), отметки «прочитано»,
защиты от повторной отправки при обрыве связи (кнопка блокируется на время отправки).

**Файлы сообщений** (2026-10-22): картинки, видео и документы чата идут через
`GET /api/openlines/chats/:chatId/files/:fileId` — прямые ссылки портала во фрейме не открываются
(нет входа в Битрикс24 у стороннего домена). Доступ к диалогу — правами сотрудника
(`imopenlines.dialog.get`), ссылка `im.v2.File.download` — его токеном, а если он не участник чата —
токеном приложения; скачивание — `Bitrix24RestClient.download` (только хост портала, до 50 МБ).
**Отправка файлов**: `im.v2.File.upload` с `fields.name/content` (вложенный `FILE` портал отвергает
`FILE_EMPTY`); у шага сначала текст, потом файлы отдельными сообщениями, пауза 1,5 с между
сообщениями (каналы доставляют асинхронно — иначе порядок путается).

**Шаблоны**: личные и общие (`MessageTemplate.shared`; общие меняют администраторы приложения, их
файлы доступны всем). Назначение `purpose`: `chat` — для чатов; `payment` — системный шаблон
сообщения со ссылкой на оплату (только администраторы, всегда общий; группа выбирает его в «Оплаты»,
в списке шаблонов чата его нет; пока выбран в группе — не удалить и не сменить назначение). Переменные (`renderMessage` в @btx24/shared): `{{Поле сделки}}`,
`{{Контакт: Поле}}`, `{=Variable:programm}`, `{=Document:…}`, `{client_name}`… — данные собирает
`MessageContextService` (bookings). При вставке шаблона в чат — `POST …/chats/:chatId/render` по сделке
чата; страница «Шаблоны» — `GET /openlines/templates/variables`, `POST /openlines/templates/preview`.

**Кэш списка чатов** (запрос владельца 2026-10-22): `OpenlineChat` хранит и сводку чата (название,
CRM, телефоны, последнее сообщение, автор, превью — превью только при «сборе текстов») — **одна строка на
чат, общая** для всех; `OpenlineChatAccess` — доступ **каждого сотрудника** к чату (как ответил
Битрикс24 на `imopenlines.dialog.get` его токеном; участник ли он). Список: страница индекса →
`cachedSummaries` (сводки + свои доступы из базы; вживую — только непрочитанные). Нет сводки или своего
доступа хоть у одного чата страницы — живая загрузка (холодный старт), она же заполняет кэш. Устаревшее
(сводка > 30 с, доступ > 5 мин) сверяется с Битрикс24 в фоне его токеном; следующее обновление списка
(раз в 15 с) уже свежее. Worker обновляет сводки всех чатов индекса раз в минуту, открытие переписки —
строку своего чата. Чужие чаты в список не попадают: без строки доступа — живая проверка, `allowed=false`
скрывает. Выключили сбор метаданных — кэш и доступы удаляются, сбор текстов — удаляются превью.
**Сообщения с телефона (Wazzup)**: строка `=== Исходящее сообщение, автор: … ===` (в начале текста или
после цитаты `>>…`) — сообщение сотрудника: справа, «📱 с телефона», не «ждёт ответа».

**Дашборд (решение владельца 2026-10-22):** в одном ряду — «Чатов ждут ответа» (→ чаты), «Все звонки»
(→ страница «Звонки»: входящие, уникальные, повторные, отвеченные, пропущенные, упущенные — по
клиентам, со списками), «Новых сделок» и «Повторные клиенты» (`newDeals`: сделки с `DATE_CREATE` в
периоде в воронках групп пользователя, «Мои» — `ASSIGNED_BY_ID` = я; повторный — у контакта есть
состоявшаяся сделка той же воронки, созданная раньше, `dealHappened`). Ниже — «Новые бронирования» и
«Удалённые бронирования» за период (`BookingJournalService.forPeriod`): любого источника — приложение и
найденные сверкой в Битрикс24; по ресурсам групп сотрудника («Мои» — создал или снял я); удалённые —
снятые, неоплаченные, удалённые в Битрикс24 и брони приложения, пропавшие в Битрикс24 (ждут решения).
Записи журнала не удаляются — история остаётся. На странице «Звонки» под плитками — журнал звонков дня.
Уведомления о бронях — кнопка «Уведомления» со счётчиком в шапке.

**«Не требует ответа» (решение владельца 2026-10-22):** одна отметка на чат для всех сотрудников —
`PUT /api/openlines/chats/:chatId/reply-status {needed}` (`openlines.read`), поля `OpenlineChat.noReply*`.
Привязана к последнему сообщению (`noReplyMessageId`): новое сообщение клиента снова «ждёт ответа»
(`isWaiting`). «Ждут ответа» на дашборде — по **всем доступным** сотруднику чатам из кэша (`attention`),
там же «Требуют внимания» — последние сообщения клиентов без ответа. Из дашборда «Открыть чаты» —
сразу «Ждут ответа» (все доступные), если они есть.
**Каналы клиента:** `GET /api/openlines/chats/:chatId/channels` — чаты того же контакта в других
открытых линиях (у каждой линии свой чат); переключатель в шапке чата открывает нужный чат.
Отправка сообщения закрывает блок ввода загрузчиком до ответа сервера.

**Дашборд менеджера (решение владельца 2026-10-23):** «Сделки за сегодня» — над «Бронями сегодня». В обоих
строка: сумма → сделка и клиент → ресурс брони → время брони; бронь прошла — голубая, идёт — зелёная,
впереди — жёлтая. Оплаченная сделка (`DashboardNewDeal.paid`: оплачен счёт приложения или есть «Сумма
внесённых оплат») — зелёная, с 🪙; бронь новой сделки — `slot` (идущая или ближайшая активная из журнала).
«Последние сообщения клиентов без ответа»: канал → аватарка клиента (`OpenlineChat.clientAvatar` — `avatar`
пользователя-коннектора из `im.dialog.messages.get`, пишут worker, список и открытие чата) → имя; время —
«сегодня в 18:11», «вчера в 18:15», раньше — датой; кнопки: сделка, чат, 👁 «скрыть с дашборда» (с
подтверждением; скрытые не входят и в «ждут ответа» этого сотрудника). Аватарка сотрудника в шапке —
`SessionInfo.user.photo` (`user.current` → `PERSONAL_PHOTO`, на 10 минут).
В «Сделках» — переключатель «за сегодня / с оплатой сегодня» и счётчик «39/2»: созданные за период и
сделки, по которым за период **поступила оплата** (`paidDeals`, любая дата создания, те же воронки и «Мои»).
Оплата (`DealPaymentsService.paidIn`, правами сотрудника): прежде всего **смарт-счета, переведённые в
«Оплачен» за период** (`crm.item.list`, `entityTypeId 31`, фильтр по `movedTime`, стадия `…:P`) — точное время
оплаты и история за любой период (так работают «30 дней»). Учёт worker'а (рост «Суммы внесённых оплат»,
`DealPaidAmount`/`DealPayment`, время — изменение сделки) — только для сделок **без оплаченных счетов**
(внесли вручную): у оплаченной счётом сделки поле меняется позже, и это не оплата того дня. Справа в строке
вкладки «С оплатой» — сумма и время оплаты, дата брони — в подписи. Нет доступа к счетам — `paidDeals: null`.
Сумма сделки пустая или 0 — «0 ₽». Низ списков блоков — «Показать ещё · 5 из 12» / «Свернуть» (`ListMore`).

**Личный дашборд** (решение владельца 2026-10-24): `GET/PUT/DELETE /api/dashboard/layout` — блоки по
порядку и ширина (⅙, ⅕, ¼, ⅓, ½, весь ряд; `DashboardLayout`, каталог — `DASHBOARD_BLOCKS` в shared). Блоки бывшего дашборда
руководителя — в общем каталоге (`/api/head-dashboard` — любому сотруднику групп, его правами);
«Активность сотрудников» — только администраторам приложения (и в каталоге, и `dashboard/activity`). Роль
«Руководитель» убрана (`AppHead` больше не читается, таблица оставлена). Новые блоки: «Сделки к закрытию»
(`dashboard/needs-close`), уведомления о бронях, сертификаты, стопы ресурсов (`GET /api/resource-stops`).

Каталог «Добавить блок» показывает только ещё не добавленные типы блоков.

**Карточка звонка** (`call-card.service.ts`, `GET /api/calls/card`, `GET /api/calls/active`): клиент по привязке
звонка или номеру, брони, сделки в работе с цветом (`DealStatusService.tones`: бронь / поля брони / пустая) и
статусом, последние сообщения свежего чата, предложенная сделка (сделка звонка, иначе самая новая открытая).

**Статус сделки** (решение владельца 2026-10-23) — у каждой сделки на дашборде (новые, с оплатой, брони
сегодня/завтра, новые/удалённые брони) и в звонках (последние, окно звонков, журнал дня — если звонок
привязан к сделке): `DealStatusService` (bookings) → `dealStatus` из shared. Канбан: провал — «Провалена»,
успех — «Завершена»; в работе — «Клиент приехал», если бронь идёт сейчас, «Ожидание клиента», если
активная бронь впереди, иначе «В работе». В работе, а бронь прошла — «Завершена» с красным «!» «закройте сделку в
Битрикс24» (`needsClose`). Брони — из журнала (без удалённых в Битрикс24 и ждущих решения); журнал о
сделке не знает — поле «конец брони» сделки. Сделки — правами сотрудника; сбой статусов звонков не
ломает звонки.

**Глобальные папки, избранное, счётчики** (решение владельца 2026-10-23). `ChatFolder.global`: папку видят
все сотрудники с доступом хотя бы к одному её чату (кэш `OpenlineChatAccess`) — только доступные чаты; своя
папка важнее чужой глобальной; меняет только владелец; «Не обращать внимания» глобальной папки действует у
всех (дашборд). «★ Избранное» (`ChatFavorite`, личное) — псевдопапка `FAVORITES_FOLDER` вверху списка, чаты
остаются и в общем списке. Счётчик непрочитанных (личный счётчик мессенджера `im.recent.list`) — в углу
аватарки чата и иконки папки (сумма по её чатам); «Не требует ответа» обнуляет счётчик чата у всех (пока
отметка действует) и отмечает чат прочитанным у отметившего (`im.dialog.read`).

**Папка «Не обращать внимания»** (`ChatFolder.ignoreAttention`, личная): чаты папки не попадают в
«Требуют внимания» и «ждут ответа» на дашборде владельца папки. **Дашборд частями**
(`?part=base|calls|deals`): основа (чаты из кэша, брони, сегодня/завтра) — сразу, звонки и новые сделки —
отдельно. Завершённые ответы DashboardService/HeadDashboardService не кэшируются;
объединяются только одновременные одинаковые запросы. Клиентские снимки и фоновый опрос —
[dashboard-sync](../../../../../docs/features/dashboard-sync.md); базовая часть с бронями без снимков.

## Имя клиента в чатах
`OpenlineChat.clientName` — контакт (или компания/лид) из привязок CRM, тем же пакетом, что телефоны
(`phonesOf`); запасной вариант — начало названия чата до « - » (`clientFromTitle`): название чата
открытой линии — это «Имя - WAZZUP - линия», и оно же — название сделки. Список чатов, шапка чата и
«Требуют внимания» показывают имя клиента (в чатах — до 15 символов, `clipName`).

## Активность сотрудников (`activity.service.ts`, `activity.ts`)
Сотрудники — участники групп (`WorkGroupMember`: сотрудники и отделы → `user.get`). Смена —
история учёта времени `timeman.record.list` (REST 3.0, `client.callV3`; по одному сотруднику за
запрос; фильтр `['startTime','between',[from,to]]`, даты — `YYYY-MM-DDTHH:mm:ss+00:00` без
миллисекунд, иначе ошибка проверки; `state.status` = `opened` — день не закрыт). Смена дня — записи,
начатые в этот день **и до недели раньше**, если не закончились до его начала: незакрытый рабочий день
тянется «до сейчас» (на экране — «смена с 18.10 18:10–сейчас»). Записи сотрудника — по отдельности (между
ними он не на смене), на экране — от первого начала до последнего конца. REST 3.0 недоступен — запасной
`timeman.status` (только последний день) и заметка на экране.
События дня: звонки телефонии VOXIMPLANT_CALL без фильтраCOMPLETED (реальные завершённые входящие
также имеют COMPLETED=N), длительность по START/END как на дашборде. Фактический сотрудник —
PORTAL_USER_ID из статистики только уже видимых CRM-дел, запасной источник RESPONSIBLE_ID.
Сетка0–24 включает ночные действия. Новые сделки — CREATED_BY_ID, брони — createdByUserId,
журнал действий — без входов/ошибок в рабочей активности. Сообщения до500на каждый из150последних
чатов: страницы50 сLAST_ID, только выбранный период; при ограничениях — заметка.

- сотрудник Битрикс24 — его сообщение;
- коннектор Wazzup с меткой `=== Исходящее сообщение, автор: … ===` — ответ с телефона: тому, чья
  смена покрывает время (`shiftOwner`); смены **нескольких** сотрудников открыты одновременно (оба не
  выключили рабочий день) — приписать одному нельзя: строка «Совместное использование» (`userId: 0`,
  `sharedBy` — чьи смены совпали; решение владельца 2026-10-23); никого — «без смены»;
- `=== SYSTEM WZ`, боты, системные (author 0) — не считаются;
- автосообщения приложения (ссылка на оплату, подтверждение — часто от имени сотрудника) пишутся
  в `SystemMessage` (`PaymentFlow.markSystem`) и тоже не считаются.
Минуты в чатах — оценка: сообщения с перерывом до 10 минут — одна сессия, не меньше 2 минут.

**Шапка чата** (решение владельца 2026-10-23): имя клиента — один раз (ссылка на контакт); под ним
каналы клиента — до двух кнопками, больше — кружок со стопкой иконок и окно «Чаты клиента»
(`ChannelSwitch`); теги: сделки (успешные), средний чек, брони (по клику — список), ближайшая бронь;
зелёный «+» — новая бронь с шага выбора сделки. На шаге сделки — по 2 в строке, 4 и «Показать ещё 4»;
сделка с текущей или будущей бронью (`ClientBookingsDto.openDeals[].booking`) — красная.

## Дашборд руководителя (`head-dashboard.service.ts`, `GET /api/head-dashboard?from&to`)
Решение владельца 2026-10-23. Руководители — ⚙ → «Приложение» → «Руководители» (`AppHead`: сотрудники и
отделы с вложенными; входят в приложение всегда); администраторы приложения видят дашборд тоже, но
открывается он первым только назначенным (`SessionInfo.headAssigned`). По дням периода и итого:
новые сделки (воронки **всех** групп, `DashboardService.newDeals`), сделки с бронью и брони по ним
(журнал, в т.ч. снятые), повторные клиенты (`happened`); звонки — все, пропущенные входящие, упущенные
клиенты (`callClients(...).lost` и нет подтверждённого ответа сотрудника после пропущенного в
чате клиента — по контакту или номеру; история проверяется токеном текущего пользователя). Период — сверху: дата,
«Сегодня» (по умолчанию), «Вчера», «Период…» (окно с началом и концом); показатели и графики — за
выбранный период, «Активность сотрудников» — на первый день периода. **Сравнение** (решение владельца
2026-10-23): `previous` — итоги предыдущего периода той же длины (`previousPeriod`: сегодня — вчера, 31 день —
31 день перед ним); на плитках ±% (конверсия в бронь — ± п.п.) и рамка: лучше — зелёная, хуже — красная;
у пропущенных и упущенных лучше — меньше. Сегодняшний неполный день сравнивается с полным вчерашним.
Аватарки сотрудников — в шапке и в «Активности сотрудников» (`user.get` → `PERSONAL_PHOTO`). «Активность сотрудников» (`GET /api/dashboard/activity`) перенесена сюда:
руководителям и администраторам, с дашборда менеджера убрана. Данные CRM — правами руководителя.

### История клиента в карточке звонка (2026-10-24)
`CallCardService` ищет чаты непосредственно по контакту (номер необязателен); если контакт ещё не
определён — по телефону. `ClientTimelineService` объединяет сообщения, звонки и дела CRM,
создание/завершение сделок, создание/отмену броней, счета и их оплату. Все REST-чтения —
`user.client`; журнал БД — только по `portalId` и ID сделок, прочитанных сотрудником в CRM.
Сбой отдельного источника не скрывает остальные: ограничения перечислены в `timeline.notes`.
Последние 200 событий (200 сделок/счетов, до 100 дел контакта + 100 дел сделок, последние сообщения
пяти доступных чатов), порядок по убыванию времени — свежие сверху (UTC), дедупликация по ID.
Интерфейс показывает последние 25 в этом порядке; «Показать ещё» добавляет более старые снизу. Оплата смарт-счёта — момент `movedTime`
стадии `:P`; дата начала брони не используется как дата её создания в журнале.
Во встройке: ФИО, телефон, число прошлых броней, средний чек, контакт, список броней, создание брони;
ниже вертикальная лента. Счётчик и кнопка открывают модальный список с доступной историей броней
(`ClientBookingsService.forContact(..., includeHistory=true)`), а не только пять последних.

Звонки, привязанные в CRM к заказу (OWNER_TYPE_ID=14), дополняются из `TelephonyCall` по
телефонам контакта, прочитанным его токеном. Фильтр БД включает портал и эти номера;
`crmActivityId` дополнительно проверяется `crm.activity.list` правами сотрудника. Без ID дела
показывается только его собственный звонок. События CRM и телефонии дедуплицируются по ID дела.
После создания брони карточка перечитывается.

### Компактная лента и высота CALL_CARD (2026-10-24)
Событие — одна строка (иконка, краткое название, дата/время, стрелка), native details раскрывает
подробности. Группы дат: Сегодня / Вчера по поясу портала, остальные — число, месяц и год.
DTO включает actorId/actorName и messageId. Автор берётся из CREATED_BY_ID сделки, AUTHOR_ID
дела CRM, createdBy/movedBy счёта, журнала брони или автора сообщения; имена сотрудников —
user.get правами пользователя. Если источник не сообщает автора — «Автор не указан».
Предпросмотр сообщения — ≤100 Unicode-символов вместе с многоточием; переход содержит
IM_DIALOG и IM_MESSAGE (обычный openMessenger не передаёт ID сообщения).
CALL_CARD вызывает fitFrame при старте и через ResizeObserver при загрузке/раскрытии содержимого;
раньше вызов был только в CalendarPage, который эта встройка не монтирует. Актуальные данные
звонка дополнительно читаются BX24.placement.call('getStatus') с таймаутом и запасными options.

### Контроль сделок и статусы (2026-10-24)
- `GET /api/dashboard/needs-close?scope=mine|all`: mine по умолчанию. Текущая очередь за всё
  доступное время, независимо от from/to дашборда. `endedForClosing` читает завершённые активные
  записи журнала постранично, с фильтрами портала и ресурсов, без прежних 60 дней / PERIOD_LIMIT.
  CRM загружается токеном сотрудника; `counts: {mine, all}` считаются из одной доступной выборки
  после проверки needsClose. mine — ASSIGNED_BY_ID текущего userId, all — все видимые сделки.
  Переключатели показывают оба числа, смена периода не перезагружает этот блок.
- `GET /api/dashboard/deal-gaps?kind=contact|chat` (`DashboardGapsService`): последние 200
  открытых сделок доступных воронок правами сотрудника (администратор приложения — все
  доступные ему в CRM). kind=contact — нет CONTACT_ID; kind=chat — нет чата ни у сделки, ни
  у контакта. Для chat требуется openlines.read; недоступный/ошибочный ответ не считается
  отсутствием чата, число непроверенных и ограничение выборки явно указаны в notes.
- Каталог содержит два независимых блока noOpenline/noContact; существующая личная раскладка
  не изменяется. У «Сделок к закрытию» собственный переключатель Мои/Все, начальное Мои.
- Иконки DashBadge слева; источники новых сделок дополнены кольцевой диаграммой.
- Плашки статусов имеют отдельные семантические токены для обеих тем; Провалена — красная,
  Ожидание клиента — оранжевая. Проверяются контраст текста ≥4,5 и более тёмный фон плашки
  относительно близкого по цвету фона строки в обеих темах.

### Прокрутка и переход к сообщению в звонке (2026-10-24)
CALL_CARD ограничен видимой высотой iframe, секция событий прокручивается самостоятельно;
всплывающая карточка сайта также имеет ограничение высоты и внутреннюю прокрутку.
Ссылка сообщения открывает полную страницу портала /online/ в новой вкладке (IM_DIALOG +
IM_MESSAGE), а не BX24.openPath: в слайдере звонка /online/ оставалась экраном «Откройте чат»
позади карточки. Домен берётся из проверенной сессии/SDK, открытие синхронно по клику.
Сделки по-прежнему открываются штатным слайдером CRM.

## Период, вкладки чатов и карточка звонка (2026-10-24)
- Вкладки UI: Все / Ждут ответа / Мои (ответственный = userId); старые Отвечены и Отдел убраны.
  Параметр status включает серверную фильтрацию **до** пагинации по 50. Ответ содержит counts
  (all/waiting/mine) по всей доступной выборке и userId для поиска по телефону.
- population в ChatsService общая для list и attention: только portalId + проверенный доступ
  сотрудника; обычные папки включены. ignoreAttention исключается из общего ожидания, но явно
  открытую папку можно просматривать. Скрытие строки на дашборде не уменьшает общий счётчик.
- GET dashboard/chat-attention (openlines.read) обновляет счётчик/строки каждые 15 секунд без
  30-секундного кэша остальных частей дашборда. Переход в чаты открывает Все без периода (последнее уточнение владельца).
- from/to — включительные локальные даты, common/period.ts переводит их в [start,end) UTC,
  не более 92 дней. Чаты — последнее сообщение в периоде и состояние ответа сейчас;
  сделки без контакта/линии — созданы в периоде и открыты сейчас; к закрытию — завершение
  брони в периоде. Это фильтрация текущих данных, не исторический снимок статусов.
- Брони «сегодня/завтра»: весь выбранный период / следующий день после to; подписи показывают
  фактические даты. Звонки, активность, журнал и остальные блоки передают тот же период.
- Журнал действий убран из SettingsPanel, добавляется блоком actionLog (только canManageApp,
  как прежде). Сохраняются фильтры автора/объекта/текста и раскрытие подробностей.
- Личные непрочитанные im.recent.list читаются с OFFSET по 200, UNREAD_ONLY=Y,
  SKIP_OPENLINES=N. В UI числовые плашки на аватарках/папках; ноль нейтральный.
- CALL_CARD: сверху ClientSituation — текущие/будущие брони по end>now, затем оставшиеся
  открытые сделки; ниже История общения, новые события сверху. Звонок — отдельная метка
  направления; сообщение — пузырь с автором и предпросмотром ≤100 символов. Входящие красные
  со стрелкой вниз, исходящие зелёные со стрелкой вверх. История прокручивается независимо.

## Два источника вложений (2026-10-24)
- AttachmentButtons используется StepsEditor (личные/общие/системные payment/auto шаблоны и
  чат) и редактором подтверждений. Две явные кнопки: Из устройства / Из Битрикса. До 10 файлов

- Без связей с бизнес-процессами Битрикс24: по уточнению владельца речь о системных алгоритмах
  приложения. Старый импорт БП не менялся функционально; новые редакторы работают сами.

## Типографика и списки дашборда (2026-10-24)
Дизайн проанализирован отдельным агентом по просьбе владельца. В пределах dash-cell-body
основной/второстепенный текст, суммы, время и статусы — 13px; заголовки14px, числовые KPI28px.
Общий каркас dash-record: объект + показатель, детали, приглушённые метаданные. В звонках —
клиент/время, направление/результат/длительность, телефон/сотрудник, сделка/статус. В сделках —
название/сумма, контакт/статус, ресурс/интервал, создание/источник; для оплат главный показатель
— поступившая сумма, общая сумма сделки ниже. В бронях — ресурс/интервал, клиент/статус,
сделка/сумма. Container queries сохраняют размер шрифта при узких блоках, перенося показатель.

Проверка на живом портале выявила 8446 доступных техническому пользователю хранилищ.
Поэтому не используем listAll с лимитом5000: первое окно читает только одну страницу,
Показать ещё передаёт nextOffset, поиск выполняется на портале с задержкой ввода250мс.

## Однострочные звонки и единое правило упущенного (2026-10-24)

### Компактные звонки и карточки броней (2026-10-24)
RecentCalls: клиент → иконка/длительность → менеджер → Сделка/Чаты → время звонка. Телефоны и
аватары в этом блоке скрыты. Общий журнал звонков сохраняет прежние данные и расположение.
`call-client-links.ts` дополняет только доступные дела CRM: контакт из communications, владельца
contact, доступной сделки или поиска по телефону. Последняя сделка — первая по DATE_CREATE DESC,
ID DESC (`crm.deal.list`), включая закрытые; без фильтра по дате звонка. Чаты ищутся по контакту
и владельцу дела CRM (`ACTIVE_ONLY=N`), затем summariesByChat проверяет права и возвращает
последние сообщения; выбирается максимум даты активности. Чатовые запросы выполняются только
при openlines.read или праве администратора приложения. Любая недоступная/отсутствующая связь
скрывает соответствующую кнопку. Недоступность дополнительных связей не убирает сам звонок.
Повторы контактов объединяются в пакетах, REST — исключительно user.client.
Брони: карточка с ресурсом/статусом, временем, клиентом, ссылкой на сделку и суммой. Container
query от560px переключает список в два столбца; узкий блок — один. Шрифт13px, прежние цвета
времени и контрастные статусы сохранены. Период броней по-прежнему берётся из дашборда.

### Время звонка как в блоке сообщений (2026-10-24)

## Журнал моих действий (2026-10-24)
`GET /api/dashboard/my-activity?from&to`: любой сотрудник приложения, userId/portalId/scope из
query не принимаются. ActivityService.mine жёстко фиксирует текущий user.userId; администратор
тоже получает только себя. Даты включительно в зоне портала, до92дней. DTO MyActivityDto:
userId/from/to/events/notes. События новые сверху, источник — доступные user.client звонки,
сделки, сообщения и ActionLog/BookingRecord только текущего портала/автора. Боты/SystemMessage
исключены; сообщение с общего телефона без доказанного автора себе не приписывается.
Внешняя переписка читается только при openlines.read или администратору приложения.
Дубли создания брони и отправки сообщения (ActionLog+native) исключены; RequestLogInterceptor
теперь сохраняет только messageIds результата отправки, без текста. Частичный error в HTTP200
логируется как ошибка. Для старых send-записей безID — сопоставление по тому же чату/времени.
Каталог myActivity доступен не администраторам, UI5+5 и refresh30сек, групповка по датам,
раскрытие как CALL_CARD, переходы в чат внутри приложения. Период влияет на этот блок.
Проверка живых данных до исправления:8последних звонков имели COMPLETED=N; user242 имел29
событий,0видимыхячеек и0звонков из-за9–22+фильтраCOMPLETED. После исправления проверить read-only.

### Счётчик в блоке сообщений дашборда (2026-10-24)
`AttentionChatDto.unread` — большее из личного счётчика `unreadByChat(user)` (тот же, что в
ChatSummary) и `OpenlineChat.clientStreak` — сообщений клиента подряд после последнего ответа
сотрудника (`lastMeaningful().streak`, пишут worker и живые сводки вместе с `lastAuthor`). Личный
счётчик есть только у участника чата, поэтому без `clientStreak` число в «Сообщениях без ответа»
почти всегда было 0. Не меняет waiting и скрытие чатов. В UI — маленький счётчик у угла аватарки и
стопка максимум4; подробности в docs/features/dashboard-sync.md.

Каналы клиента: query channel группирует собственный/провайдерский транспорт (shared messageChannel),
фильтр до counts/offset; доступные channels из всей разрешённой популяции. В телефонном поиске
применяется тот же фильтр. ChannelSwitch показывает только summariesByChat с положительными правами;
sibling chats собственного коннектора также определяются по MessengerMessage remote/deal context.
