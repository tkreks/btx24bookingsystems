# audit

**Назначение:** журнал действий (решение владельца 2026-10-22) — добавляемый блок «Журнал действий» дашборда: кто, что, когда
и откуда. Таблица `ActionLog` — только добавление (триггеры БД запрещают UPDATE/DELETE).

| Маршрут (`B24AuthGuard`) | Право | Что |
|---|---|---|
| `POST /api/activity/enter` `{placement, dealId}` | любой сотрудник (и без доступа — «попытка входа») | вход в приложение: откуда (сделка, меню) |
| `GET /api/admin/action-log?from&to&userId&actorKind&entityType&entityId&q&category&severity&before&limit` | админ приложения | записи, новые сверху; `limit`1–100 (без него100), в блоке5; `before` — курсор |

**Что пишется**
- `RequestLogInterceptor` (глобальный, api): **каждый** изменяющий запрос сотрудника (POST/PUT/PATCH/DELETE),
  удачный и с ошибкой; подпись — `LABELS` (новые маршруты — «метод путь», пока не добавлены). Тело — без
  паролей/кодов/токенов, тексты сообщений — только длиной (`sanitize`). Маршруты из `SKIP` пишутся подробно сами.
- Брони: `BookingJournalService.history` дублирует каждую запись истории брони (`booking.created`,
  `booking.cancelled` — сотрудником, **системой по неоплате**, удалена в Битрикс24; `imported`, `changed_in_bitrix`, оплата).
- Сделка: `deal.edit_open` (карточка брони → «Редактировать», `GET /api/deal-form?purpose=edit`) со значениями;
  `deal.update` — «было → стало» (`changes: [{field, label, before, after}]`) из карточки, при создании брони
  и автозаполнение типа брони системой.
- Группы и настройки приложения — `diffFields` «было → стало» по разделам.
- Оплаты (worker, `PaymentFlow`): ссылка отправлена / не отправлена, оплата получена, счёт «не оплачен», срок вышел.

**Инварианты:** сбой записи журнала не ломает действие (предупреждение в лог). Портал — из контекста;
выборка только своего портала. `X-Btx24-Placement` (заголовок интерфейса) — поле «откуда».

## Страницы блока журнала (2026-10-24)
ActionLogPanel передаёт limit=5 на первом запросе и Показать ещё. API читает limit+1,
возвращает limit записей и nextCursor при наличии следующей страницы. Все последующие
страницы сохраняют from/to и фильтры; границы дат UTC берутся из часового пояса портала.
Смена периода/фильтров начинает список с5записей, поздняя страница прежнего запроса отбрасывается.
Тесты:5→5→1, курсор без дублей, portal p1/p2 и UTCграницы, неправильные лимиты; прежний
APIвызов безlimitпо-прежнему100. Браузер5→10→11 и смена периода во время загрузки.

## Категории и критичность (2026-10-24, ADR0010)
Единый classifyActionLog из shared применяется ко всем новым/историческим записям. DTO содержит
category/severity; 10 категорий и4уровня, фильтры API валидируются. При фильтрации сервер
сканирует страницы по200 в пределах исходного tenant/period/query, пока не получит limit+1
совпадений; курсор — последняя показанная запись. Без этих фильтров прежний запросlimit+1.
Нет миграции/backfill: ActionLog неизменяем. Полные правила и инвентаризация всех14источников —
[docs/features/action-log-classification.md](../../../../../docs/features/action-log-classification.md).
Ошибки запросов, подробно логирующих успех самостоятельно, теперь сохраняются общим
перехватчиком; их HTTP статус входит в details. Предпросмотры не логируются. Убраны дубли
activity/error и groups-order. Неудавшаяся компенсация брони — критическое событие.

Личная лента берёт только userId аутентифицированного сотрудника через ActivityService, без
права просмотра чужого ActionLog. Результат send (HTTP200 с частичной ошибкой) теперь сохраняет
messageIds и ошибку, чтобы не выдавать сбой за успех и не дублировать сообщение в активности.
Ни текст результата, ни содержимое файлов в новые поля журнала не попадают.
