# bookings

**Назначение:** журнал броней (ADR 0006), сверка с Битрикс24 и уведомления (ADR 0007).

Право — в любой группе или администратор приложения.

**Сервисы**
- `BookingJournalService` — записи и история: `recordCreated` (приложение), `recordImported`
  (найдена в Битрикс24), `recordChanged`, `recordCancelled`, `note`. Исполнитель — `BookingActor`:
  сотрудник, система (`SYSTEM.paymentTimeout` = «Система: автоматизация — удаление брони при
  неоплате», `SYSTEM.reconcile`) или Битрикс24 (`SYSTEM.bitrix`). В истории — «было/стало».
- `BookingSyncService` — сверка (worker `BookingSyncJob`, раз в 10 минут, токеном приложения).
- `BookingAlertsService` — уведомления: создание по отпечатку, доставка в чат, статусы, решения.
- `bitrix-bookings.ts` — чтение модуля бронирования (общее с календарём).

**Инварианты**
- Истина о слотах — Битрикс24 (ADR 0003): по журналу пересечения не проверяются.
- История — только добавление: UPDATE/DELETE `BookingHistory` запрещены триггерами БД.
- Бронь приложения (`source = app`), которая не совпала с Битрикс24, **не меняется** сверкой —
  только уведомление; меняет её решение сотрудника. Бронь из Битрикс24 (`source = bitrix`)
  следует за Битрикс24 с записью в истории.
- **Удалённая в Битрикс24 бронь по сделке ждёт решения** — и из приложения, и созданная в самом
  Битрикс24 (решение владельца 2026-10-23): уведомление «пропала», запись остаётся активной, календарь
  показывает её отдельно с кнопками «Оставить бронь» (создать заново) / «Удалить из приложения».
  Служебная бронь из Битрикс24 без сделки при удалении сразу уходит в историю (`removed_in_bitrix`).
- Первая сверка принимает существующие брони без уведомлений (`bookingSyncBaselineAt`).
- Одно и то же расхождение (вид + фактическое состояние) — одно уведомление.
- Сообщения в чат уведомлений пишет приложение (системное действие, токен приложения);
  удаление брони при решении — токеном сотрудника (его права, режим «только чтение», песочница).
- Клиентская бронь приложения — со сделкой; бронь приложения — с автором (CHECK в миграции).

**Создание брони** (сага, токен сотрудника): новая сделка в воронке группы (если нужна) → бронь
(`booking.add`; `1018` → 409) → связь со сделкой и клиентом → системные поля сделки по
`PortalSettings.dealFieldMap` (ID брони, даты брони и визита, гости, тип брони по товарам,
комментарий) → товары (если переданы; полная замена строк) → журнал броней (`paymentMode`). Сбой
после брони — бронь удаляется; созданная сделка остаётся (в ошибке операции). Повтор с тем же
`idempotencyKey` — прежний результат. Запись в Битрикс24 подчиняется режиму «только чтение» и
песочнице (сделка 678, даты 2020).

**Брони клиента** — `booking.v1.booking.list` по контакту + сделки контакта (поля «ID брони» и
даты брони): видны и брони без клиента в Битрикс24, и удалённые (по датам из сделки).

**Сообщения клиенту** — настройки группы (`options.bookingTypes`, `options.payments.clientMessage`,
`failMessage`), правила и подстановка — `@btx24/shared` (`client-messages.ts`: `detectBookingType`,
`renderTemplate`, `clientResourceName`). Тексты по умолчанию — там же (сервер и интерфейс видят одни).

**Пока нет:** подписки на события `onBooking*` (только сверка по расписанию), создания брони
(сага) и контроля оплаты; кнопки «Изменить/Отменить» в чате открывают приложение — передача
`?alert=` во фрейм не проверена вживую.

**Тип брони** (решение владельца 2026-10-22): менеджер выбирает тип в форме брони
(`CreateBookingDto.bookingTypeId`); не выбрал — по товарам сделки (`crm.deal.productrows.get`), как
БП 270. Группа «Тип брони обязателен» (`options.bookingTypeRequired`, включено у «Бань»): тип не
выбран и не определился — 400 до любых записей в Битрикс24. `BookingTypeFillService` (worker, раз в
2 минуты) заполняет пустое поле «Тип бронирования» у изменённых сделок в работе из воронок групп с
типами брони — заполненное менеджером не трогает. Значения поля-списка пишутся **номером варианта**:
БП хранит внутренний код (XML_ID «3af19224…»), `DealFieldMapService.enumId` переводит код/название в
номер (`crm.deal.userfield.list`); не нашли — поле не пишется.

**Поля сделки группы** (`options.dealFields`, флаги С/П/О; `deal-form.ts`, `DealFormService`): форма
брони показывает поля «С» (у существующей сделки — с её значениями) и шлёт их в
`CreateBookingDto.dealFields`; карточка брони — «Редактировать» → поля «С»/«П». Сервер принимает
только поля группы, которые можно менять: не множественные, не только для чтения в CRM и не
заполняемые приложением (`APP_FILLED_ROLES`: ID и даты брони, тип, счета, ссылки). Обязательные
(«required») проверяются до записей в Битрикс24. Деньги пишутся «сумма|валюта сделки» (при
создании — RUB), да/нет — 1/0, дата и время — из пояса портала в UTC. При создании системные поля
важнее полей формы. `defaultValue` и `formula` из настроек передаются в `DealFormField` (формула —
только для чисел и сумм); применяет их форма, сервер пишет присланные значения.

**Снятие брони** (`BookingCancelService`, кнопка «Снять бронь» в карточке): бронь должна быть на
ресурсе группы; нет в журнале — сначала `recordImported`, затем `booking.delete` (токен сотрудника:
режим «только чтение» пускает только брони приложения → 403 `BOOKING_READ_ONLY`) и
`recordCancelled('manual', comment)`. Активные `PaymentRequest` брони → `cancelled` (иначе по сроку
клиенту уйдёт «не оплачено»); счёт остаётся — предупреждение. Повтор: бронь уже удалена — отмена у
нас без ошибки.

**Мастер брони (решение владельца 2026-10-23).** Новая сделка — без ввода названия: «Имя клиента 25.10.2026
Баня 1» (клиент, дата брони, ресурс). У группы с `options.dealKinds` (бани) после группы — шаг «Тип сделки»:
«Покупка сертификата» — без брони: `POST /api/certificates/sale` (сделка с типом «Покупка сертификата» и
суммой = номиналу, сертификат в модуле `certificates`), затем окно оплаты всей суммы (`preview` отдаёт
`source: certificate`, бронь не требует); «Бронирование посещения» — оплата `prepayment` (ссылка с таймером),
тип бронирования обязателен; «Бронирование сертификатом» — `certificate`, а со ссылкой — `prepayment` и
`prepaymentAmount` (пишется в «Сумму предоплаты», в окне оплаты подставляется); «Без оплаты» — `postpay`.
`dealKind` заполняет «Тип сделки» по началу названия варианта (`enumId(..., prefix)`); у «без оплаты» — свой
вариант «Бронирование без оплаты» (добавлен в поле портала 2026-10-26). Поле «Тип сделки» в форме брони — с
ролью `dealType` (и найденное по названию): мастер выбирает тип в разделе «Группа», в «Полях сделки» поля нет. Тип бронирования с `unavailable` (Теремок) не выбирается.
Порядок групп — `WorkGroup.sort` (⚙ → «Группы», стрелки, `PUT /api/admin/groups-order`); мастер его не
меняет. Товары: только ресурс брони, «Выбрать» (весь каталог), теги разделов (`options.productSectionsHidden`
— скрытые 👁) → окно раздела с вложенными.

**Стоп ресурса** (`resource-stops.service.ts`, `ResourceStop`): `POST /api/resource-stops/check` — брони
ресурса за дни периода в Битрикс24; `POST /api/resource-stops` — только если броней нет (иначе 409 со
списком), с причиной; `DELETE /api/resource-stops/:id` — снять. Право — `booking.edit` в группе ресурса.
Создание брони в стоп — 409 `RESOURCE_STOPPED`; календарь отдаёт `stops`, мастер не даёт выбрать ресурс.
В самом Битрикс24 стоп не виден (бронь там поставить можно) — это ограничение.

**Статус сделки** — `DealStatusService` (`deal-status.service.ts`, правило — `dealStatus` в shared): канбан +
брони журнала; см. openlines/MODULE.md.

**Сверка назад** (`SYNC_LOOKBACK_DAYS` = 31): список броней Битрикс24 берётся с запасом в прошлое.
Известная бронь, удалённая там, отмечается (`removed_in_bitrix` для служебных броней из Битрикс24 без
сделки; для броней по сделке и броней приложения — уведомление «пропала» и решение сотрудника). Прошедшая бронь, которой нет в журнале, записывается без
уведомления, «создание» — на дату начала брони (Битрикс24 не отдаёт дату создания).

**Гарантии создания брони (2026-10-22).** Заявка с ключом идемпотентности: готово — повтор вернёт тот
же результат; идёт — 409 (зависла дольше 2 минут — можно повторить); **сорвалась — повтор выполняется
заново**: новая сделка прошлой попытки используется снова (без второй сделки), бронь, которую не снял
откат, сначала снимается. Портал не ответил — 503 «Бронь не создана… повторите — ничего не задвоится».
Форма держит один ключ на открытие — повтор кнопкой безопасен.

**Бронь приложения, удалённая в Битрикс24** (решение владельца 2026-10-23). До решения сотрудника она
остаётся в календаре (слой «Удалена в Битрикс24 — нужно решение»), в «Бронях сегодня» дашборда и в
списках. «Создать заново» (`BookingRestoreService.recreate`): `booking.v1.booking.add` с ресурсами и
временем журнала, связь со сделкой (без неё — откат), клиент сделки, поле «ID бронирования» сделки;
у брони **новый ID** — он переписывается в запись журнала (история та же, `recreated_in_bitrix` с
прежним ID) и в счета приложения. Слот уже занят — 409 `BOOKING_OVERLAP`. «Удалить в приложении» —
отмена в журнале с причиной `removed_in_bitrix` от имени сотрудника. Обе — только если брони в
Битрикс24 правда нет (иначе 409 `BOOKING_EXISTS`). «Ждёт решения» на дашборде
(`BookingJournalService.pendingRemoval`) — активная запись + уведомление «брони нет» **в любом статусе**
(его могли отметить «Решено» вручную); такая бронь не входит в счётчики «Бронирований сегодня /
завтра» и не делает сделку «с бронью», в списках — с пометкой.

### Мастер во встройке звонка (2026-10-24)
«Бронирование посещения» выбрано по умолчанию и стоит первым, «Покупка сертификата» — вторым.
Быстрый переход к дате доступен и в узком окне. Во встройке CALL_CARD панель времени на шаге
«Дата и ресурс» заменена окном по нажатию на таймлайн: начало берётся из места клика, менеджер
задаёт начало и завершение, включая дату следующего дня. Отмена окна сохраняет прежний выбор.
Во встройке шкала показывает выбранные сутки; насечки и подписи снизу — каждые 4 часа
по часовому поясу портала. Вне встройки шкала «заезд/выезд» сохраняет отметки дат.

### Период блоков дашборда (2026-10-24)
- GET booking-alerts принимает from/to: уведомления по createdAt в локальном периоде,
  статусы и counts — текущие в этой выборке. Без дат прежний режим.
- GET resource-stops принимает from/to: пересечение со сроком действия стопа; исторический
  конец ограничен liftedAt, стоп, снятый до начала, не показывается. Права ресурсов сохранены.
- BookingJournal.endingBetween: завершения endsAt в [start,end), отдельно от пересечений
  activeListBetween; применяется к «Сделкам к закрытию» за выбранные даты.

**Редактор подтверждений (2026-10-24).** К каждому сообщению добавлены оба источника вложений:
Из устройства / Из Битрикса. Новые вложения — копии StoredFile, прежние DiskFileRef после
импорта остаются совместимы. Отправку обоих вариантов выполняет PaymentFlow.sendChain;
имена при старом импорте БП разрешаются только для DiskFileRef.

### Мастер в CALL_CARD (2026-10-24)
BookingForm при callPlacement=true получает отдельный call-booking-backdrop: верх фрейма,
полная высота100dvh, без мобильного выравнивания к низу. Форма flex, шапка/шаги/подвал не
сжимаются, bk-body прокручивается внутри доступной высоты. Для обычного мастера класс не

### Панель переходов CALL_CARD не зависит от низа iframe (2026-10-24)
После сообщения владельца о недоступной кнопке нижняя панель перенесена визуально под
заголовок, перед шагами и содержимым (только callPlacement). Сводка в панели скрыта: она
уже есть в заголовке. Поле шага прокручивается отдельно, scrollbar видим и доступен фокус
клавиатуры. На slot «Далее» видно всегда; без выбранного ресурса кнопка отключена с подсказкой.
Свёрнутый мастер CALL_CARD восстанавливается кнопкой сверху, поскольку нижний dock тоже может
быть обрезан порталом. Проверка: iframe1200px в контейнере320px с overflow:hidden, реальные
клики Далее/Назад и колесо, minimise/restore, обе темы, узкий/короткий/широкий экран.

### Создание из звонка: видимая обратная связь и товары (2026-10-24)
В CALL_CARD причины отказа в создании (включая локальные проверки, обязательные поля и ошибки
API) показываются непосредственно у верхней панели действий; во время запроса — явное
состояние отправки и отключённая кнопка. onInvalidCapture показывает первую нативную ошибку
поля, переводит фокус и прокручивает содержимое к нему: браузер при такой ошибке не вызывает
onSubmit. Ограничения времени, прав и обязательных полей сохраняются. Повтор отправки использует
прежний idempotencyKey. Окна заполненных полей и каталога прикреплены к верху CALL_CARD,
их кнопки подтверждения расположены сразу после заголовка. PaymentDialog получает callPlacement
из CallLayer и также открывается сверху, включая восстановление после сворачивания.
В каталоге невыбранный товар показывает «Добавить +», выбранный — «− количество +» с ручным
вводом. Ноль убирает товар. Изменение суммарного количества дублирующихся строк существующей
сделки сохраняет цены/скидки: рост первой строки, уменьшение с последних строк. Количество
единое для каталога, выбранных товаров, итогов и запроса создания.
Проверено браузером с подменёнными ответами API: обязательное поле, локальный отказ, конфликт409,
повтор, pending/disabled, успешная бронь и верх окна оплаты в iframe1200px, обрезанном до320px;
каталог Добавить/плюс/минус/ручной ввод/ноль и payload. Реальные брони для тестов не создавались.

**Очередь закрытия сделок (2026-10-24).** `BookingJournalService.endedForClosing(portalId, now,
resourceIds)` читает все активные записи с dealId и endsAt<=now, постранично по стабильному id.
На каждой странице фильтруется портал; результат ограничен ресурсами групп. Прежние 60 дней
и лимит выборки периода на текущую очередь не действуют. В CRM отдельно проверяются права,
статус сделки и отсутствие следующей активной брони. Другие периодические выборки не менялись.

### Шаг отправки предоплаты в CALL_CARD (2026-10-24)
После «Товары и поля» кнопка «Далее: предоплата» создаёт бронь и открывает PaymentDialog для
этой сделки/брони. В CALL_CARD сумма и «Отправить ссылку на предоплату» стоят сразу после
заголовка, до истории счетов и параметров. Кнопка доступна в iframe1200px, обрезанном до320px.
Сумма предварительно рассчитывается сервером, допускает изменение; связь с созданной бронью
сохраняется. API/финансовые правила/шаблоны и идемпотентность не менялись. При ошибке отправки
повтор использует тот же ключ; повторно бронь не создаётся. Ошибки, busy и результат рядом
с кнопкой. Успех доставки показывается только при messageSent=true; sent без доставки явно
сообщает, что ссылка не отправлена, даёт предупреждение и возможность скопировать ссылку.
Пока ссылка формируется, нет ложного сообщения о доставке; polling истории обновляет результат.
Обычное окно счетов вне CALL_CARD сохраняет прежнюю компоновку.

**Критический аудит компенсации (2026-10-24).** Если после ошибки создания не удалось удалить
уже созданную бронь (leftBooking), BookingCreateService пишет booking.compensation_failed
с bookingId/dealId/operationId. Классификация — Ошибки/Критическая. Исходная ошибка и состояние
BookingOperation сохраняются, политика компенсации и идемпотентность не меняются.

Занятость в BookingForm и список ClientBookings обновляются прямыми запросами каждые
15 секунд, при фокусе/восстановлении сети/мутациях. Снимки дашборда на эти запросы не
распространяются; введённые поля не сбрасываются. См. `docs/features/dashboard-sync.md`.

### Шапка чата и снятые брони (2026-10-26)
Снятие брони через приложение не очищает поля сделки «ID бронирования» / даты. `ClientBookingsService`
не показывает бронь из полей сделки, если в модуле её нет, а в журнале она `cancelled`.

### Клиент брони обязателен (2026-10-26)
`BookingCreateService.requireClient`: клиентская бронь — только с контактом (заявка `contactId` /
`newDeal.contactId` или `CONTACT_ID` выбранной сделки), иначе 400 `CLIENT_REQUIRED` до записей.
У выбранной сделки нет контакта, а в заявке он есть — после создания сделки/брони
`crm.deal.contact.add` (`IS_PRIMARY=Y`); сбой — предупреждение, бронь остаётся. Проверка — после
повтора готовой заявки (повтор по ключу не требует клиента заново). Новый клиент из мастера —
`POST /api/crm/contacts` (`BookingDirectoryService.createContact`, право `booking.create`, сначала
поиск по телефону). Подробности — `docs/features/booking-constructor.md`.
