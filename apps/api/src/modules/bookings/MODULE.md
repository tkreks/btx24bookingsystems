# bookings

**Назначение:** журнал броней (ADR 0006), сверка с Битрикс24 и уведомления (ADR 0007).

| Маршрут (`B24AuthGuard`) | Право | Что |
|---|---|---|
| `GET /api/booking-alerts?status=` | `booking.details` | уведомления, счётчики по статусам, названия ресурсов |
| `PUT /api/booking-alerts/:id` `{status}` | `booking.edit` | статус: `new`/`viewed`/`resolved`/`ignored` (+ кто и когда; сообщение в чате обновляется) |
| `POST /api/booking-alerts/:id/resolve` `{resolution}` | `booking.edit` / `booking.cancel` | `accept_bitrix` — принять как в Битрикс24; `cancel_booking` — удалить в Битрикс24 и отменить |
| `GET /api/bookings/:bookingId/history` | `booking.details` | история брони (аудит) |
| `POST /api/bookings` | `booking.create` в группе | создать бронь — сага `booking-create.service.ts` (журнал `BookingOperation`, ключ идемпотентности, компенсация) |
| `POST /api/bookings/:bookingId/cancel` `{groupId, comment?}` | `booking.cancel` в группе | снять бронь: удалить в Битрикс24 и отменить в журнале (`manual` + причина); ожидание оплаты по брони закрывается |
| `GET /api/deal-form?groupId=&dealId=` | `booking.create` или `booking.edit` в группе (+ `booking.details` со сделкой) | поля сделки группы для формы брони и карточки: тип, варианты, «два в строку», значения сделки |
| `PUT /api/deals/:dealId/fields` `{groupId, values}` | `booking.edit` + `booking.details` в группе | правка полей сделки из карточки брони (только изменённые; режим «только чтение» → 403 `DEAL_READ_ONLY`) |
| `GET /api/deals/:dealId/bookings` | `calendar.view` | брони сделки и её клиента (встройка открывается на дате брони) |
| `GET /api/openlines/chats/:chatId/bookings` | `openlines.read` | брони клиента чата: было / сейчас / будет, открытые сделки |
| `GET/PUT /api/admin/booking-sync/deal-fields`, `…/detect` | админ приложения | системные поля сделки портала (роль → код), автоопределение по названиям |
| `GET/PUT /api/admin/booking-sync` | админ приложения | горизонт сверки, время и ошибка последней сверки |
| `POST /api/admin/booking-sync/chat` | админ приложения | создать чат уведомлений (один раз) |
| `GET /api/admin/resources`, `PUT /api/admin/resources/:resourceId` `{clientName}` | админ приложения | имя ресурса для клиента (`{house}` в сообщениях) |
| `GET /api/admin/disk?storageId=&folderId=` | админ приложения | обзор Диска для вложений (токен администратора, нужно право `disk`) |
| `GET /api/admin/bizproc-import?templateId=` | админ приложения | типы брони и сообщения из БП (`bizproc-import.ts`) — в форму группы, без сохранения |

Право — в любой группе или администратор приложения.

**Сервисы**
- `BookingJournalService` — записи и история: `recordCreated` (приложение), `recordImported`
  (найдена в Битрикс24), `recordChanged`, `recordCancelled`, `note`. Исполнитель — `BookingActor`:
  сотрудник, система (`SYSTEM.paymentTimeout` = «Система: автоматизация — удаление брони при
  неоплате», `SYSTEM.reconcile`) или Битрикс24 (`SYSTEM.bitrix`). В истории — «было/стало».
- `BookingSyncService` — сверка (worker `BookingSyncJob`, раз в 10 минут, токеном приложения).
- `BookingAlertsService` — уведомления: создание по отпечатку, доставка в чат, статусы, решения.
- `bitrix-bookings.ts` — чтение модуля бронирования (общее с календарём).

**Инварианты**
- Истина о слотах — Битрикс24 (ADR 0003): по журналу пересечения не проверяются.
- История — только добавление: UPDATE/DELETE `BookingHistory` запрещены триггерами БД.
- Бронь приложения (`source = app`), которая не совпала с Битрикс24, **не меняется** сверкой —
  только уведомление; меняет её решение сотрудника. Бронь из Битрикс24 (`source = bitrix`)
  следует за Битрикс24 с записью в истории.
- Первая сверка принимает существующие брони без уведомлений (`bookingSyncBaselineAt`).
- Одно и то же расхождение (вид + фактическое состояние) — одно уведомление.
- Сообщения в чат уведомлений пишет приложение (системное действие, токен приложения);
  удаление брони при решении — токеном сотрудника (его права, режим «только чтение», песочница).
- Клиентская бронь приложения — со сделкой; бронь приложения — с автором (CHECK в миграции).

**Создание брони** (сага, токен сотрудника): новая сделка в воронке группы (если нужна) → бронь
(`booking.add`; `1018` → 409) → связь со сделкой и клиентом → системные поля сделки по
`PortalSettings.dealFieldMap` (ID брони, даты брони и визита, гости, тип брони по товарам,
комментарий) → товары (если переданы; полная замена строк) → журнал броней (`paymentMode`). Сбой
после брони — бронь удаляется; созданная сделка остаётся (в ошибке операции). Повтор с тем же
`idempotencyKey` — прежний результат. Запись в Битрикс24 подчиняется режиму «только чтение» и
песочнице (сделка 678, даты 2020).

**Брони клиента** — `booking.v1.booking.list` по контакту + сделки контакта (поля «ID брони» и
даты брони): видны и брони без клиента в Битрикс24, и удалённые (по датам из сделки).

**Сообщения клиенту** — настройки группы (`options.bookingTypes`, `options.payments.clientMessage`,
`failMessage`), правила и подстановка — `@btx24/shared` (`client-messages.ts`: `detectBookingType`,
`renderTemplate`, `clientResourceName`). Тексты по умолчанию — там же (сервер и интерфейс видят одни).

**Пока нет:** подписки на события `onBooking*` (только сверка по расписанию), создания брони
(сага) и контроля оплаты; кнопки «Изменить/Отменить» в чате открывают приложение — передача
`?alert=` во фрейм не проверена вживую.

**Тип брони** (решение владельца 2026-10-22): менеджер выбирает тип в форме брони
(`CreateBookingDto.bookingTypeId`); не выбрал — по товарам сделки (`crm.deal.productrows.get`), как
БП 270. Группа «Тип брони обязателен» (`options.bookingTypeRequired`, включено у «Бань»): тип не
выбран и не определился — 400 до любых записей в Битрикс24. `BookingTypeFillService` (worker, раз в
2 минуты) заполняет пустое поле «Тип бронирования» у изменённых сделок в работе из воронок групп с
типами брони — заполненное менеджером не трогает. Значения поля-списка пишутся **номером варианта**:
БП хранит внутренний код (XML_ID «3af19224…»), `DealFieldMapService.enumId` переводит код/название в
номер (`crm.deal.userfield.list`); не нашли — поле не пишется.

**Поля сделки группы** (`options.dealFields`, флаги С/П/О; `deal-form.ts`, `DealFormService`): форма
брони показывает поля «С» (у существующей сделки — с её значениями) и шлёт их в
`CreateBookingDto.dealFields`; карточка брони — «Редактировать» → поля «С»/«П». Сервер принимает
только поля группы, которые можно менять: не множественные, не только для чтения в CRM и не
заполняемые приложением (`APP_FILLED_ROLES`: ID и даты брони, тип, счета, ссылки). Обязательные
(«required») проверяются до записей в Битрикс24. Деньги пишутся «сумма|валюта сделки» (при
создании — RUB), да/нет — 1/0, дата и время — из пояса портала в UTC. При создании системные поля
важнее полей формы.

**Снятие брони** (`BookingCancelService`, кнопка «Снять бронь» в карточке): бронь должна быть на
ресурсе группы; нет в журнале — сначала `recordImported`, затем `booking.delete` (токен сотрудника:
режим «только чтение» пускает только брони приложения → 403 `BOOKING_READ_ONLY`) и
`recordCancelled('manual', comment)`. Активные `PaymentRequest` брони → `cancelled` (иначе по сроку
клиенту уйдёт «не оплачено»); счёт остаётся — предупреждение. Повтор: бронь уже удалена — отмена у
нас без ошибки.
