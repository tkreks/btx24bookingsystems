# messengers

**Назначение:** ⚙ → «Мессенджеры» (ADR 0014): номера компании в мессенджерах (WhatsApp и Telegram),
браузер на номер в сервисе `apps/messenger`, вход кодом по номеру или QR, экран по VNC.

| Маршрут (B24AuthGuard + PermanentAdminGuard) | Что |
|---|---|
| `GET /api/admin/messengers` | мессенджеры портала с живым состоянием (код входа, QR, аккаунт) |
| `POST /api/admin/messengers` `{kind, phone, auth?, title?}` | создать и запустить браузер |
| `POST /api/admin/messengers/:id/restart` `{auth?}` | перезапустить; `auth` — сменить способ входа |
| `POST /api/admin/messengers/:id/stop` | остановить браузер |
| `DELETE /api/admin/messengers/:id` | выйти из аккаунта и удалить |
| `POST /api/admin/messengers/:id/vnc-ticket` | одноразовый билет на экран (`wss://…/api/messengers/vnc?ticket=`) |
| `GET /api/admin/messengers/:id/screenshot` | снимок экрана (PNG) |
| `PUT /api/admin/messengers/:id/line` `{mode: own, name} \| {mode: null}` | создать свою линию и привязать / отвязать |
| `PUT /api/admin/messengers/:id/groups` `{groupIds}` | группы номера |
| `GET /api/admin/messengers/:id/chats`, `…/chats/:chatId/messages?before=` | переписка из базы |
| `POST /api/admin/messengers/:id/send {to, text}` | написать (номер или чат); привязан к линии — через линию (`queued`) |
| `POST …/messages/:messageId/edit {text}`, `DELETE …/messages/:messageId` | изменить / удалить у всех своё |
| `POST /api/admin/messengers/:id/import` | загрузить историю (в линию не передаётся) |
| `GET /api/messengers`, `…/:id/chats`, `…/messages`, `POST …/send`, `…/edit`, `DELETE …` (B24AuthGuard; группы номера, `openlines.read`/`send`) | номера групп сотрудника; своя линия — с положительной проверкой каждого диалога |
| `GET /api/messengers/status` (B24AuthGuard) | блок дашборда «Мессенджеры»: номера групп сотрудника (`openlines.read`), только `ready` и с ошибкой (`MESSENGER_ERROR_STATES`, с описанием); `canScreen` — право писать |
| `POST /api/messengers/:id/vnc-ticket`, `GET …/:id/screenshot` (B24AuthGuard; группа номера с `openlines.send` или администратор приложения) | экран номера из дашборда |
| `GET\|POST /api/messengers/:id/screen-files`, `DELETE …/:fileId`, `POST …/:fileId/attach`, `DELETE …/screen-files` (то же право) | файлы для отправки с экрана: хранятся в сервисе час; `attach` — подставить в следующее окно выбора файла (сотрудник жмёт 📎 на экране), `DELETE` без файла — отменить ожидание |
| `POST /api/messengers/hook` (без B24AuthGuard: только сеть стенда, nginx закрывает снаружи; `MESSENGER_TOKEN`) | события сервиса: сообщения, правки, удаления, статусы |

## Инварианты
- Подключение/экран/настройки — постоянные администраторы приложения; чужой портал — 404.
- Экран номера (VNC) и файлы для него — тому, кто может писать с номера (`forUser(…, send=true)`):
  администратор приложения или группа номера с `openlines.send`. Просмотр статуса — `openlines.read`.
- WebSocket VNC — только с билетом (`vnc-tickets.ts`: одноразовый, 1 минута, выдан после проверки
  портала); без билета сервис не вызывается.
- Сервис `messenger` — наш внутренний (не портал Битрикс24): ходим к нему `fetch` из
  `messenger-service.client.ts`, а не через модуль `bitrix24`.
- Истина о составе мессенджеров — таблица `Messenger`; реестр сервиса догоняет её в `list`.

- Переписка идемпотентна по `(messengerId, externalId)`; правка не затирает прежний текст
  (`edits`), удаление — `deletedAt`.
- Своя линия: всё к Битрикс24 — токеном приложения (методы коннектора работают только в контексте
  приложения); события `OnImConnector*` — `onBitrixEvent('ONIMCONNECTOR', …)` в `EventsService`.

- Своя линия: сообщения из приложения проходят через линию. Сотруднику нужны группы номера и
  read/send; каждый существующий чат положительно проверяется `imopenlines.dialog.get` его клиентом.
  Первое исходящее — явное действие сотрудника с send; без автоматического пробного сообщения.

## Подводные камни
- whatsapp-web.js зависит от разметки WhatsApp Web: после обновления WhatsApp вход может ломаться —
  обновлять библиотеку (`apps/messenger/package.json`).
- Неофициальный способ: номер могут ограничить за массовые/холодные рассылки.

## Медиа

- `GET /api/admin/messengers/:id/messages/:messageId/media` — файл после проверки портала/
  постоянного администратора. Пользовательский `GET /api/messengers/:id/messages/:messageId/media`
  проверяет группу номера/`openlines.read`; привязанный номер только через права ОЛ.
- `POST …/:id/send-file` (admin/user) — multipart `file`, `to`, `text` (необязательная подпись).
  До64МБ; пользовательскому пути нужно `openlines.send`. Для ОЛ — от имени сотрудника через
  firstContact; для номера без ОЛ — шлюз, с сохранением автора в переписке.
- `GET /api/messengers/files/:messengerId/:fileId?exp&sig` — публичный файл только по HMAC-ссылке
  сроком сутки для скачивания Битрикс24. Не заменяет авторизацию пользовательских маршрутов.
- `media-links.ts` подписывает идентификаторы/срок, `mediaColumns` сохраняет параметры вложения;
  бинарные данные лежат в томе messenger. История подгружается лениво. Удалённое — 404.
- Скачивание из событий оператора ограничено HTTPS-origin портала, каждый redirect проверяется,
  поток прерывается при >64МБ. Сбой не выдаётся за успешную отправку имени файла. Частичный повтор
  продолжает с уже сохранённого числа вложений b24MessageId.
- UI: изображения/видео/аудио по apiBlob, документы скачиваются, URL освобождаются. Подробнее ADR0014.

## Клиент, сделки и каналы (2026-10-24)
- `@btx24/shared/phones`: +7/7/8/10 цифр совпадают, включая городские; международные коды сохраняются.
- `MessengerCrmService.match`: duplicate PHONE → контакты/компании → сделки (входящие только P).
  В фоне app client; в HTTP только user.client. Пустого фильтра сделок нет, все страницы REST.
- 00900: MessengerChat хранит activeDealId/CRM ID cache 60сек; сообщения имеют неизменяемый снимок
  dealId/awaitingDeal/relayChatId. Смена сделки назначает только pending сообщения. Импорт прошлой
  истории не назначает ей текущую сделку. LID может наследовать выбор известного клиента по телефону.
- Одна активная сделка при новом входящем выбирается автоматически; несколько — выбор сотрудника.
  Pending видны в приложении; в уже существующую ОЛ попадают с отключённым CRM tracker. При ошибке CRM не считаем клиента новым.
  Выбранные сделки в собственной линии передаются с disable_crm=Y: новые сделки/контакты не создаём.
- Существующий диалог первой сделки переиспользуется. Следующая сделка использует virtual chat ID
  `<remote>::deal:<id>`; транспорт всегда получает исходный remote. Edit/delete используют relayChatId
  исходного сообщения. Повтор отправки файлов/эхо firstContact учитывают исходный remote.
- Контекст и выбор: GET `…/:id/chats/:chatId/context`, PUT `…/deal {dealId}` (admin/user).
  GET messages?dealId=ID/general фильтрует до пагинации; ID валидируется CRM правами сотрудника.
  Отправка несёт ожидаемый dealId, смена другим сотрудником →409; из архивной истории composer скрыт.
- GET `/messengers/openlines/:id/context`, PUT `…/deal`: тот же выбор в обычном ChatView собственного
  коннектора. Группа номера + положительная авторизация диалога. Чужих провайдеров не переназначаем.
- GET `/messengers/search?phone=`: только available numbers по группам/read. Проверка регистрации
  внутренним POST contact без отправки. found/not_found/unavailable различаются; canSend проверяет
  send и доступ к существующей ОЛ. Дополнительно возвращает доступные существующие CRM-диалоги:
  менеджер выбирает продолжение либо подключённый канал. Чужой провайдер не становится нашим.
- Поиск: письмо в RecentCalls без чата, кнопка CallCard без ОЛ; dialog top layer доступен во встройке.
  Канал в ChatsPage фильтрует до подсчёта/пагинации и в результатах поиска по телефону; в ChatView
  select переключает диалоги клиента. Список sibling dialogs положительно авторизован.

- Новый канал найденного клиента не создаёт ОЛ автоматически. Входящее остаётся в переписке
  мессенджера приложения до явного выбора сотрудника: выбрать/применить сделку, «Работать в этом
  канале» или написать. publishChosen передаёт ожидающие входящие в ОЛ страницами по100 (не клиенту),
  пропускает удалённые, редактирования/история сохраняются. Менеджер также может открыть существующий
  CRM-диалог другого провайдера из поиска. Уже существующие ОЛ продолжают принимать сообщения.

## Telegram
`kind: telegram` — вход только на экране (`auth` всегда `qr`, переключателя кода нет). ID чатов —
`<userId>@lid` (номер в `phone`, если Telegram его показывает), отправка по номеру — `<номер>@c.us`, как
у WhatsApp. Текст оператора из линии уходит без разметки (`bbToMessenger(text, 'telegram')`). Своё
сообщение можно изменить 48 часов. Устройство сервиса — `apps/messenger/MODULE.md`.
