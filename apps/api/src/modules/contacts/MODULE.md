# contacts

Уведомления о расхождении известных контактных данных, подтверждённом удалении и недоступности;
блок дашборда «Дубли контактов» (поиск и объединение, ADR 0022).
Контакты приложением не редактируются — кроме объединения дублей (решение владельца 2026-10-30).

- `GET /api/contact-alerts?status&before&from&to` — B24AuthGuard + AppAdminGuard, 50 записей,
  курсор и фильтры в рамках портала. Значения и данные автора — только после CrmAccessService.
  Без прав доступны лишь ID/тип/статус предупреждения (в том числе о недоступном/удалённом контакте).
  `contactName` — название из копии CRM (CrmEntity, тип 3), тоже только при видимости контакта.
- `PUT /api/contact-alerts/:id {status}` — new/viewed/resolved/ignored, статус и инициатор в журнале.
  «Принято к сведению» не восстанавливает и не меняет карточку контакта.
- `POST /api/contact-alerts/bulk {ids (≤200), status}` — «Принять все изменения» в ленте уведомлений:
  по одному через setStatus (журнал на каждое), чужой портал и уже совпадающий статус пропускаются.
- Создание ContactAlert — транзакционно с CrmEntity и ActionLog; уникальный fingerprint на портал.
  Начальная загрузка/обогащение не сигнализирует. Изменения служебных времён/флагов не сигнализируют.
  Отклонение — изменение ранее известного бизнес-поля: подтверждённое событие либо новая DATE_MODIFY.
- Удаление подтверждается ONCRMCONTACTDELETE; данные остаются tombstone. Его автор неизвестен,
  прежний MODIFY_BY_ID не является доказательством автора удаления.
- Периодическая сверка наличия по 50 известных ID с устойчивым курсором создаёт `missing`,
  если контакт перестал возвращаться. Это может быть удаление **или права**; данные не удаляются.
- ContactSyncJob доставляет новые/просмотренные предупреждения последних 3 дней в тот же alertChatId,
  что брони. Ошибка хранится, повтор — на следующем проходе. В чат идут лишь ID, тип и номер аккаунта,
  без телефонов, имён клиентов и значений полей. Повтор события не дублирует предупреждение;
  неоднозначный сетевой исход отправки сообщения может привести к повторной доставке (как у броней).
- Авторство: источник наблюдения `bitrix`, MODIFY_BY_ID — **последний редактор**, имя — из PortalEmployee.
  contactSystemUserIds отмечает системные аккаунты; это не доказывает, какое приложение/человек
  инициировали правку. `application=null` до подтверждённой корреляции с собственной операцией.
- Собственная доставка приложения имеет отдельный журнал `contact.alert_delivered`, источник system/app,
  automation=contact-alerts, operationId и executionAccountId. Не приписываем ей чужие правки CRM.

## Дубли контактов (решение владельца 2026-10-30, ADR 0022)
Контракт — `packages/shared/src/contact-duplicates.ts`. Все маршруты — `B24AuthGuard` + **`PermanentAdminGuard`**
(админы портала и список AppAdmin; доступ по временному паролю — 403 `NOT_PERMANENT_ADMIN`).

- `GET /api/contacts/duplicates?by=all|phone|email|name|messenger&q=&cursor=&limit=` (по умолчанию 30, максимум 100;
  `cursor` — смещение строкой). Источник — копия CRM (`CrmEntity`, тип 3, `deletedAt IS NULL`, портал из
  контекста): параметризованный `$queryRaw` с `JSON_EXTRACT` только NAME/LAST_NAME/SECOND_NAME/PHONE/EMAIL/IM/
  DATE_CREATE/DATE_MODIFY/ASSIGNED_BY_ID и колонкой `photo`. `photo` контакта — `CrmEntity.photo`, иначе
  `clientAvatar` его последнего чата открытой линии (`OpenlineChat.crm.contactId`, тот же портал; URL CDN — без
  токена, как в звонках); нет — null (инициалы). `messengers` — из IM: `IMOL` → коннектор из `imol|<коннектор>|…`
  (wz_whatsapp_…, btx24_telegram, fbinstagramdirect…), остальные — по VALUE_TYPE; код — `messageChannel`, только
  `DUPLICATE_CHANNELS`. Контакты группы — **старые сначала** (без даты создания — в конце).
  **ID мессенджеров** (`messenger`): поля — по ролям сопоставления полей контакта (`contactFieldMap` портала,
  `defaultCode` из SYSTEM_FIELDS и CONTACT_FIELD_CANDIDATES — поля Wazzup), код одной роли другой не достаётся;
  значения — одним `JSON_ARRAY(JSON_EXTRACT(row, ?…))`, пути параметрами, коды проверены `^UF_CRM_[A-Z0-9_]+$`.
  Пространства не смешиваются: Telegram ID (цифры) / логин Telegram (без @, строчными) / номер WhatsApp
  (`…@c.us`) / WhatsApp LID (`…@lid` и поле LID) / MAX ID / логин MAX. Union-find вместе с телефоном и почтой,
  тот же `MAX_SHARED_KEY`. Копия CRM берёт `UF_*` контакта целиком — отдельной выборки не нужно.
  На портале 2026-10-31: 64 группы по мессенджеру (Telegram 31 совпадение, MAX 54, LID — 0), максимум 3 контакта;
  `all` — 675 групп, максимум 4. Индекс в памяти api на портал, 5 минут; после объединения сбрасывается.
  Нормализация (`contact-duplicates.index.ts`): телефон — `normalizeClientPhone` (8…→7…, 10 цифр → 7…, короче —
  не ключ); почта — trim+lowercase; имя — слова NAME+LAST_NAME+SECOND_NAME строчными, ё→е, по алфавиту, меньше
  двух слов — не ключ. Телефон/почта — union-find (A~B по телефону, B~C по почте → одна группа); имя — отдельные
  группы; `all` — телефон/почта + группы по имени, не вошедшие целиком в телефон/почта-группу (иначе имя —
  дополнительная причина). Значение, общее для >5 контактов (`MAX_SHARED_KEY`) (служебный номер, «no@mail.ru»), не связывает.
  Сортировка групп: больше контактов, затем самое свежее изменение. `q` — по имени, почте, а с цифрами — по цифрам телефона.
  **Видимость:** данные копии отдаются без `CrmAccessService` — блок только для постоянных администраторов
  (решение владельца); открывать его другим ролям — только вместе с проверкой видимости.
- `GET /api/contacts/duplicates/compare?ids=1,2` (2–10) — свежие данные токеном сотрудника одним `batch`:
  `crm.contact.get`, `crm.contact.fields` (подписи, типы), `crm.deal.list {filter:{CONTACT_ID}}` (`total` — число
  сделок), затем `crm.status.list` для подписей статусов. Поля — непустые хотя бы у одного; служебные
  (ID, даты, авторы, HAS_*, ORIGIN*, LEAD_ID, COMPANY_IDS, PHOTO), только для чтения и файлы не показываются.
  PHONE/EMAIL/IM/WEB — `multi` (Битрикс24 складывает сам), `conflict` — разные заполненные значения (пробелы
  нормализованы). `suggestedPrimaryId` — больше сделок, при равенстве — старше.
- `POST /api/contacts/duplicates/merge` (`ContactMergeService`): zod; заново читает контакты; для каждого
  поля с конфликтом выбранное значение (по умолчанию — основного) пишется `crm.contact.update` в основной и в
  контакты, где поле заполнено иначе (пустое выбранное — очищает); затем `crm.entity.mergeBatch`
  `[основной, …]`. SUCCESS → удалённые помечаются `deletedAt` в копии CRM (поэтому событие удаления не создаёт
  предупреждение «контакт удалён»), индекс сбрасывается, журнал `contact.merged` (изменённые поля, idempotencyKey,
  результат). CONFLICT → `status: conflict`, поля перечитываются; уже записанные значения не откатываются
  (это выбранные значения), журнал `contact.merge_conflict`. ERROR/сбой → 502 `MERGE_FAILED`, журнал `contact.merge_failed`.
  **Идемпотентность:** повтор того же `idempotencyKey` — прежний результат из журнала (`contact.merged`),
  одновременные повторы ждут одного выполнения (в памяти api). CONFLICT не запоминается — можно повторить.
- Блок (web, `ContactDuplicatesBlock`): слева самый ранний контакт (аватарка, под ней значки мессенджеров), справа
  второй или стопка остальных с «N контактов»; при >2 контактах список раскрывается с флагом «Не объединять» —
  флаги только в состоянии блока (не сохраняются), в окно сравнения уходят лишь оставшиеся (2–10).
- Запись — только через `ContactMergeGrant` / `client.callContactMerge` (см. `bitrix24/MODULE.md`).
- Изменение основного контакта придёт событием и может дать предупреждение «изменён» (ContactAlert) — это
  ожидаемо: правку сделал сотрудник через приложение (автор в журнале `contact.merged`).
