# bitrix24

**Назначение:** единственная точка обращения к Битрикс24 — установка приложения, порталы
(тенанты) и их OAuth-токены, входящие события, REST-клиент. Доменные модули берут клиент через
`PortalService.clientFor(portal)` и не ходят в портал сами.

## Эндпоинты
| Маршрут | Назначение |
|---|---|
| `POST /api/b24/install` | URL установки локального приложения. Обмен `REFRESH_ID` на сервере авторизации → проверка `user.admin` → сохранение портала → `event.bind` |
| `GET /api/b24/install` | 400: установка открывается только из Битрикс24 |
| `POST /api/b24/install` (событие `ONAPPINSTALL`) | тот же сценарий, если в форме приложения включено «Приложение само завершает установку» (поля в `auth[...]`) |
| `GET /api/session` | кто открыл приложение (`B24AuthGuard`): портал, пользователь, isAdmin, readOnly |
| `GET /api/admin/placements`, `POST …/sync` | статус и регистрация встроек (сделка: вкладка и кнопка, левое меню) — только администратор, только явным действием |
| `POST /api/b24/app` | вход из Битрикс24: nginx отдаёт сюда `POST /`. Если портал не зарегистрирован и открыл администратор — регистрация по данным фрейма (та же проверка), затем `303` на SPA |
| `GET /api/auth/login?domain=` → `GET /api/auth/callback`, `POST /api/auth/logout` | вход вне портала через аккаунт Битрикс24 (контроллер — в `access`, сессии — `auth/web-session.service.ts`) |
| `POST /api/b24/events` | обработчик событий (`event.bind`). Проверка `auth.application_token` → журнал `Bitrix24Event` → 200 |

## Инварианты
- **Режим «только чтение» (`B24_READ_ONLY`, по умолчанию `true`; решение владельца 2026-10-21 —
  на боевом портале изменения запрещены).** Клиент отклоняет изменяющие методы до запроса
  (`READ_ONLY_MODE`), в т.ч. внутри `batch`. Разрешены чтения (`*.list|get|fields|…`) и регистрация
  самого приложения (`event.*`, `placement.*`) — см. `rest/read-only.ts`. Снимать флаг — только
  по явному разрешению владельца.
- **Доверяем только серверу авторизации.** POST установки подделываем, поэтому `member_id`,
  `client_endpoint`, токены и `user_id` берутся из ответа `oauth/token` (нужен `client_secret`).
  `SERVER_ENDPOINT` принимается только из `B24_TRUSTED_OAUTH_HOSTS`: облако — `oauth.bitrix.info`,
  российское облако (`*.bitrix24.ru`) — `oauth.bitrix24.tech` (проверено 2026-10-21: сертификат
  `*.bitrix24.tech`, ответы идентичны `oauth.bitrix.info`), «коробка» — домен портала. Новый хост
  добавлять только после такой же проверки: на него уходит `client_secret`.
- **Установить может только администратор** (`user.admin === true`).
- **Вход вне портала (решение владельца 2026-10-22).** `GET /api/auth/login` → `https://{портал}/oauth/authorize/`
  (`state` = `{portalId}.{случайное}` в cookie `btx24_login`, 10 мин) → `callback` с `code`: `state`
  совпадает с cookie, `server_domain` — из `B24_TRUSTED_OAUTH_HOSTS`, `grant_type=authorization_code`,
  `member_id` ответа = портал входа, затем `user.current` (тот же `UserTokenVerifier`) и
  `AccessService.canEnter`. Сессия `WebSession`: в cookie `btx24_session` (HttpOnly, Secure, Lax,
  30 дней скользящих) — случайный секрет, в БД — его sha256 и зашифрованные токены сотрудника;
  refresh — заранее, одним запросом на сессию; отказ сервера авторизации удаляет сессию.
  `B24AuthGuard` берёт cookie только при отсутствии Bearer и только с заголовком
  `X-Btx24-Standalone: 1` (CSRF: чужой сайт не поставит заголовок без CORS). `redirect_uri` —
  `APP_BASE_URL/api/auth/callback`, но облако возвращает на адрес обработчика (`/?code&state`) —
  nginx `web` переводит такой запрос на callback по формату `state`.
- **Секреты:** access/refresh-токены — AES-256-GCM (`ENCRYPTION_KEY`), `application_token` — только
  sha256. Токены из `auth` входящих событий в журнал не пишутся. Смена `ENCRYPTION_KEY` делает
  сохранённые токены нечитаемыми — нужна переустановка.
- **Песочница записи** (`B24_SANDBOX_*`, решение владельца 2026-10-21: тестовая сделка 678,
  брони с датами в 2020 году). При `B24_READ_ONLY=true` изменяющий вызов проходит, только если
  `SandboxWritePolicy` узнаёт его целиком: действия по сделкам из списка (кроме удаления);
  правка контактов этих сделок, их смарт-счетов (`crm.item.update` entityTypeId 31) и
  удаление/правка оплат (`crm.item.payment.*`); в чатах открытых линий этих сделок
  (`imopenlines.crm.chat.get`, решение владельца 2026-10-21) — вход `imopenlines.session.join`,
  `im.message.add` и `im.v2.File.upload` только в `chat<ID>` такого чата — принадлежность читается из Битрикс24 (кэш 1 мин);
  чат уведомлений о бронях (ADR 0007): `im.chat.add` — только пока `PortalSettings.alertChatId` пуст,
  `im.message.add` — только в него, `im.message.update` — только сообщения из `BookingAlert`; `booking.add` — период
  внутри [FROM, TO); изменение/удаление/связи — только броней из журнала `SandboxBooking`
  (созданных песочницей). Всё нераспознанное и любая запись внутри `batch` — `READ_ONLY_MODE`.
  Уборка: `node dist/scripts/sandbox-cleanup.js --member <id> [--apply]` — удаляет только брони журнала.
- **Разрешение «создавать новые»** (решение владельца 2026-10-22, `PortalSettings.createInBitrix`,
  переключатель в ⚙ → «Приложение», только постоянные администраторы): `booking.add` на любые даты
  и `crm.deal.add`. Созданное пишется в `AppCreatedEntity` (не в `SandboxBooking` — уборка его не
  тронет); дальше только с ним: связи/правка/удаление своей брони (её можно связать с любой сделкой),
  поля, товары и комментарии своей сделки. Существующие брони и сделки — только чтение; удалять
  сделки нельзя. Выключили разрешение — созданное тоже больше не меняется. Политика действует и без
  `B24_SANDBOX_*`. Смарт-счёт сделки (`crm.item.add` 31 с `parentId2`) — тоже «новое»; дальше — свой
  счёт и его оплаты, сообщение клиенту и комментарий — по сделке со счётом приложения (ADR 0009).
- **«Менять поля сделок»** (`PortalSettings.updateDealFields`, решение владельца 2026-10-22):
  `crm.deal.update` любой сделки; товары и удаление существующих сделок — нет.
- **Повторы REST** — только для того, что портал гарантированно отклонил: `QUERY_LIMIT_EXCEEDED`
  (с паузой) и `expired_token` (один refresh). Сетевые ошибки и таймауты не повторяются: `*.add`
  мог выполниться.
- **Refresh-токен меняется при каждом обмене.** Один refresh на портал в процессе (single-flight),
  перед обменом и после отказа токены перечитываются из БД — вдруг их уже обновил другой процесс
  (api/worker). Отказ сервера авторизации → `REAUTH_REQUIRED` (переустановка).
- **Лимит частоты** — «ведро токенов» на `member_id` (`B24_RATE_PER_SEC`, `B24_RATE_BURST`), отдельно
  в api и в worker. Очередь общая для всех сотрудников портала: при перегрузке запрос ждёт десятки секунд,
  а внешний прокси через ~60 с отдаёт 504 (2026-10-27). Поэтому **чтение** (метод на чтение или batch только
  из чтений) для запроса, чей клиент уже закрыл соединение (`clientGone()`, флаг `closed` в `requestContext`),
  не отправляется: `acquire` возвращает false, место в лимите не тратится, ошибка `CLIENT_GONE` (499, без
  журнала сбоев). Запись всегда доводится до конца (журнал операций, компенсация).
- **События:** проверить → сохранить → 200. Повторная доставка возможна — обработка идемпотентна.
  `ONAPPUNINSTALL` обрабатывается сразу (портал `UNINSTALLED`, токены стёрты), остальные остаются
  `PENDING` для worker.
- `batch` > 50 команд делится на части, только если в нём нет ссылок `$result[...]`.

- **Пользовательские запросы** (`B24AuthGuard`): `Authorization: Bearer <AUTH_ID>` +
  `X-B24-Member-Id` из `BX24.getAuth()`. Токен проверяется `user.current` на endpoint
  зарегистрированного портала (токен чужого портала не пройдёт), результат кэшируется по
  sha256 токена на 5 минут. Истёкший → 401 `TOKEN_EXPIRED` (интерфейс делает `BX24.refreshAuth`).
- **Встройки не регистрируются автоматически** — на боевом портале вкладка появится у всех.

## Подводные камни
- Токены приложения выданы администратору, установившему приложение, и несут его права —
  в пользовательских эндпоинтах их не использовать (только `user.client`).
- Пустые словари Битрикс24 возвращает как `[]` — `batch` нормализует `result_error` и др.

## Тесты
`*.spec.ts` рядом с кодом; `testing/fakes.ts` — Prisma в памяти и «портал + сервер авторизации» на `fetch`.

**Сбои запросов (2026-10-22).** Лимит — `RateLimiter` на портал (2/с, всплеск 30; api и worker —
отдельно). `QUERY_LIMIT_EXCEEDED` повторяется до 5 раз с паузой, `expired_token` — после обновления;
сеть и таймауты **не** повторяются (иначе `*.add` задвоит). Окончательный сбой — `onFailure`:
`PortalService` пишет его в журнал действий (`bitrix.error`, от имени сотрудника или «Система»): перегрузка,
сеть, сбой портала (`TRANSIENT_CODES`) и любые неудачные изменения; одинаковые за минуту — одной
записью. Пользователю — 503 «Битрикс24 сейчас не ответил — действие не выполнено, повторите».

**REST 3.0** (`client.callV3(method, params)`): `POST <endpoint>api/<method>`, JSON-тело, токен —
в `auth`; ответ — `result` (`items` / `item`), ошибка — `{ error: { code, message, validation } }`
(код `BITRIX_REST_V3_EXCEPTION_*`, подробности проверки — в тексте ошибки). Только чтение; повтор
после `expired_token` и лимита — как у `call`. Используется для `timeman.record.list`.

## События и встройки (2026-10-24)
- Подписки: `ONAPPUNINSTALL` (обязательная) и необязательные (`OPTIONAL_EVENTS`): звонки
  `ONVOXIMPLANTCALLINIT/START/END` (scope `telephony`), брони `ONBOOKINGADD/UPDATE/DELETE`, сделки
  `ONCRMDEALADD/UPDATE/DELETE`. При установке необязательные, которые не встали (нет права), пропускаются;
  ⚙ → «Встройки» показывает состояние, «Подключить» ставит недостающее, «Перевстроить» снимает и ставит заново.
- Встройки: вкладка и кнопка в сделке, левое меню, вкладка в окне звонка `CALL_CARD` (scope `telephony`).
  «Placement not found» при подключении — в токене ещё нет нужного права (обновить страницу после переустановки).
- Звонки обрабатываются сразу (`TelephonyCall`: номер — из начала, сотрудник — кто ответил). События броней и
  сделок только сохраняются (`PENDING`); worker `EventSyncJob` раз в 15 с запускает по ним сверку броней /
  учёт оплат одним проходом на пачку и отмечает их `PROCESSED`. Плановая сверка — страховка от потерь.


### Клиентская встройка звонка (2026-10-24)
CALL_CARD самостоятельно подгоняет высоту фрейма при старте и изменении содержимого.
placement.info().options дополняются командой JS-интерфейса getStatus (таймаут 2,5 с,
при отсутствии команды/ответа сохраняется исходный контекст).
Переход к сообщению строит путь /online/?IM_DIALOG=chat<ID>&IM_MESSAGE=<messageId>.

Переход к сообщению из CALL_CARD: полный адрес портала с IM_DIALOG/IM_MESSAGE в новой вкладке.
Через openPath страница online внутри слайдера не инициализировала мессенджер. Домены
сохраняются из session.portal.domain/SDK; режим авторизации setPortalDomain не меняет.

### Поля и контакты (уточнение владельца 2026-10-28)
Ранее разрешённое заполнение ID мессенджеров отозвано. REST-клиент блокирует add/update/delete
контактов (`crm.contact.*`, `crm.item.*` entityTypeId=3), в том числе в batch и вне readOnly,
с CONTACT_WRITE_DISABLED. Песочница также не разрешает обновление контакта сделки 678.
Создание схемы UF-поля сделки/контакта — только явным действием в «Поля»; sandbox разрешает
только тип/кратность/код/XML_ID известных ролей shared/system-fields. Данные карточек не записываются.
Сопоставленные поля контакта читаются из PortalSettings.contactFieldMap.
