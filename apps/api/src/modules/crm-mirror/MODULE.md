# crm-mirror

**Назначение:** копия CRM в базе приложения для дашборда (ADR 0013): сделки, лиды/контакты/компании,
звонки телефонии, сотрудники. Копия — кэш, не истина.

| Файл | Что |
|---|---|
| `crm-rows.ts` | поля копии, разбор строк `crm.*.list`, события CRM → что обновить |
| `crm-mirror.service.ts` | запись (только worker, токен приложения): первичная загрузка, изменения по дате, удаления, клиенты сделок и звонков, статистика линий, сотрудники |
| `crm-access.service.ts` | видимость записи сотруднику — его токеном, `select: ['ID']`; ответы хранятся (`CrmAccessCheck`), старше 5 минут — перепроверка в фоне |
| `crm-mirror.reader.ts` | чтение для дашборда: каждая выборка проходит `CrmAccessService` |
| `apps/api/src/worker/crm-mirror.job.ts` | расписание: события — каждые 5 с, изменения — раз в минуту, сотрудники — раз в 10 минут |

## Инварианты
- **Ни одна запись копии не уходит сотруднику без `CrmAccessService`** (кроме имён и аватарок
  сотрудников портала). Новый способ чтения — только через `CrmMirrorReader`.
- Звонок виден, если видна хоть одна привязка: владелец (`OWNER_TYPE_ID`/`OWNER_ID`, если это
  лид/сделка/контакт/компания) или клиент из `COMMUNICATIONS` (`callBindings`). Иначе — не виден.
- Ответ о видимости из базы показывается сразу; устаревший (≥5 минут) перепроверяется в фоне —
  не ставить фоновую проверку в путь ответа.
- Пока `CrmSyncState.backfillDoneAt` пуст (или у сделок в копии нет нужных полей — `fieldsKey`),
  дашборд читает портал, как раньше.
- Запись идемпотентна (upsert по `portalId` + ID Битрикс24); удалённое — `deletedAt`, строка остаётся.

## Подводные камни
- События CRM (`CRM_ENTITY_EVENTS`) подключает администратор в ⚙ → «Встройки»; без них изменения
  приходят раз в минуту по дате изменения. Статус `ONCRMDEAL*` в `Bitrix24Event` ведёт `EventSyncJob`,
  остальные события CRM помечает обработанными `CrmMirrorJob`.
- Проверки прав — в памяти api и в `CrmAccessCheck`; ответы старше 30 дней удаляет worker.
- Сопоставление полей сделки сменилось → сделки загружаются заново (дашборд до конца загрузки — у портала).
- В выборке сделки — базовые поля, коды системных полей (⚙ → «Приложение») и `COMMENTS` (экран внешнего
  пользователя, ADR 0021). Внешний пользователь читает копию без проверки прав сотрудника — права решает
  `external-users` (группы и видимые поля).

## Контакты и история (2026-10-28)
- Контакты синхронизирует отдельный `ContactSyncJob`: события ADD/UPDATE/DELETE из долговечной
  очереди Bitrix24Event, без отсечения по возрасту. Ошибка → FAILED, повтор не раньше минуты;
  новые события не блокируются старыми ошибками. Другой CRM job эти события не подтверждает.
- Полный снимок: `crm.contact.get` для события, `crm.contact.list` с `*, UF_*, PHONE, EMAIL, WEB, IM`
  для начальной загрузки всех контактов и периодических изменений. Курсоры начальной загрузки и
  временного окна изменений хранятся отдельно в CrmSyncState; за проход до двух страниц по 50.
- CrmEntity хранит все полученные поля; частичный ответ дополняет строку, не стирая уже известное.
  Снимок и ActionLog «было → стало» сохраняются одной транзакцией. Повтор идентичного ответа
  не добавляет историю; удаление оставляет данные и tombstone, старое событие не оживляет контакт.
- `contact.imported/changed_in_bitrix/deleted_in_bitrix` — источник bitrix; MODIFY_BY_ID и
  DATE_MODIFY сохраняются как сведения CRM, не выдаются за известного автора события приложения.
  `contact.messenger_linked` — локальная связь из приложения, сама карточка CRM не меняется.
- История начинается с первого наблюдённого снимка. REST-событие не содержит полных старых значений:
  несколько изменений до чтения могут попасть одним снимком. Исходные события остаются в Bitrix24Event.
- Данные копии по-прежнему показываются только через CrmAccessService; история доступна
  администраторам в существующем журнале действий с фильтром entityType=contact.

## Предупреждения и авторство (2026-10-28)
В той же serializable-транзакции с изменением снимка создаётся ContactAlert. Первичная загрузка
baseline — без предупреждений, но с историей. Для poll требуется рост DATE_MODIFY, для event —
подтверждённое событие; сравниваются известные бизнес-поля, служебные даты/флаги исключаются.
Журнал содержит changes/deviations и actor с последним редактором, типом учётной записи и
неизвестным инициирующим приложением. При удалении автор не выводится из прежнего редактора.
Сверка наличия отдельно проходит известные контакты по50 ID (contact_presence), не удаляет их
при пустом результате: пишет contact.missing_in_bitrix и предупреждение для проверки прав/удаления.
