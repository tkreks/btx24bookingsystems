# payments — счёт и ссылка на оплату (ADR 0009)

- `PaymentsService` (api, токен сотрудника): `GET /api/payments/preview`, `POST /api/payments`,
  `GET /api/payments?dealId`. Группа счёта (право `payment.send` в ней): выбранная в окне →
  группа брони — та, где состоит её ресурс (ресурс ровно в одной группе; запасной путь — группа
  из журнала; воронка сделки может быть другой — бронь «Бань» по сделке воронки «Домики и
  беседки») → группа воронки сделки. На одну воронку бывает несколько групп
  (Домики, Домики на воде, Беседки) — превью отдаёт `groupOptions`, окно показывает выбор.
  Создаёт смарт-счёт, пишет ID счёта в сделку и стадию оплаты группы — только если стадия из
  воронки сделки (иначе предупреждение), 20 секунд ждёт ссылку.
- Сообщение со ссылкой — системный шаблон оплаты группы (`payments.prepaymentTemplateId` /
  `surchargeTemplateId` → `MessageTemplate` с `purpose: payment`, всегда общий): шаги по порядку,
  файлы шаблона (`StoredFile`) — отдельными сообщениями. Не выбран — `clientMessage` /
  `surchargeMessage` группы или стандартный текст; шаблон пропал — стандартный текст и
  предупреждение. Выбранный в группе шаблон удалить нельзя (409 `TEMPLATE_IN_USE`).
- `PaymentFlow` — шаги после счёта, общие для api и worker: ссылка → поле сделки → сообщение
  клиенту → комментарий; ожидание → оплачено / срок вышел (снять бронь, аннулировать оплаты счёта).
- `PaymentJob` (worker, 30 с) доводит `link_pending` и `sent`; сбой заявки — `attempts++`, повтор.
- `GET /api/payments/invoices?dealId` — все смарт-счета сделки (правами сотрудника) со стадией и
  заявкой приложения; «в работе» (`invoiceInWork`) — заявка ждёт ссылку/оплату или счёт не закрыт.
  В шапке чата — «Счета · в работе N» с таймером ближайшего срока; в окне — «В работе» / «Все счета».
- Ошибка `PAYMENT_ACTIVE` («уже выставлен такой счёт») в окне оплаты сопровождается кнопкой «Перейти к
  счёту»: просмотр счёта с текстом, что ушёл клиенту, и «Отправить повторно»
  (`POST /payments/requests/:id/send` с `{ resend: true }`, `PaymentFlow.resendLink`: та же ссылка и текст,
  срок не продлевается). Сотрудник, не состоящий в чате клиента, входит в него сам
  (`imopenlines.session.join` его токеном) — worker так не делает.
- Предоплата по умолчанию для типа брони (2026-10-31, `defaultPrepaymentSteps` в shared): у группы с типами брони
  (Бани) нет шаблона оплаты и своего текста — уходит текст брони (почасовая, суточная, программы, теремок) или
  сертификата + файлы Диска из файлового шага подтверждения типа (два PDF). Выбранный шаблон группы главнее.
  Свой текст типа — `bookingTypes[].prepayment` (⚙ → группа → типы брони → «Сообщение со ссылкой на оплату»),
  главнее стандартного. Файлы Диска в заявке и в окне оплаты — `disk:<ID>` (`diskFileId`): правка текста в окне
  их не теряет.
- Запасной путь (`FlowContext.fallbackSend/fallbackSendFile`, только запрос сотрудника): Битрикс24 не принял
  сообщение/файл — пишем из мессенджера с прежней перепиской (`MessengerChatsService.dealTargets`, чат с самым
  свежим диалогом линии). Нет такого чата — прежнее предупреждение «отправьте ссылку вручную».
- Встройка сделки: «Отправить» закрывает окно и открывает чат; сообщение сразу в ленте со статусом
  (`web/bookings/pending-payment.ts`, `ChatView.pending`), счёт и ссылка создаются в фоне. Из мастера и карточки
  звонка окно работает по-прежнему.
- `GET /api/admin/invoice-meta` — воронки/стадии/поля смарт-счетов для ⚙ → группа → «Оплаты».

Ссылка аннулируется (удаляются неоплаченные оплаты счёта) и по сроку, и при «Не оплачен» в Битрикс24. «Свой» счёт —
запись в `AppCreatedEntity` (пишется при выставлении) **или** заявка с этим `invoiceId`: песочница убрана, журнал сам
не пишется, и из-за этого ссылки счетов 5268/5270/5272 оставались рабочими после срока (2026-10-31).
`PaymentJob.reannulClosed` дожимает такие закрытые заявки (пометка «ссылку не аннулируем», 7 дней).

Сообщение «не оплатили вовремя» (`expire`, любой вид оплаты и любая группа): `payments.failMessage` группы, иначе
`DEFAULT_FAIL_MESSAGE` (с 2026-10-31 — «{client_name}, напоминаем, что для подтверждения Вашей брони … мы вынуждены
снять предварительное бронирование»). Уходит **первым**, затем счёт «Не оплачен», аннулирование ссылки, снятие брони
(только предоплата). Срок — у каждой заявки свой (`deadlineAt`: срок группы или заданный менеджером). При ручном
«Не оплачен» в Битрикс24 сообщение не уходит.

Предоплата по типам брони видна и правится в «Шаблоны → Системные» («Настроить» у строки типа): текст и файлы пишутся
в `bookingTypes[].prepayment`; «Вернуть стандартный текст» удаляет своё сообщение типа.

**Очистка e-mail «wazzup»** (`PortalSettings.removeWazzupEmail`, ⚙ → «Приложение»): перед выставлением счёта и ещё раз
перед отправкой ссылки у контакта сделки удаляются только адреса, содержащие `wazzup` (платёжный сервис отклоняет оплату
с такой почтой); нормальные адреса остаются. Без уведомлений и предупреждений; сбой (нет прав, нет контакта) оплату не
останавливает. Запись — через `ContactEmailCleanupGrant` (`bitrix24/MODULE.md`).

Инварианты: ссылку не логировать; срок оплаты — только если сообщение клиенту ушло (вся цепочка шаблона); удалять
можно только оплаты счёта, созданного приложением (`AppCreatedEntity` `invoice` → `payment`);
бронь снимается только своя (политика записи).

**Сумма внесённых оплат** — `PaidAmountService.recompute` (заново по всем счетам сделки, только при
изменении; запись в журнал действий) и `worker/PaidAmountJob` (раз в 5 минут: изменённые счета и
заявки). Подробнее — `docs/features/booking-lifecycle.md`.

## Автоматические рассылки (`auto-messages.service.ts`, worker `AutoMessageJob`, раз в 5 минут)
Правила — в настройках группы (`options.autoMessages`: название, «за N часов до начала брони», окно
отправки `с–до` по времени портала, системный шаблон с назначением `auto`, вкл/выкл; пример владельца
2026-10-23 — «Просим подтвердить бронирование» за сутки, 9:00–22:00). Брони — активные клиентские
записи журнала со сделкой; группа — по ресурсу брони. Время отправки — `autoSendAt` (`@btx24/shared`):
срок вне окна сдвигается в окно того же дня (раньше 9:00 — в 9:00, позже 22:00 — за 10 минут до конца
окна); не успеть до начала брони — без рассылки. Не рассылаем: бронь сделана позже срока, бронь пропала
в Битрикс24 (ждёт решения), вне окна. Отправка — `PaymentFlow.sendChain` (чат сделки, от имени
ответственного; `SystemMessage.source = auto`), итог — комментарием в сделке. `AutoMessageLog`
(уникально правило + бронь) пишется до отправки: повтор прохода не задвоит, сбой («нет чата») не
повторяется.

### Чат контакта при новой сделке (2026-10-24)
У новой сделки может не быть чата, хотя контакт давно переписывается в открытой линии.
`PaymentFlow.chatTargets` пробует чаты сделки и чаты её `CONTACT_ID`; кандидат контакта
проверяется через `imopenlines.dialog.get` (точный `CONTACT|id`), чужой/недоступный исключается.
Отправка в такой чат — `imopenlines.crm.message.add` с `CRM_ENTITY_TYPE=contact` и ID контакта.
Старая сделка в привязке чата допустима. Для файлов и закрытой сессии сохраняется проверка
принадлежности чата сделке либо контакту. Никаких перепривязок CRM; срок оплаты по-прежнему
запускается только после успешной отправки всей цепочки. Существующие неотправленные счета
самостоятельно повторно не рассылаются.

### Рабочего чата нет — новый чат выбранным мессенджером (2026-10-26)
Окно оплаты не пишет «создайте работающий чат»: при `preview.chatProblem` вместо кнопки — мессенджеры,
где найден клиент сделки (`GET /messengers/deal-targets/:dealId`), и «Только выставить счёт». Выбор
уходит в `POST /payments` как `via: { messengerId, to }`; право писать с номера (`openlines.send`)
проверяется до создания счёта. `FlowContext.newChat` (только в запросе сотрудника) отправляет первое
сообщение цепочки через `MessengerChatsService.send(..., forDeal)` — новый чат линии сразу привязан к
контакту сделки; следующие шаги находят его как обычный рабочий чат. Ссылку не дождались за 20 с
(доводит worker, `newChat` нет) — прежнее предупреждение «нет рабочего чата», срок не идёт. У сделки
нет контакта — мессенджеров нет, окно просит указать клиента.

### Вложения и цепочки системных шаблонов (2026-10-24)
Шаблоны предоплаты и доплаты редактируются на странице Шаблоны с назначением «Сообщение об
оплате» и выбираются в Оплатах группы. Для каждого сообщения — два источника вложений:
устройство или Диск Битрикс24. Новые файлы Диска сохраняются копиями StoredFile по правам
выбравшего сотрудника. Вся цепочка уходит в порядке текст→файлы→следующий шаг; прежний
инвариант срока оплаты (вся цепочка успешно отправлена) сохраняется. Тест PaymentsService
параметризован для prepayment/surcharge. Прямая отправка из БП Битрикс24 не добавлялась.
Подтверждения брони допускают старый DiskFileRef или новый StoredClientFileRef
{storedFileId,name}; sendChain читает копию только с portalId отправки. Нет миграции БД.

**Окно оплаты из звонка (2026-10-24).** CallLayer передаёт callPlacement в PaymentDialog:
окно и кнопка восстановления закреплены сверху iframe, поскольку портал может обрезать нижнюю
часть фрейма. Обычная страница сохраняет прежнее расположение. API и создание счетов не менялись.

### Шаг отправки предоплаты в CALL_CARD (2026-10-24)
После «Товары и поля» кнопка «Далее: предоплата» создаёт бронь и открывает PaymentDialog для
этой сделки/брони. В CALL_CARD сумма и «Отправить ссылку на предоплату» стоят сразу после
заголовка, до истории счетов и параметров. Кнопка доступна в iframe1200px, обрезанном до320px.
Сумма предварительно рассчитывается сервером, допускает изменение; связь с созданной бронью
сохраняется. API/финансовые правила/шаблоны и идемпотентность не менялись. При ошибке отправки
повтор использует тот же ключ; повторно бронь не создаётся. Ошибки, busy и результат рядом
с кнопкой. Успех доставки показывается только при messageSent=true; sent без доставки явно
сообщает, что ссылка не отправлена, даёт предупреждение и возможность скопировать ссылку.
Пока ссылка формируется, нет ложного сообщения о доставке; polling истории обновляет результат.
Обычное окно счетов вне CALL_CARD сохраняет прежнюю компоновку.

### Ссылка на оплату из встройки сделки (2026-10-26)
`POST /api/payments` принимает необязательные `purpose` (основание, до 200 символов — в названии и
комментарии счёта), `timeoutHours` (1–24) и `message` (текст клиенту; `{{СсылкаНаОплату}}` — ссылка,
без переменной ссылка добавляется последней строкой, `withPaymentLink` в `@btx24/shared`). Хранятся в
`PaymentRequest.purpose / timeoutMinutes / message` (миграция `20261026000100_payment_request_custom`):
ссылку может довести worker. Свой текст заменяет шаблон оплаты группы (одно сообщение, без файлов);
свой срок действует и для доплаты. Срок доплаты вышел — только счёт «Не оплачен» и аннулирование ссылки:
бронь, стадия сделки и сообщение «не оплачено» — только для предоплаты.

### Вид «Произвольная» (`kind: 'custom'`, 2026-10-26)
Вкладка по умолчанию окна «Получить оплату» (`CustomPaymentForm`). Обязательны `amount` и `purpose`
(быстрый выбор — `PAYMENT_PURPOSES`), срок — `timeoutHours`, текст — `message` (по умолчанию
`DEFAULT_PAYMENT_LINK_MESSAGE`). Не требует брони и не привязывается к ней, не проверяет активный счёт,
не пишет ID счёта/ссылку в поля сделки и не меняет стадию; счёт — по настройкам группы в стадии
предоплаты. Срок вышел — только счёт «Не оплачен» и аннулирование ссылки. Enum `PaymentKind` + `custom`
(миграция `20261026000200_payment_kind_custom`). Переменные БП в шаблонах оплаты:
`{=Variable:paymentlink_new}` = ссылка, `{=Variable:paymentsum_new}` = сумма (`BP_VARIABLE_ALIASES`).

## Служебный чат сделки (2026-10-29)
Рабочего чата нет, а у сделки есть служебный чат (`ServiceChat`, менеджер выбрал «Без мессенджера») —
ссылка, подтверждение и автосообщения записываются туда (`source: payment | automation`), в Битрикс24 не
уходят; окно оплаты в этом случае не просит выбрать мессенджер (`chatProblem` = null). Явный выбор
мессенджера в окне (`ctx.newChat`) важнее служебного чата.

## Служебный чат (ADR 0020, 2026-10-29)
Нет рабочего чата и сотрудник не выбрал мессенджер, а у сделки есть служебный чат — текст (ссылка,
подтверждение, автосообщение) записывается туда (`source: payment|automation`), файлы — строкой с именем;
`chatProblem` тогда null. Клиенту такое сообщение передаёт менеджер.

## Окно оплаты: свой текст и вложения на одну отправку (2026-10-30)
`GET /payments/preview` дополнительно отдаёт: `templateId` (id системного шаблона оплаты, которым собран
текст; `?templateId=` — другой системный шаблон оплаты портала, чужой/не найден → 400 `TEMPLATE_NOT_FOUND`,
для `custom` параметр игнорируется), `messageText` (тексты шагов через пустую строку, переменные сделки,
`{prepayment}`, `{minutes}` подставлены, `{link}`/`{deadline}` остаются; без строк «📎»), `messageFiles`
(файлы шагов — `StoredFile` без содержимого), `deal` (`TITLE`, `OPPORTUNITY`, `CURRENCY_ID`) и `contact`
(имя — из данных шаблонов, иначе `crm.contact.get` токеном сотрудника; нет доступа → null). Поле `message`
(с «📎») — как раньше, для совместимости.
`POST /payments`: `message` — и для предоплаты/доплаты (заменяет шаблон группы одним сообщением), `fileIds`
(до `PAYMENT_MAX_FILES`, уникальные, только вместе с `message`) → `PaymentRequest.messageFileIds` (миграция
`20261030000100_payment_request_message_files`). Файл допустим, если это `StoredFile` портала, созданный
сотрудником, или файл системного шаблона оплаты портала; иначе 400 `FILE_NOT_FOUND` (до создания счёта).
Отправка (`PaymentFlow.deliver`): текст, затем файлы заявки (`withFileData`); ссылка добавляется последней
строкой, только если в тексте нет ни `{{СсылкаНаОплату}}`, ни `{link}` (и других форм ссылки
шаблонизатора — `hasPaymentLinkToken`) — `ownTextWithLink`, без задвоения. Уборка файлов
(`FilesService.dropUnused`) не трогает файлы заявок в `link_pending`/`sent`.

## Статусы счетов, архив, отправка выставленного, «ожидающие оплату» (2026-10-31)
Статус счёта для интерфейса — `invoiceDisplayStatus` (`@btx24/shared`): «Оплачен» (зелёный) /
«Проигран» (красный: стадия провала в Битрикс24 или заявка `expired|failed|cancelled`) / «Ждёт оплату»
(оранжевый: ссылка у клиента — `sent` + `messageSent`, или открытый счёт не приложения) / «Выставлен»
(синий: `link_pending` или `sent` без отправки клиенту). Стадия Битрикс24 важнее заявки.
- `GET /payments/client-invoices?dealId` теперь отдаёт **все** счета сделок контакта со `status`,
  `archived`, `requestId` и действующей бронью (`booking`: бронь заявки, иначе ближайшая бронь сделки).
  Активные — с действующей бронью в любом статусе, кроме «Проигран», плюс открытые, по которым ждём
  оплату; остальные `archived: true` (во встройке — кнопка «Архив (N)» с модальным окном).
- `GET /payments/invoice-view?dealId&invoiceId` — просмотр счёта (окно как в шаге выставления, только
  чтение): счёт из Битрикс24 правами сотрудника + заявка приложения (текст `message`, файлы, срок,
  ссылка), `complete: false` — счёт без заявки (во встройке он закрыт оверлеем «данные могут быть
  неточными» с кнопкой «Показать собранные данные»).
- `POST /payments/requests/:id/send` — отправить клиенту выставленный счёт («Выставлен»): право
  `payment.send` в группе счёта (или администратор приложения); уже отправлен → 409 `ALREADY_SENT`,
  закрыт → 409 `NOT_SENDABLE`. `PaymentFlow.sendLink`: ссылка есть — `deliver` (сообщение, срок с этого
  момента, статус станет «Ждёт оплату» сам), нет — обычный `awaitLink`.
- `GET /payments/awaiting` — блок дашборда «Счета, ожидающие оплату»: заявки `sent` с `messageSentAt`
  по группам сотрудника с `payment.send` (администратору — все), раньше истекающие сверху, без срока —
  в конце; названия сделок — `crm.deal.list` токеном сотрудника (недоступные — «Сделка #N»).
