# payments — счёт и ссылка на оплату (ADR 0009)

- `PaymentsService` (api, токен сотрудника): `GET /api/payments/preview`, `POST /api/payments`,
  `GET /api/payments?dealId`. Группа счёта (право `payment.send` в ней): выбранная в окне →
  группа брони — та, где состоит её ресурс (ресурс ровно в одной группе; запасной путь — группа
  из журнала; воронка сделки может быть другой — бронь «Бань» по сделке воронки «Домики и
  беседки») → группа воронки сделки. На одну воронку бывает несколько групп
  (Домики, Домики на воде, Беседки) — превью отдаёт `groupOptions`, окно показывает выбор.
  Создаёт смарт-счёт, пишет ID счёта в сделку и стадию оплаты группы — только если стадия из
  воронки сделки (иначе предупреждение), 20 секунд ждёт ссылку.
- Сообщение со ссылкой — системный шаблон оплаты группы (`payments.prepaymentTemplateId` /
  `surchargeTemplateId` → `MessageTemplate` с `purpose: payment`, всегда общий): шаги по порядку,
  файлы шаблона (`StoredFile`) — отдельными сообщениями. Не выбран — `clientMessage` /
  `surchargeMessage` группы или стандартный текст; шаблон пропал — стандартный текст и
  предупреждение. Выбранный в группе шаблон удалить нельзя (409 `TEMPLATE_IN_USE`).
- `PaymentFlow` — шаги после счёта, общие для api и worker: ссылка → поле сделки → сообщение
  клиенту → комментарий; ожидание → оплачено / срок вышел (снять бронь, аннулировать оплаты счёта).
- `PaymentJob` (worker, 30 с) доводит `link_pending` и `sent`; сбой заявки — `attempts++`, повтор.
- `GET /api/payments/invoices?dealId` — все смарт-счета сделки (правами сотрудника) со стадией и
  заявкой приложения; «в работе» (`invoiceInWork`) — заявка ждёт ссылку/оплату или счёт не закрыт.
  В шапке чата — «Счета · в работе N» с таймером ближайшего срока; в окне — «В работе» / «Все счета».
- `GET /api/admin/invoice-meta` — воронки/стадии/поля смарт-счетов для ⚙ → группа → «Оплаты».

Инварианты: ссылку не логировать; срок оплаты — только если сообщение клиенту ушло (вся цепочка шаблона); удалять
можно только оплаты счёта, созданного приложением (`AppCreatedEntity` `invoice` → `payment`);
бронь снимается только своя (политика записи).

**Сумма внесённых оплат** — `PaidAmountService.recompute` (заново по всем счетам сделки, только при
изменении; запись в журнал действий) и `worker/PaidAmountJob` (раз в 5 минут: изменённые счета и
заявки). Подробнее — `docs/features/booking-lifecycle.md`.

## Автоматические рассылки (`auto-messages.service.ts`, worker `AutoMessageJob`, раз в 5 минут)
Правила — в настройках группы (`options.autoMessages`: название, «за N часов до начала брони», окно
отправки `с–до` по времени портала, системный шаблон с назначением `auto`, вкл/выкл; пример владельца
2026-10-23 — «Просим подтвердить бронирование» за сутки, 9:00–22:00). Брони — активные клиентские
записи журнала со сделкой; группа — по ресурсу брони. Время отправки — `autoSendAt` (`@btx24/shared`):
срок вне окна сдвигается в окно того же дня (раньше 9:00 — в 9:00, позже 22:00 — за 10 минут до конца
окна); не успеть до начала брони — без рассылки. Не рассылаем: бронь сделана позже срока, бронь пропала
в Битрикс24 (ждёт решения), вне окна. Отправка — `PaymentFlow.sendChain` (чат сделки, от имени
ответственного; `SystemMessage.source = auto`), итог — комментарием в сделке. `AutoMessageLog`
(уникально правило + бронь) пишется до отправки: повтор прохода не задвоит, сбой («нет чата») не
повторяется.

### Чат контакта при новой сделке (2026-10-24)
У новой сделки может не быть чата, хотя контакт давно переписывается в открытой линии.
`PaymentFlow.chatTargets` пробует чаты сделки и чаты её `CONTACT_ID`; кандидат контакта
проверяется через `imopenlines.dialog.get` (точный `CONTACT|id`), чужой/недоступный исключается.
Отправка в такой чат — `imopenlines.crm.message.add` с `CRM_ENTITY_TYPE=contact` и ID контакта.
Старая сделка в привязке чата допустима. Для файлов и закрытой сессии сохраняется проверка
принадлежности чата сделке либо контакту. Никаких перепривязок CRM; срок оплаты по-прежнему
запускается только после успешной отправки всей цепочки. Существующие неотправленные счета
самостоятельно повторно не рассылаются.

### Вложения и цепочки системных шаблонов (2026-10-24)
Шаблоны предоплаты и доплаты редактируются на странице Шаблоны с назначением «Сообщение об
оплате» и выбираются в Оплатах группы. Для каждого сообщения — два источника вложений:
устройство или Диск Битрикс24. Новые файлы Диска сохраняются копиями StoredFile по правам
выбравшего сотрудника. Вся цепочка уходит в порядке текст→файлы→следующий шаг; прежний
инвариант срока оплаты (вся цепочка успешно отправлена) сохраняется. Тест PaymentsService
параметризован для prepayment/surcharge. Прямая отправка из БП Битрикс24 не добавлялась.
Подтверждения брони допускают старый DiskFileRef или новый StoredClientFileRef
{storedFileId,name}; sendChain читает копию только с portalId отправки. Нет миграции БД.

**Окно оплаты из звонка (2026-10-24).** CallLayer передаёт callPlacement в PaymentDialog:
окно и кнопка восстановления закреплены сверху iframe, поскольку портал может обрезать нижнюю
часть фрейма. Обычная страница сохраняет прежнее расположение. API и создание счетов не менялись.

### Шаг отправки предоплаты в CALL_CARD (2026-10-24)
После «Товары и поля» кнопка «Далее: предоплата» создаёт бронь и открывает PaymentDialog для
этой сделки/брони. В CALL_CARD сумма и «Отправить ссылку на предоплату» стоят сразу после
заголовка, до истории счетов и параметров. Кнопка доступна в iframe1200px, обрезанном до320px.
Сумма предварительно рассчитывается сервером, допускает изменение; связь с созданной бронью
сохраняется. API/финансовые правила/шаблоны и идемпотентность не менялись. При ошибке отправки
повтор использует тот же ключ; повторно бронь не создаётся. Ошибки, busy и результат рядом
с кнопкой. Успех доставки показывается только при messageSent=true; sent без доставки явно
сообщает, что ссылка не отправлена, даёт предупреждение и возможность скопировать ссылку.
Пока ссылка формируется, нет ложного сообщения о доставке; polling истории обновляет результат.
Обычное окно счетов вне CALL_CARD сохраняет прежнюю компоновку.

### Ссылка на оплату из встройки сделки (2026-10-26)
`POST /api/payments` принимает необязательные `purpose` (основание, до 200 символов — в названии и
комментарии счёта), `timeoutHours` (1–24) и `message` (текст клиенту; `{{СсылкаНаОплату}}` — ссылка,
без переменной ссылка добавляется последней строкой, `withPaymentLink` в `@btx24/shared`). Хранятся в
`PaymentRequest.purpose / timeoutMinutes / message` (миграция `20261026000100_payment_request_custom`):
ссылку может довести worker. Свой текст заменяет шаблон оплаты группы (одно сообщение, без файлов);
свой срок действует и для доплаты. Срок доплаты вышел — только счёт «Не оплачен» и аннулирование ссылки:
бронь, стадия сделки и сообщение «не оплачено» — только для предоплаты.

### Вид «Произвольная» (`kind: 'custom'`, 2026-10-26)
Вкладка по умолчанию окна «Получить оплату» (`CustomPaymentForm`). Обязательны `amount` и `purpose`
(быстрый выбор — `PAYMENT_PURPOSES`), срок — `timeoutHours`, текст — `message` (по умолчанию
`DEFAULT_PAYMENT_LINK_MESSAGE`). Не требует брони и не привязывается к ней, не проверяет активный счёт,
не пишет ID счёта/ссылку в поля сделки и не меняет стадию; счёт — по настройкам группы в стадии
предоплаты. Срок вышел — только счёт «Не оплачен» и аннулирование ссылки. Enum `PaymentKind` + `custom`
(миграция `20261026000200_payment_kind_custom`). Переменные БП в шаблонах оплаты:
`{=Variable:paymentlink_new}` = ссылка, `{=Variable:paymentsum_new}` = сумма (`BP_VARIABLE_ALIASES`).
