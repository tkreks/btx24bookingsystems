# Технический долг и отложенные решения

Сюда записываем найденное вне scope текущей задачи. Формат: дата, что, где, почему важно.

- 2026-10-21 — Кэш проверенных токенов пользователей (`UserTokenVerifier`) — в памяти процесса
  api; при нескольких репликах — общий кэш.
- 2026-10-21 — Лимитер REST — в памяти процесса; api и worker считают раздельно. При нескольких
  репликах api нужен общий (Redis/БД).
- 2026-10-20 — MCP `search_code` лексический (регулярки, без компилятора): диапазоны строк
  символов приблизительные, `find_references` нет. Пересмотреть, когда кода станет много.
- 2026-10-20 — Нет e2e-тестов api на реальной БД; CI проверяет только применение миграций.

## Открытые линии (PR #11)
- ~~Отправка цепочки не идемпотентна~~ — закрыто 2026-10-30 (`idempotencyKey` + `ChainSendGuard`:
  память процесса + `ActionLog` `chat.send_chain`, см. openlines/MODULE.md «Повтор отправки цепочки»).
  Остаток: без уникального индекса — дубли на разных репликах api не отсекаются, журнал ищется за 24 ч.
  Надёжно — таблица `ChainSendOperation` (`portalId, userId, idempotencyKey` unique, `status`,
  `fingerprint`, `result Json`), если api станет несколько реплик.
- Без индекса (сбор метаданных выключен) сортировка чатов приблизительная — по дате изменения дела CRM.
- Индекс видит закрытые сессии только с момента включения (первый проход — неделя назад).
- Файлы вложений хранятся в БД (LONGBLOB, ≤10 МБ). При росте — вынести в объектное хранилище.
- Обновление — опросом (30 с / 15 с); push-событий для чужих коннекторов REST не даёт.


## Оплаты (2026-10-23)
- `worker/paid-amount.job.ts`: `client.listAll('crm.item.list', …)` без `pick` — результат `{ items }`,
  поэтому список изменённых счетов всегда пуст и пересчёт «Суммы внесённых оплат» идёт только по
  заявкам приложения. Исправление включит запись поля во все сделки с изменёнными счетами —
  решить с владельцем (переключатель `updateDealFields`) прежде чем чинить.

## События Битрикс24 (2026-10-24)
- `Bitrix24Event` хранит все события навсегда; `ONCRMDEALUPDATE` приходит на каждое изменение сделки

  перейти на push (SSE/WebSocket).


## Устойчивость переписки — аудит плана Wazzup (2026-10-24)

Не исправлялось: владелец запросил только план. Блокирующие задачи до отказа от старого провайдера:
- apps/messenger/src/messages.ts Outbox: память, MAX5000/shift и потеря при рестарте; нужна постоянная
  очередь и корректное поведение при заполнении, а не молчаливое удаление принятого события.
- MessengerInboxService.apply логирует сбой отдельного события, но hook может подтвердить весь пакет;
  приём необходимо отделить от применения, ACK после постоянного сохранения каждого события.
- MessengerConnectorService.firstContact/sendFromLine: отправка до сохранения результата; нужен
  сохранённый intent/outbox и разбор таймаута с неизвестным исходом, без слепого повторного send.
- CHAT_GROUP=false в регистрации: отдельный virtualchat.id не доказывает отдельный nativeOL диалог;
  нужен контрактный пилот при нескольких сделках/номерах и модель transport thread vs business case.
- OpenlineChat — сводка, история чужих ОЛ ещё читается у Битрикс24; crm-mirror пока является кэшем.
  Для автономности нужны полноценная локальная история/медиа, собственные IDs и матрица владения.
Подробности/критерии: docs/features/wazzup-migration-and-local-core.md, ADR0016.

## Внешние пользователи (2026-10-29, ADR 0021)
- Роль «технолог»: вход отклоняется («пока не готов»); нужен экран только тех. окон (решение владельца — позже).
- Рабочие часы ресурса для «Доступности» не настраиваются — сутки 00:00–24:00, как в прототипе.
- Товары сделки не хранятся в копии CRM — экран внешнего пользователя читает их токеном приложения (кэш 5 мин).
- Нет интерфейса создания/отключения внешних пользователей и выбора `visibleFields` — только смена пароля.

## Отправка сообщений оператора и скачивание файлов портала (2026-10-30)
- Дубль `ONIMCONNECTORMESSAGEADD` отсекается замком в памяти процесса `api` (`MessengerConnectorService.once`).
  Атомарно между процессами — только записью-«заявкой» до отправки: новая таблица (например,
  `MessengerLineSend { portalId, messengerId, b24MessageId, part, status: sending|sent|failed, externalId?, error?, updatedAt }`,
  `@@unique([portalId, b24MessageId, part])`; P2002 → не отправлять; `failed`/зависшая `sending` старше N минут —
  можно перезахватить условным `updateMany`). Подходящей уникальности сейчас нет: у `MessengerMessage` уникален
  `(messengerId, externalId)` — ID мессенджера известен только после отправки; `b24MessageId` — обычный индекс.
  Нужна миграция; делать, если `api` станет больше одного экземпляра.
- `Bitrix24RestClient.download` без `{ redirects: 'portal' }` (`openlines/files.service.ts` — `disk.file.get`
  `DOWNLOAD_URL`) следует перенаправлениям `fetch` по умолчанию — на любой хост. Проверить, уводит ли Диск на
  другой хост, и перевести на `redirects: 'portal'` (или список доверенных хостов).

## Образ api: движок миграций Prisma и прокси сборки (2026-10-30)
- Исправлено: в сборочном слое `Dockerfile` есть OpenSSL — `npm ci` кладёт в образ `schema-engine-debian-openssl-3.0.x`,
  api больше не качает движок при старте (раньше зависал → api unhealthy).
- Осталось: с сервера binaries.prisma.sh (Cloudflare) напрямую недоступен, только через HTTP-прокси окружения.
  Сборка api: `docker compose -f docker-compose.yml -f docker/telegram/compose.yml build --build-arg HTTPS_PROXY=$HTTPS_PROXY --build-arg HTTP_PROXY=$HTTP_PROXY api web`
  (без прокси `npm ci` висит на загрузке движка). Можно вынести в compose `build.args`.
