# Технический долг и отложенные решения

Сюда записываем найденное вне scope текущей задачи. Формат: дата, что, где, почему важно.

- 2026-10-21 — Кэш проверенных токенов пользователей (`UserTokenVerifier`) — в памяти процесса
  api; при нескольких репликах — общий кэш.
- 2026-10-21 — Лимитер REST — в памяти процесса; api и worker считают раздельно. При нескольких
  репликах api нужен общий (Redis/БД).
- 2026-10-20 — MCP `search_code` лексический (регулярки, без компилятора): диапазоны строк
  символов приблизительные, `find_references` нет. Пересмотреть, когда кода станет много.
- 2026-10-20 — Нет e2e-тестов api на реальной БД; CI проверяет только применение миграций.

## Открытые линии (PR #11)
- Отправка цепочки не идемпотентна: при обрыве связи повтор может задублировать сообщения.
  Нужен ключ запроса и журнал отправок.
- Без индекса (сбор метаданных выключен) сортировка чатов приблизительная — по дате изменения дела CRM.
- Индекс видит закрытые сессии только с момента включения (первый проход — неделя назад).
- Файлы вложений хранятся в БД (LONGBLOB, ≤10 МБ). При росте — вынести в объектное хранилище.
- Обновление — опросом (30 с / 15 с); push-событий для чужих коннекторов REST не даёт.


## Оплаты (2026-10-23)
- `worker/paid-amount.job.ts`: `client.listAll('crm.item.list', …)` без `pick` — результат `{ items }`,
  поэтому список изменённых счетов всегда пуст и пересчёт «Суммы внесённых оплат» идёт только по
  заявкам приложения. Исправление включит запись поля во все сделки с изменёнными счетами —
  решить с владельцем (переключатель `updateDealFields`) прежде чем чинить.

## События Битрикс24 (2026-10-24)
- `Bitrix24Event` хранит все события навсегда; `ONCRMDEALUPDATE` приходит на каждое изменение сделки
  портала — нужна очистка обработанных старше N дней.
- Слой звонков опрашивает `/api/calls/active` раз в 6 с из открытого приложения; при многих сотрудниках —
  перейти на push (SSE/WebSocket).
