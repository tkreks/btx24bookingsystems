# Порядок работы над задачей

1. **Понять задачу.** Цель, ограничения, критерии готовности. Если чего-то нет — спросить или
   записать допущение явно. Для нетривиальной задачи — чекпоинт `.agent/tasks/<id>.md`
   (`TASK_TEMPLATE.md`).
2. **Собрать контекст.** Известный файл — читать напрямую. Иначе: `project_overview` (раз за
   сессию) → `search_code` → `read_source`/`get_module_context`. Перед правкой посмотреть
   вызывающих, типы, проверки доступа/тенанта и существующие тесты.
3. **План** — для изменений в нескольких модулях, схеме БД или контракте API. Короткий:
   какие файлы, какая миграция, какие тесты.
4. **Изменение.** Минимальное, в стиле окружающего кода. Общие файлы — аддитивно.
5. **Проверки.** Точечные по ходу, полный `npm run check` (или для затронутых workspace'ов)
   в конце. Изменения в БД — проверить миграцию на стенде (`db_schema` до/после).
6. **Документация** в том же изменении: `MODULE.md`, `docs/features/*`, ADR при необходимости.
7. **Отчёт.** Что сделано; команды проверок с результатом; что не проверено и почему;
   открытые вопросы.

## Диагностика стенда
`env_status` → `app_logs` (`grep` по ошибке) → `db_schema`/`db_query`. Если контейнер не
поднимается — смотреть `app_logs` для `db` и `app`; перезапуск/пересборку стенда делает
человек или агент с явного разрешения.

## Параллельная работа
Разные агенты — разные ветки/worktree и разные модули. Порядок слияния изменений в общие файлы
(`app.module.ts`, `schema.prisma`, `packages/shared/src/index.ts`) договаривается заранее.
Миграции из параллельных веток перед мёржем пересоздаются поверх актуального `main`.
