# Фоновая синхронизация дашборда

Дашборд сначала показывает доступный снимок, затем всегда выполняет запрос к API и мягко
заменяет данные отдельных блоков. Раскрытия событий, выбранные фильтры, количество
показанных строк и введённые поля не сбрасываются. Вверху по центру — статус синхронизации,
время последнего общего обновления и кнопка повторного запроса. При сетевом сбое остаётся
последний успешный результат с предупреждением; повтор происходит автоматически.

## Снимки и права

`DashboardCache` хранит разрешённые снимки в sessionStorage текущей вкладки максимум пять
минут. Ключ включает проверенные `/session` и `/groups`: портал, сотрудника, административный
доступ, роли, разрешения и ресурсы групп, а также полный URL с периодом/фильтрами.
Смена области доступа пересоздаёт дерево дашборда. Старые области и истёкшие снимки
очищаются при запуске; выход/потеря сессии очищают снимки. 401/403 удаляет результат запроса.
Токены в снимки не входят. Запрещённое хранилище iframe не мешает работе через сеть.

Снимки разрешены только для звонков, сделок/сводок, аналитики руководителя, активности,
ожидающих ответа чатов, диагностики сделок, журнала действий и сертификатов.
Базовая часть дашборда с бронями, очередь закрытия сделок, уведомления о бронях, стопы
ресурсов и рабочие смены запрашиваются заново, без сохранения снимка.

## Копия CRM вместо кэша (ADR 0013, 2026-10-24)

Сделки, контакты/лиды/компании, звонки и сотрудники дашборд берёт из базы приложения: их ведёт
worker (события CRM — за секунды, изменения по дате — раз в минуту). Что показать сотруднику,
решает Битрикс24 его токеном (проверка номеров записей). Ответы хранятся: при входе данные
показываются сразу по последним ответам, устаревшие (старше 5 минут) перепроверяются в фоне. Такие ответы идут мимо
кэша ответов (`X-Cache: db`), подпись «из кэша» у блоков не появляется. Пока первичная загрузка
копии не закончилась — данные у портала и кэш, как описано выше.

## Автообновление

Активные подписки дашборда обновляются каждые 30 секунд; ожидающие ответа чаты — каждые
15 секунд. Возврат на вкладку и восстановление сети немедленно обновляют данные. Успешная
мутация API запускает обновление через 200 мс (несколько мутаций объединяются).
В скрытой вкладке периодические запросы приостановлены. Одновременные запросы одного
ресурса объединяются. Неиспользуемые блоки не опрашиваются. Конфигурация раскладки
не перечитывается фоновым опросом, чтобы не затереть текущую настройку пользователем.

Журнал действий перечитывает первые N строк текущего фильтра, где N увеличивается по
пять кнопкой «Показать ещё». Новые события не создают пропусков между страницами.

## Календарь, список и доступность — без кэша

API-запросы браузера выполняются с `cache: no-store`; сервер выставляет `Cache-Control:
no-store`. Блоки дашборда (не календарь) сервер отдаёт из stale-while-revalidate кэша по
сотруднику: 20 с свежий, до 10 мин — сразу с пересчётом в фоне; брони дашборда и очередь
закрытия — 15 с / 2 мин. Изменение сбрасывает только свои разделы (брони, сделки, звонки, чаты,
активность) своего портала ([ADR 0012](../decisions/0012-dashboard-server-swr.md)).

Откуда данные, видно всегда: под блоком — «из кэша · данные на 14:02 · обновляем…» или
«обновлено 14:05» (заголовки `X-Cache*`); вверху — сколько блоков показаны из кэша. Пока сервер
обновляет кэш в фоне, клиент переспрашивает через 3 секунды. Блок без данных показывает
заготовку строк с надписью «Идёт загрузка данных…».

Пока нет ответа на выбранную дату/группу, поверх календаря (и таймлайна занятости в мастере)
— загрузчик «Загрузка броней…»; прежний день виден под ним, но недоступен для действий.

Календарь (включая его виды списка/доступности), занятость в мастере брони и список броней
клиента запрашиваются напрямую каждые 15 секунд, при возврате на вкладку и после действий.
Одновременные опросы не пересекаются. Нет снимков в sessionStorage, HTTP-кэша или серверного
response-cache. При смене даты/группы старый ответ не отображается для нового запроса;
возврат из дашборда в календарь всегда загружает день заново. Фоновый опрос не меняет
введённые в мастере значения. Метаданные полей самого CalendarService также без TTL.
Справочники товаров и сопоставления полей CRM не являются кэшем занятости ресурсов.

Данные остаются актуальными на момент последнего ответа, а не непрерывно: изменения извне
появляются на следующем опросе. Финальные проверки создания и пересечений выполняет API/
Битрикс24; предварительная сетка не заменяет эти проверки.

## Стабильность прокрутки и строк (2026-10-24)

Статус синхронизации занимает постоянную высоту 26px; время не исчезает на период запроса,
длинные сообщения статуса обрезаются, не переносят страницу. Одинаковые JSON-ответы сохраняют
ссылку на данные. Перед изменением данных/появлением ошибки захватывается видимая запись
дашборда; после React commit её положение восстанавливается в layout effect. Это относится как к странице,
так и к внутренней прокрутке журнала/таймлайна; внутренние списки восстанавливаются первыми. У записей звонков,
чатов, журнала и блоков стабильные ключи-якоря. В начале страницы прокрутка не корректируется:
там новые события сразу видны. Фон не вызывает повторный fitWindow по новому объекту дня.

У сетки 60 колонок убраны 59 обязательных горизонтальных gap: они давали минимум 708px и
переполнение мобильного iframe. Зазоры теперь заданы полями ячеек. Длинные сообщения
ограничены шириной блока. Для звонков — собственная горизонтальная прокрутка, одинаковая
сетка всех строк с фиксированной шириной статуса, длительности, времени и места под кнопки.
Статус: трубка и отдельная стрелка/красный крестик/значок упущенного.

Сообщения ожидающих ответа чатов — облако непосредственно за именем, по оставшейся ширине;
дата меньше времени. Число непрочитанных — маленький счётчик у правого верхнего угла аватарки (2026-10-24, владелец);
оно и стопка максимум из четырёх карточек — большее из личного `unread` (`unreadByChat`) и числа
сообщений клиента после последнего ответа сотрудника (`clientStreak`). Число ожидающих ответа
независимо от числа непрочитанных.

WebSocket/SSE не внедрены: транспорт сам не решает перемонтирование/изменение размеров DOM.
Событийная доставка может стать следующим отдельным шагом после согласования источников
событий портала, авторизации соединения и работы API/worker в разных процессах; текущий
фоновый опрос сохраняет проверку прав через обычные API-запросы.
