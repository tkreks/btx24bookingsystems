# Переход WhatsApp и Telegram на подключения приложения

Анализ 2026-10-25 по запросу владельца. MAX исключён из изменений. Это план перехода,
а не описание уже реализованной маршрутизации автоматизаций.

## Фактическое состояние

Владелец отключил два WhatsApp и Telegram от подписки прежнего провайдера. Настройки его
личного кабинета из приложения не проверялись; это исходное условие со слов владельца.
Наши три подключения в Messenger имеют состояние ready. По данным приложения:

| WhatsApp +74993467272 | 14 | 85 / 37 |
| WhatsApp +74993257916 | нет | 7 / 0 |
| Telegram БК Алатырь | 16 | 19 / 7 |

Дополнительно проверено живым REST `imopenlines.config.get`: обе линии активны (ACTIVE=Y),
в очереди каждой по два оператора; приветствия, ответы при отсутствии оператора и закрытии
отключены. CRM и CRM_CHAT_TRACKER включены на уровне линий; наш код передаёт disable_crm=Y
для выбранных/ожидающих сделок, что нужно сохранить для защиты от дублей.

Числа — снимок диагностики, не счётчики интерфейса. У этих сообщений нет relayError;
это не подтверждает доставку всех сообщений: импорт и ожидающие выбора канала сообщения
специально не передаются в ОЛ. В индексе есть старые wz_whatsapp/wz_telegram и новые
btx24_whatsapp/btx24_telegram. Прежняя история не исчезла из-за отключения подписки.

## Что сейчас делает код

- Основной список ChatsService.list — индекс OpenlineChat либо дела CRM IMOPENLINES_SESSION.
  MessengerChat без ОЛ не входит в этот список. Доступ — по правам сотрудника.
- MessengerChatsService.send умеет писать первым через собственный сервис, даже без ОЛ.
  С привязанной линией firstContact доставляет сообщение и отражает его в собственной ОЛ.
  Такое действие сейчас выполняет сотрудник; готового системного первого контакта нет.
- Новый канал найденного CRM-клиента ожидает явного выбора сотрудника, чтобы автоматически
  не открыть конкурирующую ОЛ. Входящие до выбора остаются в переписке мессенджера.
- AutoMessagesService использует PaymentFlow.sendChain; тот ищет ОЛ сделки/контакта и
  отправляет через imopenlines.crm.message.add, затем пробует im.message.add для закрытой
  сессии. Чата нет — ошибка/предупреждение, прямой отправки по телефону нет.
- Выбор не проверяет работоспособность провайдера: кандидаты идут по chatId DESC. Старый
  чат может быть выбран; принятие сообщения Битрикс24 не доказывает доставку в мессенджер.
- При disable_crm=Y локальная activeDealId не создаёт автоматически CRM-привязку чата
  Битрикс24. Поэтому одного подключения всех номеров к ОЛ недостаточно для sendChain.
- Вложения ищут boundChat отдельно от текста. При нескольких диалогах нужны единый маршрут
  всей цепочки и подтверждение доставки каждого шага.
- AutoMessageLog защищает от повторного запуска правила; failed сейчас автоматически не
  повторяется (уникальность ruleId+bookingId). Бесконтрольный retry недопустим, если доставка
  произошла, а подтверждение потерялось.

## Рекомендуемая схема

Оставить WhatsApp и Telegram у одного транспорта — приложения. Сохранить собственные ОЛ
как интерфейс операторов и источник прав; старые диалоги провайдера оставить историей.
Второй WhatsApp подключить к собственной ОЛ отдельным действием настройки. Не пытаться
перепривязать чужой провайдерский чат к нашему коннектору или переносить историю как новые
входящие: это создаст дубли, уведомления и ложные ожидания ответа.

Для приложения источником маршрута сделать явную связь:
портал → сделка → messengerId → remote chatId → собственный b24ChatId (если есть).
Точный контракт/схема требуют отдельного изменения и миграции. В UI менеджер видит клиента
и выбранный канал; старые диалоги доступны как история с обозначением отключённого канала.
Новые сообщения без собственной ОЛ должны быть доступны в общем рабочем списке и ожиданиях
с проверкой группы номера/прав, а не теряться до ручного создания ОЛ.

Автоматизация использует тот же маршрут, что сотрудник:
1. Закреплённый доступный канал сделки; при нескольких вариантах — явный выбор менеджера.
2. Если переписки ещё нет — заранее заданный канал группы и проверенный адрес клиента
   (телефон/Telegram ID). Системная отправка первого сообщения — отдельный поддерживаемый
   путь, с отражением в собственной ОЛ и CRM-журнале. Не делать пробных отправок клиенту.
3. Если канал недоступен/адрес не найден — видимая ошибка и задача сотруднику. Не менять
   WhatsApp на Telegram, номер отправителя или провайдера автоматически после ошибки:
   неизвестный результат может уже означать доставку.
4. Текст и файлы всей цепочки идут в один маршрут. Журнал каждого шага хранит ключ операции,
   внешний ID и состояния «в очереди / отправлен транспортом / подтверждён / ошибка /
   результат неизвестен». Не обещать прочтение там, где транспорт его не подтверждает.
5. Возобновление после сбоя — с неотправленного шага. Не повторять доставленное при сбое
   записи зеркала в ОЛ. Системные сообщения исключать из активности сотрудников.

Права фоновой отправки — явные настройки группы/канала и контекст портала; не создавать
поддельный B24UserContext сотрудника. Ручной выбор и существующие диалоги по-прежнему
проверяются токеном сотрудника. MAX и прочие подключения не затрагивать.

## Порядок внедрения и проверки

1. Подтвердить активность собственных линий/очереди операторов, подключить второй WA;
   сохранить существующую историю и сделать собственный канал явно выбранным у сделок.
2. Реализовать общий список с переписками без ОЛ, выбор маршрута и системный первый контакт;
   переключить PaymentFlow/AutoMessagesService на единый транспортный маршрут.
3. Добавить журнал доставки, видимые ошибки и безопасное продолжение цепочек.
4. Проверить на контакте владельца: новое исходящее без чата, ответ клиента, действующая
   и закрытая сессии, два WA одного клиента, Telegram без видимого телефона, несколько сделок,
   текст+файл, повтор события, недоступный транспорт, потеря подтверждения, изоляция порталов
   и права обычного сотрудника. Клиентам ничего не отправлять для диагностики.
5. Только после этого считать автоматизации переведёнными. Отдельно проверить активные
   роботы/БП самого Битрикс24: автоматизации приложения и роботы Wazzup — разные отправители;
   их конфигурация в этом анализе не проверялась и не менялась.

Возврат подписки имеет смысл только как временный откат к прежнему единственному транспорту,
если переписка нужна до доработки. Тогда параллельную обработку тех же каналов приложением
нужно согласованно отключить; иначе вернутся конкурирующие ОЛ. Одно восстановление подписки
не исправляет выбор канала в автоматизациях приложения.

## Официальная документация

Проверена через MCP bitrix24-docs:
- [imopenlines.crm.message.add](https://apidocs.bitrix24.com/api-reference/imopenlines/openlines/messages/imopenlines-crm-message-add.html):
  нужен существующий CRM-чат; USER_ID должен участвовать в чате и иметь доступ к CRM.
- [imconnector.send.messages](https://apidocs.bitrix24.com/api-reference/imopenlines/imconnector/imconnector-send-messages.html):
  передаёт сообщения внешнего транспорта в ОЛ, требует контекст приложения; user_id отражает
  автора-менеджера, disable_crm=Y отключает CRM tracker. Этот метод сам не доставляет сообщение
  клиенту в WhatsApp/Telegram — доставку выполняет наш сервис.
