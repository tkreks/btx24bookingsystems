# ADR 0014: Мессенджеры через браузерный сервис (начинаем с WhatsApp Web)

Статус: принято, 2026-10-24. Основание: владелец — «у нас некоторые мессенджеры в тарифе инбокс, мы не
можем писать клиентам сообщения первыми; нужен коннектор, который в некоторых ситуациях поможет
связаться с клиентом»; мастер «мессенджер (WhatsApp, Telegram, MAX) → номер телефона → экземпляр
браузера (в идеале — с подключением по VNC) → авторизация»; начать с одного WhatsApp, учитывая ещё один
WhatsApp, Telegram и MAX; позже — сопоставление с открытыми линиями Битрикс24.

## Варианты для WhatsApp

| Вариант | Как работает | За | Против |
|---|---|---|---|
| **whatsapp-web.js** (выбран) | Puppeteer + настоящий Chromium с WhatsApp Web | браузер, который можно показать по VNC; вход кодом по номеру или QR; зрелая библиотека; тот же подход годится для MAX (у него нет открытого API) | неофициально — риск ограничения номера; до ~2 ГБ памяти на номер (замер после первой синхронизации); ломается при обновлениях WhatsApp Web (обновлять библиотеку) |
| Baileys | протокол WhatsApp Web без браузера | лёгкий, быстрый | неофициально (тот же риск); нет браузера — нечего показать по VNC; для MAX не подходит |
| WAHA / Evolution API | готовый сервер поверх тех же движков | готовые REST и веб-хуки | лишний чужой сервис; у WAHA несколько сессий — платно; поверх тех же неофициальных движков |
| WhatsApp Business Cloud API | официальный API Meta | официально, без риска блокировки | первым — только одобренными платными шаблонами; номер переносится на Cloud API; верификация бизнеса |

Неофициальные способы нарушают условия WhatsApp: номер могут ограничить, особенно за массовые и
холодные рассылки. Пишем только своим клиентам и по одному — это сказано в мастере. Если понадобится
массово и без риска — Cloud API с шаблонами (отдельное решение).

## Решение
- **Сервис `messenger`** (`apps/messenger`, контейнер `messenger`, том `messenger-data`): на каждый
  номер — виртуальный экран Xvfb `:N`, x11vnc на `5900+N` (только localhost контейнера, без пароля),
  Chromium с WhatsApp Web через whatsapp-web.js; сессия входа — `LocalAuth` в томе (после перезапуска
  вход не нужен). Реестр номеров — `instances.json` в томе; истина о мессенджерах портала — база api.
  Внутренний HTTP (`/instances…`) и WebSocket VNC; наружу не публикуется, с `MESSENGER_TOKEN` — ещё и
  по токену.
- **api** (`modules/messengers`): таблица `Messenger` (портал, вид, номер, способ входа, последнее
  состояние); `⚙ → Мессенджеры` — только **постоянные** администраторы приложения
  (`PermanentAdminGuard`: номер компании — это право писать от её имени). Чужой портал мессенджер не
  видит (404). Сервис потерял номер — список поднимает его снова.
- **Прокси (владелец, 2026-10-24):** с сервера WhatsApp и Telegram напрямую недоступны (DNS не
  отвечает) — браузеры ходят через HTTP-прокси `MESSENGER_PROXY` (по умолчанию `62.233.57.133:1081`).
  Telegram — тоже через него.
- **Вход:** по умолчанию — код по номеру (whatsapp-web.js `pairWithPhoneNumber`: 8 символов вводятся
  в телефоне «Связанные устройства → Связать по номеру телефона»); можно QR — он виден на экране.
- **Экран по VNC:** администратор получает одноразовый билет (`POST …/vnc-ticket`, 1 минута), браузер
  открывает `wss://…/api/messengers/vnc?ticket=…`, api проверяет билет и проксирует WebSocket в
  сервис (`vnc-proxy.ts`), интерфейс — noVNC. Запасной вид — снимок экрана раз в 3 секунды.
- Настройки — **отдельная страница** вместо окна (владелец).

## Переписка и открытые линии (владелец, 2026-10-24)
«Сообщения могут быть отредактированы и удалены»; «кнопка сопоставления → модалка: сопоставить с ОЛ
Битрикс24 или создать свою ОЛ — приложение работает как сервер сообщений»; «чат переключается в режим
мессенджера: это и предыдущие сообщения подтягиваются из мессенджера, общение — через коннектор».

- **Переписка в базе приложения** (`MessengerChat`, `MessengerMessage`) — одна копия на портал.
  Сервис отдаёт события (`message_create` — входящие и отправленные, в том числе с телефона;
  `message_edit`; `message_revoke_everyone`; `message_ack`) в `POST /api/messengers/hook` (только
  внутри стенда, nginx закрывает путь снаружи) с повторами; api применяет их идемпотентно по ID.
  **Правка** хранит прежние тексты (`edits`), **удаление** — отметка `deletedAt`, текст остаётся.
  Своё сообщение можно изменить (WhatsApp — 15 минут) и удалить у всех из приложения.
- **Привязка к открытой линии** (владелец, 2026-10-24: «важно корректно отслеживать действия
  пользователей … привязаться к существующей ОЛ не желательно, лучше создавать новую»). Только **своя
  новая** линия (`lineMode: own`; привязка к чужой линии — WAZZUP и др. — отменена):
  `imconnector.register` (`btx24_<вид>`), `imopenlines.config.add`, `imconnector.activate`,
  `imconnector.connector.data.set`, подписка на `OnImConnector*`.
  - Клиент пишет → `imconnector.send.messages` (правка — `update.messages`, удаление —
    `delete.messages`).
  - Сотрудник пишет **через линию**: в Битрикс24 или в «Чатах» приложения (`im.message.add` его
    токеном) → линия присылает `OnImConnectorMessageAdd` → приложение доставляет через номер →
    `imconnector.send.status.delivery`. Правка/удаление — `im.message.update`/`delete` →
    `OnImConnectorMessageUpdate`/`Delete`. Действия видны в Битрикс24; права на чаты — права линии.
  - Первое сообщение клиенту, у которого ещё нет чата в линии: доставляем через номер и открываем
    чат в линии этим сообщением от имени сотрудника (`message.user_id`); эхо линии узнаётся по чату и
    тексту — второй раз не уходит.
  - **Очередь действий:** событие линии выполняется сразу; сбой (номер не подключён, сеть) —
    повтор раз в 30 с, до 5 попыток за час (`Bitrix24Event` `FAILED`, попытка — `[n]` в `error`).
- **Без привязки** номер работает **только в приложении**, напрямую через шлюз; из Битрикс24 его не
  прочитать и не написать. Доступ — **группы номера** (`Messenger.groupIds`): `openlines.read` —
  читать, `openlines.send` — писать; разграничения по чатам нет (оно — только у линии).
  Вход для сотрудников — «Чаты» → 📱.
  **Изменено 2026-10-26 (владелец):** сообщения приложения клиенту — только через рабочие открытые
  линии. Номер без привязки только принимает: отправка — `409 NO_OPENLINE` «привяжите номер к линии»;
  номер не `ready` или канал линии не подключён — `409 CHAT_NOT_WORKING`.
- История: «Загрузить историю» (последние 50 чатов × 50 сообщений) — в открытую линию не передаётся.

## Последствия
- Новый контейнер, до ~2 ГБ памяти на номер (замер 2026-10-24 после первого входа); `shm_size: 1gb`.
- Внешний прокси (Nginx Proxy Manager) должен пропускать WebSocket (`docs/deploy.md`: «Websockets
  Support» — вкл), иначе работает только снимок экрана.
- Удаление тома `messenger-data` = выход из всех аккаунтов (нужно согласие владельца, как и для БД).

## Вложения (2026-10-24)

- Сервис хранит байты в томе `messenger-data` (`/data/media/<instance>/<hash>` + JSON-метаданные),
  ID файла детерминирован по экземпляру и ID сообщения. БД хранит только ID/тип/имя/размер
  (`20261024000800_messenger_media`). Файл не раздувает таблицу переписки.
- Входящие медиа скачиваются до доставки события в api. История без файла подгружается лениво
  через POST сервиса `/instances/:id/media`; удалённые сообщения вложение через приложение не выдают.
- Максимум 64 МБ: браузер, multer, сервис/хранилище и загрузчик оператора. nginx `/send-file`
  допускает 70m вместе с multipart; прочие API по-прежнему 10m. Межсервисный base64 — до96МБ тела.
- Просмотр фото/видео/голосовых: аутентифицированный apiBlob → временный Blob URL, при смене
  чата URL освобождается. Документы скачиваются с исходным именем; HTML/SVG не исполняются как
  страницы нашего origin (attachment + CSP sandbox + nosniff). Подпись файла и выбор сохраняются
  при ошибке отправки; параллельные нажатия не отправляют повторно.
- Для открытой линии `message.files` принимает публичные `{url,name}` (проверено официальным
  MCP `imconnector.send.messages`). URL подписан HMAC (отдельный производный ключ), срок сутки,
  подпись привязана к messengerId/fileId/exp. Файлы не публикуются списком и не доступны по угадываемому ID.
- Файлы оператора из `OnImConnectorMessageAdd`: HTTPS только на самом портале, включая каждый
  redirect; лимит проверяется до/во время чтения потока. Ошибка файла не заменяется фиктивным
  успешным текстом. При повторе нескольких файлов продолжаем после уже сохранённых сообщений
  данного b24MessageId; подтверждение доставки содержит все externalId.
- Живая форма `message.files` оператора пока не подтверждена: свою линию владелец ещё не создавал.
  На тестовой переписке без линии проверяются реальные файлы, правки и удаления. Входящие события
  тестируются без отправки дополнительных сообщений клиенту.

### Совместимость WhatsApp Web (проверено на тестовых вложениях)
Новые MessageKey не содержат `_serialized`: перед downloadMedia/edit/delete дополняем его через
`ensureSerializedId` (тот же widOf). В whatsapp-web.js 1.34.7 DownloadManager вызывается без
`mimetype`, современный WA отвергает image/ptt/video как application/octet-stream. `browser-media.ts`
берёт готовый расшифрованный mediaBlob или вызывает DownloadManager с явным MIME сообщения,
с лимитом64МБ, затем сохраняет в MediaStore. Ключи шифрования/ссылки WA остаются в браузере:
из Puppeteer наружу возвращаются только MIME, имя и base64 файла. Удалённые сообщения в UI
не показывают вложения, чтение обычного media endpoint для них — 404.

## Telegram (владелец, 2026-10-24)

Владелец: «делай Telegram Web». Тот же подход, что у WhatsApp: экран Xvfb + VNC + Chromium с Telegram
Web K через тот же прокси. Готовой библиотеки автоматизации Telegram Web нет, поэтому сообщения не
разбираются со страницы: сервис вызывает **Telegram API (MTProto) клиентом самой страницы**
(`rootScope.managers.apiManager.invokeApi`) — это официальный протокол Telegram, а от внутренностей
Telegram Web зависит только точка входа. Изменения — `updates.getDifference` со своим состоянием в томе
(после перезапуска пропущенное дочитывается). Вход — только на экране (QR или номер, код и облачный
пароль), способ входа в мастере не выбирается. Подробности и подводные камни — `apps/messenger/MODULE.md`.

Последствия: номер, скрытый настройками приватности, находится через `contacts.importContacts` — он
добавляется в контакты аккаунта; Telegram ограничивает аккаунты за массовые и холодные рассылки (пишем
только своим клиентам). Отправленное из приложения на экране Telegram Web видно после обновления страницы.

## MAX (2026-10-25)

Тот же подход: экран Xvfb + VNC + Chromium с web.max.ru (MAX с сервера доступен напрямую — без прокси).
Открытого API для личного номера у MAX нет (Bot API пишет только от бота), библиотеки автоматизации тоже.
Сервис говорит **протоколом самой страницы через её же WebSocket** (`wss://api.oneme.ru/websocket`):
скрипт до загрузки страницы оборачивает `WebSocket`, копии кадров сервера уходят в сервис, свои команды
сервис шлёт в то же соединение с отрицательным `seq` (страница нумерует свои с нуля, ответы на наши ей
не показываются). Формат кадра (заголовок 10 байт + msgpack, LZ4) и коды команд взяты из кода
web.max.ru и проверены на живом соединении; команда до входа рвёт соединение — шлём только после входа.
Вход — только на экране (QR или номер и код). Пропущенное за простой дочитывается историей чатов,
изменившихся после сохранённого времени. Подробности — `apps/messenger/MODULE.md`.

Последствия: неофициальный способ — MAX может ограничить аккаунт за рассылки; при смене протокола
web.max.ru (новые коды или поля) сломаются сервисные команды, экран продолжит работать. Отправленное из
приложения на экране web.max.ru видно после обновления страницы.
