# 0003. Брони и ресурсы — в модуле бронирования Битрикс24

- Статус: принято (подтверждено владельцем 2026-10-21)
- Дата: 2026-10-20
- Заменяет часть 0001 о том, что пересечения броней защищает ограничение EXCLUDE в нашей БД.

## Контекст
Рабочий прототип (`docs/prototype/node-red-v3.md`) хранит ресурсы и брони в штатном модуле
бронирования Битрикс24 (`booking.v1.*`) и связывает каждую бронь со сделкой CRM. Сотрудники уже
видят эти брони в интерфейсе Битрикс24; бизнес-процессы оплаты завязаны на сделку.

## Решение
1. **Источник истины для ресурсов и броней — Битрикс24** (`booking.v1.resource.*`,
   `booking.v1.booking.*`). Источник истины для денег и товаров — сделка CRM.
2. Наша PostgreSQL хранит то, чего в Битрикс24 нет:
   - порталы и их OAuth-токены (зашифрованы), `application_token`, часовой пояс, маппинг UF-полей;
   - настройки: группы ресурсов, режимы времени, тех. окна, поля формы, оплаты;
   - внешних пользователей (пароль — только хеш) и их права;
   - журнал операций (многошаговое создание брони, ключи идемпотентности), аудит;
   - кэш/снимки для быстрого календаря (не источник истины, всегда можно пересобрать).
3. Пересечения броней проверяет Битрикс24 (ошибка `1018` → наш `409`); наша предварительная
   проверка — ради понятного сообщения. Ограничение EXCLUDE в нашей БД для броней не нужно;
   расширение `btree_gist` оставлено (безвредно, пригодится для локальных интервалов).
4. Все вызовы Битрикс24 — через модуль `bitrix24` (лимиты, refresh, batch, ретраи).

## Альтернатива
Собственный движок бронирования в PostgreSQL с синхронизацией в Битрикс24. Отклонено пока:
двойной источник истины, сложная синхронизация, сотрудники уже работают со штатным модулем.
Вернуться, если модуль Битрикс24 не покроет требования (например, тех. окна как блокировка).

## Последствия
- Тесты логики броней — на моках клиента Битрикс24 + контрактные проверки на тестовом портале.
- Ограничения REST (`booking.list` ≤50 без пагинации, 2 запроса/с) — забота клиента и кэша.
- Многошаговое создание (сделка → бронь → связь → товары) нужно делать как сагу с журналом и
  компенсацией, а не «один batch и надежда».
