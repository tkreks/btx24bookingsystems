# 0004. MariaDB и разбиение на контейнеры db / api / worker / web

- Статус: принято (решение владельца 2026-10-21)
- Дата: 2026-10-21
- Заменяет в ADR 0001 выбор PostgreSQL и схему «один контейнер приложения».

## Контекст
PostgreSQL выбирали ради ограничения EXCLUDE против пересекающихся броней. После ADR 0003 брони
хранит Битрикс24, и этот довод отпал. Владелец уже сопровождает MariaDB в других проектах
(бэкапы, инструменты, опыт) и хочет, чтобы проект состоял из нескольких Docker-контейнеров.

## Решение
1. **MariaDB 11.8 (LTS)**, Prisma 7 с адаптером `@prisma/adapter-mariadb`, `provider = "mysql"`.
   Сервер: `utf8mb4` / `utf8mb4_unicode_ci`, `default-time-zone=+00:00`. Время хранится в
   `DATETIME(3)` в UTC (Prisma пишет UTC); часовой пояс портала — только при отображении и
   расчётах.
2. **Контейнеры:**
   | Сервис | Образ | Назначение |
   |---|---|---|
   | `db` | `mariadb:11.8` | БД, только `127.0.0.1:${DB_HOST_PORT}` |
   | `api` | Dockerfile `target: api` | NestJS HTTP API, применяет миграции при старте, наружу не публикуется |
   | `worker` | тот же образ `api`, `node dist/worker.js` | фоновые задачи: кэш, контроль оплат по таймауту, рассылки |
   | `web` | Dockerfile `target: web` (nginx) | статика фронтенда + прокси `/api` → `api`; единственный опубликованный порт |
3. Nginx Proxy Manager проксирует на `web` (`192.168.10.15:3080`). `web` отвечает `200` и на POST
   к SPA: портал открывает обработчик POST-запросом.
4. Агентский read-only доступ к БД — пользователь `agent_ro` (`SELECT`, `SHOW VIEW`, ≤5 соединений).

## Последствия
- Частичных индексов и EXCLUDE нет; уникальность «с условием» делаем через вычисляемые колонки
  или в коде. CHECK в MariaDB работает.
- `jsonb` нет — JSON-колонки (`Json` в Prisma) хранятся как `LONGTEXT` с проверкой `JSON_VALID`.
  Всё, по чему нужен поиск, раскладываем в обычные колонки.
- Порядок старта: `db` → `api` (миграции) → `worker`, `web`.
