# 0007. Локальный календарь, синхронизация с Битрикс24 и жёсткий аудит

- Статус: принято (требование и ответы владельца 2026-10-21)
- Дата: 2026-10-21
- Меняет ADR 0003 (п. 1–2) и расширяет ADR 0006.

## Контекст
Владелец (2026-10-21): все действия с бронями должны быть прозрачны; в приложении два календаря —
**локальный** (брони приложения в нашей БД) и **онлайн-запись Битрикс24** (`booking.v1`); ресурсы
синхронизируются; каждое действие фиксируется — кто, что, как и когда, включая действия системы
(«Система: автоматизация — удаление брони при неоплате»). Расхождение между календарями (например,
бронь на будущую дату вручную изменили в Битрикс24) при очередной сверке должно уходить
сообщением в выделенный чат: «зафиксировано расхождение, как поступить?».

ADR 0003 запрещал «свою копию» броней. Это требование без копии невыполнимо: чтобы заметить
расхождение, нужно знать, какой бронь **должна быть**.

## Решение
1. **Локальная бронь** (`BookingRecord`, ADR 0006 → расширяется) — основная запись о брони,
   созданной через приложение: сделка, программа, ресурс, время, гости, комментарий, стоимость,
   предоплата, статус, срок оплаты. В Битрикс24 она **зеркалится** (`booking.v1.booking.add`),
   чтобы слот был занят и для онлайн-записи. Пересечения по-прежнему окончательно отсекает
   Битрикс24 (`1018` → `409`).
2. **Брони Битрикс24, созданные не приложением** (онлайн-запись клиентов, ручные в интерфейсе
   портала) — импортируются как записи с `source = bitrix` и показываются в приложении с пометкой.
   Сами по себе расхождением не считаются.
3. **Ресурсы** — таблица-зеркало (`Resource`): полная сверка `booking.v1.resource.list` +
   события `onBookingResourceAdd/Update/Delete`. Удалённый в Битрикс24 ресурс помечается
   архивным; если на нём есть будущие брони — это расхождение.
4. **Синхронизация броней** — два канала:
   - события `onBookingAdd/Update/Delete` (быстро; приходят только с `ID`, без автора и данных);
   - сверка worker'ом по расписанию: все брони Битрикс24 на горизонте `[сегодня, +N дней)`
     против локальных. Событие — лишь повод перечитать бронь, истина для сравнения — чтение.
5. **Расхождение** (`BookingDiscrepancy`) — открытая запись с типом (нет в Битрикс24 / другое
   время / другие ресурсы / ресурс удалён / связь со сделкой потеряна), снимками «в приложении» и
   «в Битрикс24». **Автоматически не исправляется.** Одно сообщение в чат расхождений на
   расхождение (не на каждый проход сверки) со ссылкой на экран решения: «оставить как в
   Битрикс24» / «вернуть как в приложении» / «отменить бронь». Решение — с автором в аудите.
6. **Аудит** (`BookingHistory` → журнал событий брони) — только добавление, запрет `UPDATE`/`DELETE`
   на уровне БД (триггеры). Каждая запись: действие, **тип исполнителя**
   (`user` / `system` / `bitrix` / `external`), ID и имя исполнителя (снимок), причина, источник
   (`app` / `event` / `reconcile` / `worker`), состояние до и после (diff), ID операции саги.
   Системные действия подписаны по-человечески: «Система: автоматизация — удаление брони при
   неоплате», «Система: оплата получена».
   ⚠ События Битрикс24 не сообщают, **кто** изменил бронь. Для изменений в портале исполнитель —
   «Битрикс24 (вручную или онлайн-запись)»; можно ли узнать пользователя по `auth` события —
   проверить на портале.
7. **Жизненный цикл брони** — конечный автомат: `awaiting_payment` → `confirmed` (предоплата
   получена) → `completed`; из любого активного — `cancelled` с причиной
   (`payment_timeout` / `manual` / `discrepancy`). Переходы — только через сервис, каждый — в аудит.

## Решения владельца (2026-10-21)
- Чат уведомлений — **новый** (создаёт администратор кнопкой в ⚙ → «Приложение»).
- Новая бронь в Битрикс24 не через приложение → уведомление «найдено новое бронирование».
- У каждого уведомления статус: **Новый / Просмотрен / Решено / Игнорировать**; в сообщении —
  кнопки «Открыть сделку», «Изменить бронь», «Отменить бронь».
- Стоимость пока считает менеджер (товары и цены вручную); предоплата и таймер — свои у каждой
  группы (воронки) и редактируются в настройках (у «БК Алатырь» — 25 000 ₽ и 90 минут).
- Горизонт сверки по умолчанию — 180 дней (настраивается), прошлое не сверяется.

## Как сделано
- `BookingSyncService` (worker, раз в 10 минут, токеном приложения): ресурсы → `Resource`
  (пропавшие — в архив); брони горизонта + связи со сделками → `BookingRecord`. Первый проход
  (`bookingSyncBaselineAt` пуст) принимает существующие брони **без уведомлений**.
- `BookingAlert` — уведомление с отпечатком (одно и то же расхождение — одно уведомление),
  статусом, автором статуса и ID сообщения в чате. Смена статуса обновляет сообщение
  (`im.message.update`), а если его уже нельзя править — ответом на него.
- Решения по уведомлению — от имени сотрудника, в историю брони: «принять как в Битрикс24»
  (запись следует за Битрикс24) и «отменить бронь» (`booking.delete` его токеном + статус
  «отменена»).
- Песочница: `im.chat.add` — только пока чата уведомлений нет; `im.message.add/update` — только в
  этот чат и только сообщения уведомлений.
- События `onBooking*` пока не подписаны — сверка по расписанию; подписка ускорит реакцию.
- Кнопки «Изменить/Отменить» ведут на страницу приложения `/marketplace/app/<ID>/?alert=<id>`;
  передаёт ли портал параметр во фрейм — проверить вживую (иначе — экран уведомлений вручную).

## Альтернативы
- Оставить истину только в Битрикс24 (ADR 0003): нельзя заметить расхождение и восстановить
  отменённую бронь; не выполняет требование владельца.
- Свой движок без зеркала в Битрикс24: онлайн-запись портала не увидит занятость.

## Последствия
- Два источника данных → сверка и расхождения — обязательная часть системы, а не «на потом».
- Запись в Битрикс24 (`booking.add/update/delete`) — только сагой с журналом операций и
  компенсацией; до снятия режима только чтения — в песочнице (сделка 678, даты 2020).
- Нужны: выбранный чат для расхождений, горизонт сверки, права приложения на запись в чат.
