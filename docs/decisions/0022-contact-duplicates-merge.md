# ADR 0022: дубли контактов — поиск по копии CRM, объединение через mergeBatch

Статус: принято, 2026-10-30 (решение владельца).

## Контекст
На портале много контактов одного клиента (пример: 29090 и 29650 «Виктория Трубицына»). Владелец: блок
дашборда «Дубли контактов» — найти по телефону, почте, имени и объединить с окном сравнения и выбором значений,
как в Битрикс24. Прежний запрет «контакты не редактировать» (2026-10-28) снимается только для объединения.

## Решение
1. **Поиск — по копии CRM** (`CrmEntity`, ADR 0013), а не `crm.duplicate.findbycomm`: тот ищет только по
   телефону/почте и по одному значению; ~27,5 тыс. контактов группируются в памяти api (кэш 5 минут на портал).
   Телефон/почта — union-find (связанные контакты — одна группа), имя — отдельные группы.
2. **Сравнение и объединение — по свежим данным Битрикс24 токеном сотрудника.** `crm.entity.mergeBatch`
   (первый ID — основной, остальные удаляются) возвращает CONFLICT, если заполненные поля различаются, поэтому
   сначала выбранное значение каждого конфликтующего поля записывается `crm.contact.update` в основной и в
   контакты, где оно заполнено иначе. Телефоны/почта/мессенджеры Битрикс24 складывает сам — их не пишем.
3. **Только постоянные администраторы приложения** (`PermanentAdminGuard`). Поэтому список дублей из копии
   CRM отдаётся без проверки видимости токеном сотрудника (`CrmAccessService`).
4. **Запись — узким разрешением.** `ContactMergeGrant` на конкретный набор контактов: только
   `crm.contact.update` этих контактов (без множественных полей) и один `crm.entity.mergeBatch` по ним; песочница
   (`B24_READ_ONLY`) пропускает эти методы только в его контексте. Остальной код по-прежнему не может менять
   контакты и вызывать mergeBatch (`CONTACT_WRITE_DISABLED`).
5. Идемпотентность — по `idempotencyKey` в журнале действий (`contact.merged`), без новой таблицы.

## Последствия
- CONFLICT после выравнивания возможен из-за полей, которых приложение не видит или не пишет (фото, файлы,
  скрытые поля) — тогда объединение делается в Битрикс24; выровненные значения не откатываются.
- Число сделок контакта — `crm.deal.list` с фильтром `CONTACT_ID` (как в остальных модулях); официальная
  документация не уточняет, учитываются ли неосновные привязки, — проверить на портале.
- Карточка группы (2026-10-30): самый ранний контакт слева, остальные — справа (стопкой); «Не объединять» — только
  в рамках экрана: отметка «это не дубль» на сервере требует хранения (таблица/журнал) — отдельное решение.
- 2026-10-31: причина `messenger` — один ID клиента в мессенджере в полях контакта (свои BTX24_* и Wazzup,
  по сопоставлению полей портала); номер WhatsApp и LID, ID и логин — разные пространства. Окно «?» на карточке
  показывает, что совпало.
- План: отметка «есть дубли» у контакта везде, где он показан (по тому же индексу).
