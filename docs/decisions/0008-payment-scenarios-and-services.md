# 0008. Сценарии оплаты брони и дополнительные услуги

- Статус: принято частично (2026-10-21): сценарий оплаты хранится у брони; процессы — по шагам ниже
- Дата: 2026-10-21

## Контекст
Владелец (2026-10-21): процессы оплаты нужно вынести в отдельную логику. Бывает предоплата по
ссылке (с таймером), доплата, предоплата наличными на месте, клиенты без предоплаты, полностью
бесплатные. Кроме бань и домиков — рестораны, бассейн, квадроциклы и другое, что тоже хочется
автоматизировать и учитывать.

## Решение
1. **Сценарий оплаты — свойство брони** (`BookingRecord.paymentMode`), выбирается в форме брони:
   | Сценарий | Что делает приложение |
   |---|---|
   | `prepayment` — предоплата по ссылке | счёт и ссылка → сообщение клиенту → таймер `timeoutMinutes` группы → оплачено: стадия «успех» + подтверждение; нет: снять бронь, аннулировать ссылку, стадия «неоплата» |
   | `cash_on_site` — наличными на месте | без ссылки и таймера; подтверждение клиенту сразу; оплату отмечает сотрудник на месте |
   | `postpay` — без предоплаты | без ссылки и таймера; подтверждение сразу; доплата/оплата после визита |
   | `free` — бесплатно | без счёта; подтверждение сразу; сумма сделки 0 |
   | `certificate` — сертификат | без ссылки; подтверждение сразу |
   **Доплата** — отдельный шаг для любого сценария (ссылка на остаток), не сценарий.
2. «Бесплатно» и «Без предоплаты» (`free`, `postpay`) — только у сотрудников с правами группы
   `booking.create` **и** `deal.create` (решение владельца 2026-10-22; `canUsePaymentMode` в
   @btx24/shared, проверка в саге и скрытие в форме). Право `deal.create` («Создание сделок») —
   новое: роль «Менеджер», функция группы; миграция включила его там, где было `booking.create`.
   Выбор сценария записывается в историю брони.
3. Каждый процесс оплаты — **конечный автомат** в worker (`awaiting_payment` → `confirmed` /
   `cancelled`), переходы — в историю брони с исполнителем («Система: …», сотрудник).
4. **Дополнительные услуги** (рестораны, бассейн, квадроциклы…) — те же «ресурсы» модуля
   бронирования Битрикс24 в отдельных группах со своими воронками, типами брони, сообщениями и
   сценариями оплаты. Отдельной сущности «услуга» не вводим, пока не появится то, что ресурсом не
   описывается (например, заказ без времени). Решение — вместе с владельцем по каждому направлению.

## Последствия
- Форма брони уже передаёт сценарий; создание брони не запускает оплату — это следующий шаг
  (счёт + ссылка + таймер), после снятия режима «только чтение» для оплат.
- Отчёты дашборда могут делить брони по сценариям (сколько бесплатных, наличными и т. д.).
