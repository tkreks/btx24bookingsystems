# ADR 0012: Серверный stale-while-revalidate для блоков дашборда

Статус: принято, 2026-10-24. Основание: владелец — «очень долго грузится, добавим кэш в данные
дашборда»; календарь при этом — без кэша, с загрузчиком до ответа на выбранную дату.
Уточняет ADR 0011: там завершённые ответы сервера не хранились совсем.

Блоки дашборда (`/dashboard?part=…`, `head-dashboard`, `dashboard/chat-attention`, `needs-close`,
`calls`, `call-log`, `recent-calls`, `activity`, `my-activity`) отвечают через `SwrCache`
(`apps/api/src/common/swr-cache.ts`) в `OpenlinesController`:
- до 20 секунд — готовый ответ без запросов к порталу;
- до 10 минут — готовый ответ сразу, пересчёт в фоне (следующий опрос клиента получит свежий);
- старше — ждём пересчёт. Одновременные одинаковые запросы считаются один раз.
- Брони на дашборде (`part=base`) и «Сделки к закрытию» — 15 секунд / 2 минуты.

Ключ — портал, сотрудник, название блока, параметры запроса и выведенные из прав входы (воронки,
ресурсы групп, доступ к чатам). Права проверяются на каждом запросе до кэша.

**Разделы (2026-10-24, владелец).** Ответ помечен порталом (`member_id`) и разделами данных:
`bookings`, `deals`, `calls`, `chats`, `activity` и неявно `access`. Успешное изменение сбрасывает
только свои разделы своего портала (`common/cache-invalidation.ts`):

| Изменение | Разделы |
|---|---|
| брони, стопы, уведомления о бронях, `ONBOOKING*` | bookings, deals (+ activity для запросов приложения) |
| сделки, оплаты, сертификаты, `ONCRMDEAL*` | deals, bookings |
| `ONVOXIMPLANT*` | calls, activity |
| чаты, папки, избранное, скрытие на дашборде | chats, activity |
| смена | activity |
| настройки, группы, права, установка, всё неописанное | все разделы |
| отметки входа/ошибок, раскладка, шаблоны, файлы | ничего |

Вне фрейма (cookie-сессия) портал до проверки сессии неизвестен — разделы сбрасываются у всех
порталов. Ответ, посчитанный во время изменения, отдаётся, но не запоминается.

**Видимость.** Каждый ответ блока несёт `X-Cache: fresh|stale|miss`, `X-Cache-Age` (с) и
`X-Cache-Refreshing: 1`. Клиент (`DashboardCache`) хранит источник и момент данных; пока сервер
обновляет в фоне — переспрашивает через 3 с (до 5 раз подряд). Под каждым блоком — подпись
«из кэша · данные на 14:02 · обновляем…» / «обновлено 14:05»; вверху — «Данные из кэша: N из M
· обновляем из Битрикс24…». Блок без данных — заготовка строк и «Идёт загрузка данных…».

Календарь, список, доступность и занятость в мастере брони кэш не используют (как в ADR 0011);
пока нет ответа на выбранную дату/группу, поверх них — загрузчик, прежний день под ним недоступен.

Цена: при открытии после паузы блок несколько секунд показывает ответ до 10 минут давности (с
подписью «из кэша»); изменения из worker'а (отдельный процесс, например сводки чатов) кэш API не
сбрасывают — их приносит фоновый пересчёт.

**Дальше — ADR 0013 (2026-10-24):** вместо кэша ответов дашборд читает копию CRM в базе приложения
(сделки, клиенты, звонки, сотрудники) с проверкой видимости токеном сотрудника (≤5 минут); такие
ответы идут мимо этого кэша (`X-Cache: db`). Кэш остаётся для того, что ещё запрашивается у портала. Память — до 1000
ответов на процесс. Запросы дольше 3 секунд пишутся в журнал API (`slow GET … part=…`).
