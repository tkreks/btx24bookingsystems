# ADR 0021: вход внешних пользователей по логину и паролю, экран «Бронирования»

Статус: принято, 2026-10-29 (требования владельца). Продолжает требования «Роли и доступ»
(`docs/product/requirements.md`) и раздел внешних пользователей прототипа (`/booking-view`).

## Контекст
Внешние пользователи (`ExternalUser`, роли `viewer` и `technologist`) перенесены из прототипа с
хешами паролей, но входа для них не было — только вход сотрудников через Битрикс24. Владелец:
сделать вход для `viewer` (в основном с телефона) — свой дашборд с выбором дня и бронированиями
списком, календарём и доступностью ресурсов. Технолог — позже (TECH_DEBT).

## Решение
1. **Отдельная сессия.** `POST /api/external/login {login, password, domain?}` → cookie `btx24_ext`
   (HttpOnly, Secure, SameSite=Lax), в базе — sha256 секрета (`ExternalSession`), 30 дней со
   скользящим продлением. Все запросы — с заголовком `X-Btx24-Standalone` (CSRF, как у входа
   сотрудников вне портала). Сессия сотрудника и внешнего пользователя не смешиваются: guard'ы разные
   (`B24AuthGuard` / `ExternalAuthGuard`), эндпоинты внешнего пользователя — только `/api/external/*`.
2. **Защита от подбора.** Неизвестный логин проверяется так же долго, как известный (scrypt по
   фиктивному хешу), ошибка одна — «Неверный логин или пароль». 5 неудач подряд — пауза 15 минут
   (`ExternalUser.lockedUntil`); с одного IP — не больше 20 попыток за 15 минут. Входы и неудачи —
   в журнале действий. Смена пароля администратором завершает сессии пользователя.
3. **Данные — из базы приложения.** Токена Битрикс24 у внешнего пользователя нет. Брони — журнал
   (`BookingRecord`, сверка с Битрикс24), ресурсы — их копия, сделки и имена клиентов — копия CRM
   (ADR 0013), последняя оплата — `DealPayment`. Права решает приложение: ресурсы его групп
   (`allGroups` — все группы портала), поля — `visibleFields` (null — все; коды полей сделки, псевдокоды
   `CONTACT_ID` — клиент, `PRODUCTS` — товары). Скрытые поля не уходят с сервера.
4. **Товары сделки** не хранятся в копии CRM: `GET /api/external/bookings/:id/products` читает
   `crm.deal.productrows.get` токеном приложения — только для брони на ресурсе его групп, с кэшем 5 минут.
   Это системное чтение от имени приложения: внешний пользователь видит только то, что ему разрешили
   настройки, а не права какого-либо сотрудника.
5. **Поля карточки** берутся из системных полей сделки (⚙ → «Приложение»): гости — `guests`, гости
   программы — новая роль `programGuests`, оплачено — `paidAmount`, важное примечание —
   `managerComment` («Комментарий менеджера»), комментарий — `COMMENTS`. Копия CRM добавляет
   `COMMENTS` и коды ролей в выборку (смена выборки перезагружает копию сделок в фоне).
6. **Доступность** — сутки 00:00–24:00 в поясе портала (как в прототипе): занято — брони, тех. окна —
   оранжевым (бронь не запрещают), свободно — остальное. Рабочих часов ресурса пока нет (TECH_DEBT).

## Уточнение владельца (2026-10-29)
Статус оплаты («Частично оплачено» и т. п.) пока не показывается — вместо него последняя оплата: сумма и время
последнего оплаченного счёта сделки (`crm.item.list`, тип 31, токен приложения); без счетов — `DealPayment`. Товары — сразу в карточке списка, без «Подробнее». Вход вне портала
по умолчанию — «Логин и пароль».

## Последствия
- Технолог при входе получает «вход для роли пока не готов» — экран тех. окон в TECH_DEBT.
- Пропавшие в Битрикс24 брони (уведомление не закрыто) внешнему пользователю не показываются.
- Пока копия CRM не загружена, суммы/гости показываются как «нет данных», а не нулями.
