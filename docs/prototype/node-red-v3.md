# Прототип на Node-RED («Booking Local Bitrix v3», v12/v13) — разбор

Источник: экспорт flow от владельца (2026-10-20). Сам flow в репозиторий **не кладём** — в нём
секрет (токен входящего вебхука). Этот документ — спецификация «как работает сейчас», на неё
опираемся при переписывании. Пункты «⚠» — проблемы прототипа, которые не переносим.

## 1. Главное архитектурное наблюдение
Брони и ресурсы живут **в модуле бронирования Битрикс24** (`booking.v1.resource.*`,
`booking.v1.booking.*`). Приложение — это UI + оркестратор над ним и CRM:
бронь ↔ сделка, товары сделки, поля сделки, стадии, бизнес-процессы оплаты.
Собственное хранилище прототипа — только файлы настроек и кэша (`/data/booking_local_*.json`)
и сессии в памяти Node-RED. Решение для новой версии — `docs/decisions/0003-bitrix-booking-as-source-of-truth.md`.

## 2. Точки входа (`/booking-local/*`)
| Маршрут | Назначение |
|---|---|
| `GET/POST /install` | страница установки: `placement.unbind` + `placement.bind` для `CRM_{DEAL,CONTACT,COMPANY}_DETAIL_{TOOLBAR,TAB}` → обработчик `/booking-local/app`, затем `BX24.installFinish()` |
| `GET/POST /app` | вход из Битрикс24 (iframe, POST с `AUTH_ID`, `REFRESH_ID`, `DOMAIN`, `member_id`, `PLACEMENT`, `PLACEMENT_OPTIONS`) → серверная сессия, cookie `bls_v3`, отдаёт SPA |
| `GET /booking-view` | прямая ссылка без Битрикс24: логин/пароль внешнего пользователя, только просмотр |
| `POST /auth/login`, `/auth/logout` | вход/выход внешних пользователей |
| `POST /rest/session/refresh` | пересоздание сессии из `BX24.getAuth()` клиента |
| `GET /rest/session` | контекст сессии (роль, права, сущность встройки) |
| `GET/POST /rest/settings` | настройки (группы, внешние пользователи) |
| `GET /rest/resources` | `booking.v1.resource.list` |
| `GET /rest/products` | разделы и товары каталога (`crm.productsection.list`, `crm.product.list`, постранично через `batch`) |
| `POST /rest/calendar` | брони на дату + обогащение данными сделки/контакта/товаров/оплат |
| `POST /rest/deals/search\|get\|create\|select` | выбор сделки, к которой привязывается бронь |
| `POST /rest/booking/create\|update\|delete` | операции с бронью |
| `POST /rest/booking/prepayment\|surcharge` | запуск БП ссылки на предоплату/доплату |
| `GET /rest/deal-fields\|deal-categories\|deal-stages\|bizproc-templates` | справочники для настроек |
| `POST /rest/payment-summary` | отчёт по оплатам в чат — логика в **другом flow** (не передан) |
| `POST /rest/audit` | вызывается фронтендом, но **в flow отсутствует** |

## 3. Модель настроек (settings v8)
- `defaultGroupId`, `removeWazzupEmail` (удалять e-mail с «wazzup» у клиента перед БП оплаты).
- **Группа ресурсов** (`groups[]`) — центральное понятие (бани, домики…):
  - `id`, `title`, `resourceIds[]` (ID ресурсов Битрикс24), `productSectionIds[]` (доступные разделы каталога, с потомками);
  - `kanbanCategoryId` — воронка сделок группы (фильтр броней и доступ пользователя);
  - режим времени `bookingMode`: `duration` (от клика + `durationHours`) или `interval`
    (заезд `checkInTime` / выезд `checkOutTime`, `defaultDays`, ночи);
  - `techWindowMinutes` — технологическое окно после каждой брони (уборка);
  - `defaultDesktopView` / `defaultMobileView`: `calendar` | `list` | `availability`;
  - `resourceDefaults` — товары по умолчанию для ресурса (в interval-режиме количество = число дней);
  - оплаты: `prepayment{StageId,MoveStage,TemplateId}`, `surcharge{…}`, `paymentTimeoutMinutes`,
    `paymentSuccess/Fail{StageId,TemplateId}`;
  - `dealFields[]` — поля сделки в форме: `name`, `required`, `inlineNext` (два в строку),
    `showCreate` / `showView` / `showList`.
- **Внешние пользователи** (`externalUsers[]`): `login`, `password`, `role` (`viewer` | `technologist`),
  `groupIds[]`, `permissions` (все поля или список видимых полей сделки).

## 4. Бизнес-правила
- Бронь всегда привязана к **сделке**. Открыли не из сделки (меню, контакт, компания) —
  сначала выбрать или создать сделку (для контакта/компании фильтр и привязка по ним).
- Создание брони (один `batch`, `halt=1`):
  `crm.deal.update` (поля формы, в т.ч. начало/конец брони в UF) →
  `booking.v1.booking.add` (`resourceIds`, `datePeriod` с timezone) →
  `booking.v1.booking.externalData.set` (связь с `crm/DEAL/<id>`) →
  запись ID брони в UF сделки → `crm.deal.productrows.set` (**полная замена** товаров) →
  контрольное чтение всего записанного.
- Пересечения: предварительная проверка через `booking.v1.booking.list`, окончательная —
  ошибка Битрикс24 с кодом `1018` → `409`.
- Тех. окно — **только отображение** (не блокирует бронь) и единственное, что видит технолог.
- Доступ сотрудника к группам: `crm.category.list` от имени пользователя; группа с воронкой,
  к которой нет доступа, скрывается (кэш 5 минут, «строгий» режим).
- Внешний пользователь видит только свои группы и разрешённые поля; технолог — только тех. окна.
- Оплата: по группе сделки/запросу → (опц.) перенос стадии → `bizproc.workflow.start`
  (документ `DEAL_<id>`). Факт оплаты — счета `crm.item.list` (`entityTypeId=31`, стадия `DT31_2:P`).
- Часовой пояс зашит: `Europe/Moscow`.

## 6. Особенности REST Битрикс24, выявленные прототипом
- `booking.v1.booking.list` отдаёт ≤50 записей без пагинации → прототип режет сутки на 24
  часовых окна (`filter[within]`) в одном `batch`. Учесть в клиенте (проверить актуальную документацию).
- Ограничение 2 запроса/с + повтор при `QUERY_LIMIT_EXCEEDED` (до 5 раз, пауза 800 мс).
- `bizproc.workflow.start` требует прав администратора.
- `crm.deal.productrows.set` заменяет все строки; `OPPORTUNITY` пересчитывается из товаров.

## 7. ⚠ Проблемы прототипа — не переносим
1. **Токен входящего вебхука в коде** (function-нода «Установка глобальных переменных») →
   токен нужно **перевыпустить** в портале; в новой версии — только в зашифрованном хранилище.
2. Пароли внешних пользователей хранятся открытым текстом; дефолт `viewer` / `change_me`.
3. Режим просмотра выполняет запросы через админский вебхук — права зрителя = права вебхука.
4. Настройки может менять любой пользователь Битрикс24 (нет проверки администратора),
   его сессия сохраняется как «сервисная» для запуска БП.
5. «Trusted app shell»: подмена на вебхук по заголовкам `Origin`/`Referer` (подделываемы).
6. Восстановление сессии из присланного клиентом `_bitrixAuth` без проверки на портале.
7. Токены сессий через `Math.random`, сессии в памяти процесса, срок 30 дней.
8. Cron обновляет кэш токеном «последнего зашедшего пользователя».
9. Нет обработки `ONAPPINSTALL`/`ONAPPUNINSTALL`, проверки `application_token`, хранения токенов портала.
10. Один портал и один часовой пояс зашиты в код.
11. Частичный сбой `batch` (бронь создана, следующий шаг — нет) не компенсируется.
12. Две почти одинаковые копии фронтенда (`/app` и `/booking-view`) и десятки копий одних и тех же функций в нодах.
